### 시작점 — 회고 질문 두 개

레벨2를 앞두고 화요일 토론 활동에서 두 가지 질문을 받았다.

> 나는 레벨1에서 실제로 어떻게 학습해왔는가?
> 내 학습법에서 지금 가장 안 풀리는 충돌 지점은 무엇인가?

대답을 하려고 책상에 앉았는데 솔직히 잘 기억이 안 났다. 블랙잭 사이클1·2와 장기 사이클1·2 — 두 달치 미션을 거쳤고 각 사이클마다 PR과 블로그 회고가 있었다.

그래서 Claude Code에 다음과 같이 요청했다. 실제로 보낸 프롬프트를 줄이면 대략 이 정도다.

> *"두 질문에 답해줘. (1) 레벨1에서 실제로 어떻게 학습해왔는가, (2) 학습법에서 지금 가장 안 풀리는 충돌 지점은 무엇인가.*
> *깃허브는 연결돼 있으니 `woowacourse/java-blackjack`, `woowacourse/java-janggi`의 내 PR을 보고, PR의 quote뿐 아니라 리뷰어와 주고받은 모든 코멘트까지 다 읽고 판단해줘. 블로그도 `johnprk.github.io` 레포의 `content/posts/woowacourse/` 아래 장기·블랙잭 사이클 1·2 글을 참고해줘. 3,000자 정도로, 실제 경험과 내용에 근거해서."*

Claude Code는 이 요청을 받자마자:

- `gh` CLI로 두 레포의 내 PR 4개를 본문·리뷰·인라인 코멘트까지 모두 받아오고
- `gh api`로 블로그 레포의 회고 4편 `.md`를 받아 `/tmp`에 떨궈 두고 차례로 `Read`
- 그 자료를 가지고 두 질문에 답하는 글 약 3,000자를 한 번에 출력

답변 자체는 만족스러웠다. "리뷰어 질문에 의존하는 메타인지", "막혀야 학습이 트리거되는데 AI는 막힘을 없앤다" 같은 내가 의식 못했던 패턴이 표 형태로 정돈됐다. 그 글로 토론에 들어가면 됐다.

여기서 끝났어야 했다. 그런데 끝나고 한 번 더 궁금해졌다.

> *"이 작업, 토큰을 얼마나 썼지?"*

### 발견 — cache_write 25만이 어디서 왔지

Claude Code는 모든 세션을 로컬에 jsonl로 기록한다.

```
/Users/john_park/.claude/projects/-Users-john-park-Desktop/<세션ID>.jsonl
```

이 세션 파일을 까서 매 응답의 `usage`를 합산했다. 결과는 이랬다.

| 구분 | 토큰 | 비율 |
|---|---:|---:|
| Input (캐시 미적용) | **56** | 0.00% |
| Output | **37,403** | 2.08% |
| Cache Read | **1,510,868** | 83.99% |
| Cache Write (creation) | **250,546** | 13.93% |
| **합계** | **1,798,873** | 100% |

(`assistant` 응답 31회, 약 90분 사용)

내가 새로 친 프롬프트는 56 토큰이고, Claude가 답으로 뱉은 글이 3.7만 토큰이고, 그 사이에 **151만 토큰이 캐시에서 읽혀 나왔고, 그중 25만 토큰은 새로 캐시에 적재된 분**이라는 뜻이었다.

세 가지가 걸렸다.

1. cache_read가 84%다. 이게 정상인가?
2. 콜드 input이 56? 내가 친 한국어가 전부 어디로 갔지?
3. cache_write 25만은 뭐가 들어가서 그 양이 됐지?

이걸 풀려면 prompt caching이 뭔지부터 봐야 했다.

### 원리 — Anthropic이 설명하는 prompt caching

[공식 문서](https://platform.claude.com/docs/ko/build-with-claude/prompt-caching)에서 핵심만 짚으면.

#### 1. 왜 도입됐나

> 프롬프트 캐싱을 사용하면 API 호출에서 사용된 컨텍스트를 캐시하고 후속 요청에서 재사용할 수 있어, 반복적인 작업이나 일관된 요소가 있는 프롬프트에서 비용과 지연 시간을 줄일 수 있습니다.

기본적으로 Claude는 **상태가 없다.** 100번째 메시지를 보내면 서버는 모델한테 "앞 99턴 + 이번 메시지를 처음부터 다 읽고 답해라"고 시킨다. 매번 처음부터. 이걸 그대로 두면 토큰이 대화 길이의 제곱에 비례해 부푼다. prompt caching은 *"한 번 처리한 prefix는 서버에 들고 있다가 다음 호출 때 다시 안 읽고 재사용한다"*는 장치다.

#### 2. 단가 차등

|  | Sonnet 4.5 base | 배율 |
|---|---|---|
| input (콜드) | $3 / 1M tok | 1.0× |
| output | $15 / 1M tok | 5.0× |
| **cache write** (5분 TTL) | $3.75 / 1M tok | **1.25×** |
| **cache read** | $0.30 / 1M tok | **0.1×** |

cache write는 **base보다 25% 비싸다.** 한 번 적재하는 비용을 더 받는 것. 대신 cache read는 base의 10분의 1이다. *한 번 비싸게 올리고 자주 싸게 읽는다*는 구조.

이 단가 비율이 중요하다. 같은 컨텐츠를 적어도 **3번 cache_read로 다시 읽어야** cache_write 비용이 손익분기를 넘는다. (1.25 + 0.1×3 = 1.55 vs 콜드 input 4번 = 4.0)

#### 3. 5분 TTL과 1시간 옵션

> 캐시는 5분 동안 유지되며, 캐시된 콘텐츠가 사용될 때마다 갱신됩니다.

기본 TTL은 5분. 마지막으로 cache_read가 발생한 시점부터 다시 5분이 카운트된다. 그래서 같은 세션에서 후속 질문을 *5분 안에* 보내면 캐시가 살아 있고, 5분을 넘기면 다음 질문에서 prefix를 다시 cache_write해야 한다. (별도 옵션으로 1시간 TTL을 지정할 수 있고, 그 경우 cache write 단가가 더 비싸진다 — Sonnet 기준 2×.)

#### 4. 자동 prefix 매칭과 breakpoint

> 시스템은 자동으로 가장 긴 이전 캐시 접두사를 확인합니다... 캐시 항목은 마지막 breakpoint 이후 5분 후에 만료됩니다.

여기서 *prefix*라는 말이 핵심인데, 풀어서 말하면 이렇다. Claude에 보내는 한 번의 요청은 항상 **정해진 순서대로** 쌓여 있다.

```
[1] 시스템 프롬프트 (Claude Code 본체 지시문)
  + [2] 사용 가능한 도구 정의 (MCP·skill 목록 등)
  + [3] 메모리 / CLAUDE.md / 환경 정보
  + [4] 지금까지의 대화 (turn 1, turn 2, ..., turn n-1)
  + [5] 이번 turn에 사용자가 새로 친 메시지
  ───────────────────
  → 모델이 답변 생성
```

이 묶음을 위에서부터 읽었을 때 *어디까지가 지난번과 똑같은가*가 prefix다. `[1] [2] [3]`이 지난번과 토큰 단위로 한 글자도 안 바뀌면, 거기까지가 캐시 prefix로 잡힌다. `[4]`까지 같으면 거기까지가 prefix다. **그 prefix가 끝나는 자리**가 cache breakpoint이고, 그 뒤(`[5]`나 새 turn)는 cache_write로 새로 적재된다.

요청에서 어디에 breakpoint를 박을지는 `cache_control` 파라미터로 표시한다. Claude Code 같은 클라이언트가 알아서 시스템 프롬프트 끝, 도구 정의 끝 등에 breakpoint를 넣어준다. 사용자가 의식하지 않아도 작동한다는 뜻.

다만 **prefix 중간 어디라도 한 토큰 바뀌면, 그 뒤 캐시는 전부 무효화된다.** 예를 들어 `[2] 도구 목록`이 바뀌면(skill을 하나 추가했다거나, 시스템 리마인더가 갱신됐다거나) `[3] [4]`가 그대로여도 그 뒤 prefix는 다시 cache_write해야 한다. 앞쪽이 흔들리면 뒤쪽도 같이 새로 적재.

#### 5. 최소 캐시 단위

> 최소 캐시 가능한 길이는 ... Claude Sonnet 4의 경우 1024 토큰입니다.

1024 토큰보다 짧은 블록은 캐시되지 않는다. 짧은 시스템 프롬프트만으로는 캐시가 안 만들어진다는 얘기.

### 실측 매칭 — 25만 토큰의 시간대별 풀이

원리를 들고 다시 jsonl로 돌아갔다. 이번 세션의 cache_write 25만이 한 시점에 몰린 게 아니라 시간대별로 흩어져 있었다. 한국 시간(KST)으로 묶으면.

| 구간 | 시각(KST) | 무엇을 했나 | cache_w |
|---|---|---|---:|
| **A** | 13:45 ~ 13:53 | 세션 첫 진입, 사용자 첫 메시지 | ~14,800 |
| **B** | **15:00 ~ 15:01** | **회고 자료 4편 통째 적재** | **~116,000** |
| **C** | 15:05 ~ 15:06 | 회고 답변 출력 + 후속 질문 1번 | ~10,000 |
| **D** | 15:13 ~ 15:22 | 토큰 정리용 후속 질문 4번 | ~36,000 |

#### A 구간 — 14,800 토큰: 세션 시드

세션이 켜질 때 *항상* 들어가는 부분이다. 한 번 적재되면 그 뒤로는 cache_read로 재사용된다.

내용을 분해하면:

- **시스템 프롬프트** (~7K): "You are Claude Code…" 본체 지시문, 보안·도구·응답 톤 룰
- **메모리 인덱스** (~0.3K): `MEMORY.md` + 거기서 가리키는 user profile / feedback 메모들
- **환경 정보** (~0.5K): cwd, 플랫폼, 모델 ID, 오늘 날짜
- **deferred MCP 도구 목록** (~1.5K): computer-use, Claude_in_Chrome 등 약 80개 도구의 *이름만* 시스템 리마인더로 들어옴 — 호출은 0회였는데도 목록 자체가 비용
- **사용 가능한 skill 목록** (~2K): `mission-retrospective`, `claude-api`, `update-config` 등 약 20개 skill의 *설명*
- **첫 사용자 메시지** (~0.4K): 회고 요청 1,204자

이 14K가 이 세션의 모든 후속 턴에서 cache_read로 재사용되는 시드다. *한 번 내고 31번 회수*되는 구조.

#### B 구간 — 116,000 토큰: 폭증의 본체

이게 25만의 거의 절반이다. 회고 답변을 위해 필요한 자료를 한 분 안에 와르르 적재했다.

| 턴 | 시각(KST) | cache_w | 적재된 컨텐츠 |
|--:|---|--:|---|
| T13 | 15:00:23 | 17,611 | 두 번째 사용자 메시지 진입 시 시스템 리마인더 재주입 (MCP 목록 + skill 목록 다시 들어옴) |
| T19 | 15:00:43 | 11,007 | `Read /tmp/blog_b1.md` — 블랙잭 사이클1 회고 22KB |
| T20 | 15:00:43 | (이어짐) | `Read /tmp/blog_b2.md` — 블랙잭 사이클2 회고 35KB |
| T21 | 15:00:46 | 16,533 | `Read /tmp/blog_j1.md` — 장기 사이클1 회고 33KB |
| T22 | 15:00:48 | 15,512 | `Read /tmp/blog_j2.md` — 장기 사이클2 회고 39KB |
| T23~25 | 15:01:08 | 18,353 | python으로 PR 본문 4개 파싱한 출력 — 약 12K |

회고 4편 raw text가 약 130KB(≈ 5만 토큰), PR 본문 4개가 약 38KB(≈ 1.4만 토큰), 거기에 `gh api` 메타데이터·jsonl 집계 스크립트 출력이 더해지면 110~120K가 자연스럽게 새 캐시 블록으로 잡힌다.

여기서 흥미로운 건 **T13의 17,611이다.** 이 턴은 사용자가 두 번째 메시지(회고 작성 본 요청)를 보낸 직후인데, 이때 시스템이 deferred MCP 도구 목록과 skill 목록을 *다시* 시스템 리마인더로 끼워 넣는다. 그러면 그 reminder 블록이 prefix 중간에 끼어들면서 그 뒤 prefix가 전부 다시 적재된다. **MCP 도구를 한 번도 호출하지 않았는데도 목록 존재만으로 매 사용자 메시지에 1만 토큰대 cache_write가 발생한다는 뜻**이다.

#### C, D 구간 — 36,000 + 10,000: 후속 질문의 비용

회고 답변 출력 후 5번의 후속 질문을 보냈다. 이때 cache_w가 어떻게 잡혔는지 보면 prefix 갱신의 패턴이 깨끗하게 드러난다.

| 시각(KST) | 사용자 질문 | cache_w | 왜 |
|---|---|--:|---|
| 15:13:56 | "토큰 어떻게 사용했는지" | 6,621 | 시스템 리마인더 재주입 + Bash 결과(jsonl 15개 집계 출력) |
| 15:15:00 | "이 세션 기준으로" | 1,099 | 거의 캐시 재사용 |
| 15:16:06 | "MCP 토큰" | 1,397 | 거의 캐시 재사용 |
| 15:18:46 | "cache_w 250K?" | 1,752 | 거의 캐시 재사용 |
| 15:22:48 | "한국 시간으로" | 진행 중 | — |

질문 사이 간격이 *5분 안*이라 캐시가 살아 있었다. 그래서 후속 질문 4번의 cache_w가 1~2K 수준에 머물렀다.

#### 그 1~2K는 어디서 왔나 — 시퀀스로 보기

캐시가 살아 있을 때 한 번의 후속 질문이 들어가는 흐름을 풀어 보면 이렇다. 예를 들어 15:18:46의 *"cache_w 250K?"* 질문은:

```
서버에 도착한 요청 묶음:
  [1~3] 시스템 프롬프트 + 도구 정의 + 메모리   ← 지난 턴과 동일
  [4]   T1 ~ T28까지의 대화 전체              ← 지난 턴과 동일
  [5]   "Cache Write가 250,546이나 들었는지 자세히 알고 싶어"  ← 새

서버의 처리:
  [1] ~ [4]까지 = 이전 캐시와 prefix가 일치
    → cache_read 113,616 토큰 (싸게 회수)
  [5] = 새로 들어온 부분
    → cache_write 1,752 토큰 (이번 턴에 캐시에 추가)
```

즉 "지금 내가 친 짧은 스크립트와, 그 직전에 시스템 리마인더로 끼어든 작은 블록"만 cache_write로 새로 적재되고, 나머지 113K는 cache_read로 그대로 회수됐다. 1~2K가 그 *증분의 크기*다.

#### 만약 5분을 넘겼다면 — 캐시 만료 후 시나리오

마지막 cache_read가 일어난 시점(15:22:48)부터 5분 카운트다운이 다시 시작된다. 만약 다음 질문을 *5분을 넘겨* 보냈다면 — 예컨대 30분 뒤에 *"아 그러면 cache_creation 단가가 정확히 얼마였지?"* 같은 질문을 보냈다면 — 다음 일이 일어난다.

```
요청은 똑같이 묶여서 도착:
  [1~3] 시스템 프롬프트 + 도구 정의 + 메모리
  [4]   T1 ~ T36까지의 대화 전체 (이번에는 회고 자료 116K 포함)
  [5]   새 질문

서버의 처리:
  서버 캐시를 뒤져 prefix 일치 부분을 찾는다
    → 5분 지났으니 캐시 항목이 만료돼 사라져 있음
    → 이전 prefix와 일치한다고 인정해줄 데이터가 없음
  결과:
    cache_read = 0
    cache_write = 약 130K (시스템 시드 14K + 회고 자료 116K + 새 질문)
```

여기서 중요한 점은 **"캐시를 다시 불러오는" 별도 호출이 없다는 것**이다. 캐시가 만료돼도 사용자나 클라이언트가 뭘 다시 업로드해야 하는 게 아니다. *클라이언트가 보내는 요청 묶음 안에는 항상 [1~5] 전체가 들어 있다.* 캐시는 그 묶음을 매번 처음부터 다 보내되, 서버 쪽에서 *"이 prefix는 전에 본 적 있다"*고 인정해주면 그만큼 cache_read 단가로 처리해주는 장치일 뿐이다.

그래서 "캐시 사라졌으니 다시 불러와야겠다"고 의식할 일은 없다. 클라이언트 입장에서 동작은 똑같다. 다만 *내야 할 단가만 콜드 input + cache_write 쪽으로 자동으로 밀린다.* 만료를 알아채는 길은 단 하나, **다음 turn의 `usage`에 cache_read가 0으로 찍히고 cache_write가 prefix 전체 크기만큼 잡히는 것**으로 사후 확인하는 것뿐이다.

만약 어느 한 번이라도 5분을 넘겼다면, 그 다음 질문에서 116K 회고 자료를 *다시 cache_write*해야 했을 것이고, 단가로 환산하면 약 $0.43이 한 번 더 청구됐을 것이다.

#### 회수가 실제로 일어났다는 증거

B 구간에서 적재한 116K가 후속 질문에서 cache_read로 어떻게 회수됐는지를 보면 prompt caching의 산수가 또렷하게 떨어진다.

| 후속 턴 | cache_read |
|---|---:|
| T26 (회고 출력) | 96,024 |
| T28 (토큰 정리 1차) | 105,896 |
| T30 | 112,517 |
| T31 | 113,616 |
| T32 | 115,368 |
| T34 | 116,517 |
| T36 | 118,583 |

매 턴 cache_read가 110~115K로 안정적으로 나온다. 이 숫자가 곧 *B 구간에 한 번 cache_write한 116K가 매 턴 그대로 회수되고 있다*는 사실이다. 한 번 1.25× 단가로 적재한 게, 후속 7번 응답에서 0.1× 단가로 회수됐다.

단가로 환산하면 cache_write 116K × $3.75/1M ≈ $0.43, cache_read 7회 × 113K × $0.30/1M ≈ $0.24. 만약 캐시 없이 매번 콜드 input으로 보냈다면 8회 × 116K × $3/1M ≈ **$2.78.** 약 6배 차이다.

### 정리 — 이번에 알게 된 것들

#### 1. cache_write는 한 번 내고 끝나는 비용이다

같은 세션에서 후속 질문이 많을수록 회수율이 올라간다. 이번 세션에서 116K cache_write가 7회 cache_read로 회수됐다는 건 **사실상 6배 할인된 것**과 같다. 회고처럼 큰 자료를 적재하는 작업은 *한 세션 안에서 후속 작업까지 모두 마치는* 것이 단가 측면에서 가장 합리적이다.

#### 2. 시스템 리마인더가 의외로 비싸다

MCP 도구를 한 번도 호출하지 않았는데, deferred 도구 목록이 시스템 리마인더로 매 사용자 메시지마다 재주입돼서 턴당 6~17K cache_write가 발생했다. 이번 세션의 cache_write 25만 중 *60K 이상이 시스템 리마인더 재주입분*으로 보인다. **사용자 메시지를 한 번 보낼 때마다 prefix가 한 번씩 갱신된다**는 사실은, 후속 질문을 잘게 자를수록 누적 비용이 커진다는 뜻이기도 하다.

#### 3. 5분 TTL을 의식하면 행동이 달라진다

이번에는 후속 질문 5번이 모두 5분 안에 들어가서 캐시가 살아 있었다. 만약 한 번이라도 5분을 넘겼다면 116K가 한 번 더 cache_write됐을 것. *질문을 묶어서 한 번에 보내는 것이 단순히 효율을 위한 매너가 아니라 단가에 직결된다.*

#### 4. raw text가 PDF·이미지보다 압도적으로 효율적이다

이번에 회고 4편이 .md 형태로 레포에 있었던 게 컸다. PDF였다면 같은 130KB가 cache_write에 더 많은 토큰으로 환산됐을 것이고, 이미지로 첨부했다면 비전 처리 비용까지 추가됐을 것이다. *블로그를 평문 .md로 운영하고 있었다는 사실이 우연한 비용 절감 장치였다.*

#### 5. 콜드 input은 거의 0이었다

이번 세션에서 *내가 새로 친 프롬프트의 콜드 input은 56 토큰*이다. 한국어로 환산하면 30~40자 수준. 시스템 프롬프트, MEMORY.md, skill 목록은 전부 cache 경로(주로 cache_write 후 cache_read 재사용)로 들어왔다. **Claude Code 같은 agentic 클라이언트는 거의 모든 입력을 캐시 친화적으로 라우팅한다.** 단가 환산에서 콜드 input은 사실상 무시 가능했다.

### 다음에 쓸 때의 룰

이번 한 번의 세션에서 본 것을 다음 작업에 써먹기 위해 룰 4개로 적어둔다.

1. **자료 큰 작업은 한 세션 안에서 후속까지 끝낸다.** 회고·리서치·정리처럼 본문이 큰 자료를 prefix로 적재하는 작업은 *적재 후 5분 안*에 후속 질문을 묶어서 보낸다. 다음 날로 미루면 cache_write를 또 낸다.

2. **후속 질문은 묶어서 한 번에 보낸다.** 사용자 메시지마다 시스템 리마인더가 재주입돼 1만 토큰대 cache_write를 만든다. 5개 질문을 따로 보내면 5번 갱신, 한 번에 묶으면 1번 갱신.

3. **`/clear`보다 같은 세션 추가 질문이 유리하다.** 회고 skill 운영 팁에는 Phase 사이에 `/clear`나 새 세션을 권하는데, 이건 *Phase가 명확히 끊어지는* 회고 작업에 한정된 얘기다. 한 가지 자료를 가지고 여러 각도로 파볼 때는 같은 세션에서 cache_read로 회수하는 게 단가에 유리하다.

4. **자료는 가능하면 .md로 받아둔다.** 블로그 글, 회고, 노트 — 어차피 다시 AI에 넣을 자료라면 처음부터 raw text로 보관해두면 cache_write 단가가 가장 낮은 형태로 들어간다.

이번 작업은 두 질문에 답을 받으려고 시작했다가, 답을 다 받고 나서 *답을 받은 행위 자체*를 한 번 더 분해해 보는 자리가 됐다. cache_write 25만이라는 숫자가 없었으면 굳이 들여다보지 않았을 영역이다. 다음 세션에서는 이 룰을 의식하면서 작업이 어떻게 달라지는지 한 번 더 jsonl을 까볼 생각이다.
