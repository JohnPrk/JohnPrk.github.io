사이클2의 요구사항은 사용자가 자기 예약을 조회하고, 시간을 바꾸거나 취소하는 기능이었다. 그런데 기능을 만드는 것 자체보다, 그 과정에서 생기는 예외를 어떻게 처리하느냐가 이번 미션의 진짜 중심이었다. 같은 roomescape 레포를 사이클 내내 쓰지만 매번 중심이 달랐는데, 전 미션이 API였다면 이번엔 예외 처리였다.

예외 처리를 이렇게 제대로 다뤄본 건 처음이었다. 넥스트스텝을 거치는 동안에도 깊게 파본 적 없는 주제라 처음엔 좀 당황스러웠다. 막상 들어가 보니 더 그랬다. 정상 흐름을 짤 때보다 에러를 설계할 때 애매한 결정이 훨씬 자주 나왔다. 어떤 상태 코드를 줄지, 메시지에 무엇을 담을지, 본인 확인을 어떻게 표현할지, 정답이 없는 문제들이라 매번 멈칫했다.

게다가 그 무렵은 테코톡 준비로 정신이 없었다. 그래서 이 미션을 혼자 오래 붙들고 파는 대신, 다른 크루들이 고민한 얘기를 듣고 그걸 AI로 빠르게 적용하는 쪽으로 갔다. 원래라면 더 오래 붙잡고 팠을 부분을, 이번엔 그렇게 넘겼다.

### 에러를 넘기는 일이 늘 귀찮았다

사이드 프로젝트를 하면 에러 응답 스펙을 내가 직접 정하고 맞춰야 했는데, 그 일 자체가 개발하는 것만큼 귀찮았다. 한 번 정해둬도 지키면 다행이고, 안 지키면 그 스펙을 만드는 데 쓴 시간을 그대로 날리는 셈이었다. 그렇다고 지속 가능하게 스펙을 정해두고 계속 더해 가는 일도 생각보다 쉽지 않았다. 응답 모양은 프로젝트마다, 엔드포인트마다 조금씩 달라졌고, 결국 매번 주먹구구식으로 넘겼다.

그런데 이번 미션에서 RFC 9457 `ProblemDetail`을 응답 형식으로 그대로 가져다 쓰니, 그 고민을 할 필요가 없었다. 에러 응답의 필드가 표준으로 고정돼 있었다. 응답은 대략 이런 모양이 된다.

```json
{
  "type": "https://roomescape.example/problems/not-found",
  "title": "리소스를 찾을 수 없음",
  "status": 404,
  "detail": "ID 1번 예약을 찾을 수 없습니다.",
  "instance": "/reservations/me/1"
}
```

type은 에러 종류를 가리키는 URI, title은 그 종류의 읽을 수 있는 이름, status는 상태 코드, detail은 이번 건의 구체적인 설명, instance는 문제가 난 요청 경로다. 어떤 에러가 나든 이 필드들로 응답이 나간다. 내가 매번 새로 정하던 응답 모양을, 표준이 대신 정해주고 있는 셈이었다.

그때 든 생각은 단순했다. 이걸로 통일하면 애초에 클라이언트와 응답 형식을 맞추는 커뮤니케이션 비용 자체가 안 들겠다 싶었다. 늘 병목이라고 느끼던 부분을 해결할 수 있는 좋은 방법이었다.

팀에서 합의한 규칙이 하나 있었다. 에러 응답을 받는 쪽은 사용자가 아니라 클라이언트다. 그래서 detail에 "다른 시간을 선택해주세요" 같은 다음 행동 안내는 넣지 않고, 무엇이 어떤 상태인지 조건만 적기로 했다.

### 상태코드만 보고도 무슨 에러인지

응답 형식만 표준을 따른 게 아니라, 상태코드도 의미별로 갈랐다.

예전엔 에러가 나면 400, 404, 403 정도로 러프하게 뭉뚱그렸다. 그러다 보니 같은 400이라도 그게 사용자 입력이 잘못된 건지 비즈니스 규칙을 위반한 건지, 코드를 열어봐야 알 수 있었다. 그 추적이 매번 귀찮았다.

이번엔 도메인 예외를 상태코드에 의미별로 붙였다.

```java
@ExceptionHandler(NotFoundException.class)
public ProblemDetail handleNotFound(...) { ... }               // 404, 식별자로 못 찾음

@ExceptionHandler(ConflictException.class)
public ProblemDetail handleConflict(...) { ... }               // 409, 동시성 충돌

@ExceptionHandler(BusinessRuleViolationException.class)
public ProblemDetail handleBusinessRuleViolation(...) { ... }  // 422, 정책 위반
```

404는 식별자로 리소스를 못 찾은 경우, 409는 동시성 충돌, 422는 비즈니스 정책 위반이다. 이렇게 갈라두니 상태코드만 보더라도 어떤 에러가 났는지 바로 이해할 수 있었다. 무엇이 잘못됐는지 알아내는 데 드는 인지 비용이 거의 없었다.

### 이름으로 본인 확인하는 게 맞을까

표준을 따라가면 되는 부분은 어렵지 않았다. 끝까지 "이게 맞나" 싶어 결론을 못 낸 건 하나였다. 본인 예약을 확인하는 방식이었다.

본인 예약을 조회하고 변경하고 취소하는 걸, 전부 `?name=홍길동` 쿼리 파라미터로 소유자를 확인하게 짰다.

```
GET    /reservations/me?name=홍길동
DELETE /reservations/me/{id}?name=홍길동
PUT    /reservations/me/{id}?name=홍길동
```

이름이 본인 확인 수단이 못 된다는 건 처음부터 분명했다. 동명이인도 있고, 쿼리 파라미터는 로그나 히스토리에 그대로 남는다. 본질적으로 권한 검증이라기보다 필터에 가까웠다. 그렇다고 세션이나 토큰 인증을 붙이는 건 이 미션 범위에선 과한 확장이라고 봤다. 인증과 인가는 아직 다루지 않는 단계였으니, `?name=`은 그 빈자리를 메우는 차선책이었다.

그래서 타협을 했다. 가장 단순한 식별 수단으로 이름을 쓰되, URL을 `/reservations/me`로 따로 둬서 관리자 경로와 분리했다. 권한 책임이 여기 있다는 신호라도 코드에 남기고 싶었다. 그리고 남의 이름으로 접근했을 때는, 자원이 있다는 사실 자체를 숨기려고 403이 아니라 404로 응답하게 했다.

```java
public Reservation findMyReservation(Long id, String name) {
    return reservationRepository.findById(id)
            .filter(r -> r.getName().equals(name))
            .orElseThrow(() -> new NotFoundException(...));
}
```

그런데 짜고 나서도 계속 걸렸다. 이 코드는 본인 확인을 하는 척하지만 실제로는 안 하는 것에 가까웠다. 이름만 맞으면 통과하니까. 차라리 `?name=`을 본인 확인이 아니라 단순 필터라고 솔직하게 정의하고, 권한 검증을 코드에서 아예 빼는 게 더 정직한 설계일 수도 있었다. 결국 404가 맞는지 403이 맞는지 스스로 답을 못 냈고, 그대로 리뷰어에게 물었다.

### 리뷰가 잡아준 것들

PR을 올리고 며칠 뒤에 1차 리뷰가 왔다. 결과는 CHANGES_REQUESTED였지만 큰 구조를 뜯어고치라는 지적은 없었다. 내가 확신이 없어 질문으로 남겨둔 것에 답이 왔고, 내가 미처 못 본 부분을 몇 개 짚어줬다.

**본인 확인은 404가 아니라 401이었다.**

③에서 끝까지 답을 못 낸 게 이 본인 확인 응답이었다. 자원이 있다는 사실을 숨기려고 404로 했는데, 그게 맞는지 403이 맞는지 모르겠어서 "실서비스에선 그럴 일 없겠지만"이라는 단서까지 달아 그대로 물어봤다. 질문으로 남긴 것 자체가 내 선택에 확신이 없어서였다. 웨지의 답은 이랬다.

> 글쎄요, 말씀주신 것처럼 벌어질 일 없는 일이지만 보안이 안 되는건 차치하고 name이라는 인증체계를 의도하신거니 저는 401 아닌가 싶네요?

읽자마자 맞는 말이라고 생각했다. 내가 붙잡고 있던 건 404냐 403이냐였는데, 정작 어긋난 건 그 앞이었다. name을 본인 확인 수단으로 의도해놓고, 응답에서는 "그런 리소스 없다"(404)고 말하고 있었다. 인증을 하려던 자리에서, 인증 실패를 인증 실패라고 말하지 않은 셈이었다. 누가 봐도 이해할 수 있는 쪽이 낫다고 생각하는 편이라 의견을 듣고 바로 401로 돌렸다.

그래서 존재 확인과 소유자 확인을 갈라냈다.

```java
// [before 제출] 이름이 안 맞으면 filter에서 걸러져 똑같이 404
return reservationRepository.findById(id)
        .filter(r -> r.getName().equals(name))
        .orElseThrow(() -> new NotFoundException(...));        // 404

// [after 리뷰 후] 없으면 404, 본인 게 아니면 401로 분리
Reservation reservation = reservationRepository.findById(id)
        .orElseThrow(() -> new NotFoundException(...));        // 404, 진짜 없음
if (!reservation.getName().equals(name)) {
    throw new UnauthorizedException("본인의 예약이 아닙니다.");   // 401, 본인 아님
}
return reservation;
```

before는 조회와 본인 확인이 filter 한 줄에 뭉쳐 있어서, 예약이 없든 남의 예약이든 결과가 똑같이 404였다. after는 존재를 먼저 확인해 없으면 404, 있는데 이름이 안 맞으면 401을 던진다. 본인 확인을 하는 척만 하던 코드가, 이제 본인이 아니면 401로 분명히 거부한다.

401로 바꾸고 나니 고민이 하나 더 따라왔다. HTTP 표준(RFC 7235)은 401을 응답할 때 WWW-Authenticate 헤더로 어떤 인증 방식을 쓰는지 클라이언트에 알려주라고 권한다. 그런데 이번엔 그 헤더를 넣지 않기로 했다. name이 쿼리 파라미터로 들어오는 식별 수단인데, 헤더로는 Bearer나 Basic 같은 표준 인증 스킴을 안내하는 건 앞뒤가 맞지 않았다. 진짜 로그인 체계는 다음 선택미션(인증과 인가)에서 다룰 부분이라, 그때 표준에 맞춰 다시 정의하기로 미뤘다. 이번엔 상태 코드와 ProblemDetail 본문만 401로 맞췄다.

**slug과 title은 한 쌍이었다.**

내가 물어본 것 말고, 웨지가 먼저 짚어준 것도 있었다.

> 20 ~ 26라인, 28~34라인은 각각 한 쌍인데 enum으로 묶어줘도 되겠네요.

그때 내 코드는 ProblemDetail에 들어갈 slug과 title을 String 상수 두 개로 따로 선언해두고 있었다. 짚이고 나서 보니 이 둘은 항상 같이 다니는 한 쌍인데, 따로 떨어뜨려 두니 한쪽만 고치면 어긋날 수 있는 구조였다. ProblemType enum으로 묶었다.

```java
public enum ProblemType {
    NOT_FOUND("not-found", "리소스를 찾을 수 없음"),
    CONFLICT("conflict", "요청이 현재 상태와 충돌함"),
    // ... 종류마다 slug과 title을 한 줄로
}
```

묶고 나서 따라온 게 두 가지 있었다. 하나는 테스트였다. 웨지는 problemType까지 정의했으니 테스트에서도 그 타입 코드를 검증하는 게 좋겠다고 덧붙였는데, enum으로 모으니 테스트가 매직 스트링 대신 ProblemType.NOT_FOUND.uri() 같은 값을 직접 참조하게 됐다. enum이 바뀌면 테스트가 그대로 따라온다. 전에는 응답 타입을 테스트에 문자열로 베껴 적어둔 거라 코드와 따로 놀았는데, 그게 정리됐다.

다른 하나는 같은 상태 코드를 의미로 가를 수 있게 된 거였다. 같은 404라도, 식별자로 못 찾은 경우와 경로 자체가 없는 경우는 클라이언트가 받아들이는 의미가 다르다. enum이 종류를 들고 있으니 NOT_FOUND와 NO_RESOURCE를 따로 둘 수 있었다. 상태 코드 하나에 의미를 하나로 뭉뚱그리지 않아도 됐다.

이 enum 정리는 미션 도중에 따로 글로도 남겨뒀다. 여기서 더 들어가면 핸들러가 예외를 어떻게 거쳐 가는지 내부 얘기라, 깊은 부분은 그 글로 미룬다.

돌이켜보면 이 반영들도 내가 코드를 붙들고 직접 깨우친 건 아니었다. 방향을 틀게 한 계기는 웨지의 리뷰였고, 어떻게 고칠지는 대체로 AI로 정리해서 반영했다.

### 사이클2를 마치며

리뷰를 반영하고 답을 정리해 올리자 웨지가 머지했다. 마지막까지 하나 걸린 건 로깅 표지였다. 요청 경로나 메서드를 못 읽어내는 상황에서 로그에 아무 표시도 안 남는데, "[Can't Parsing]" 같은 표지라도 남겨두라는 코멘트였다. 그건 끝내 반영하지 못한 채 미션이 마무리됐다. 남은 숙제로 적어뒀다.

사실 이번 미션에서 내가 트레이드오프를 길게 저울질해 고른 결정은 별로 없었다. 응답 형식은 RFC 9457 ProblemDetail이라는 표준이 있었고, 상태 코드를 의미별로 나누는 방식도 명확했다. 더 나은 대안이 따로 있는 것도 아니었다. 그러니 고민 끝에 골랐다기보다, 명확한 표준을 그대로 가져다 따랐다는 쪽이 맞는 것 같다. 시간이 부족했는데, 다행히 다른 크루들의 이야기를 듣고 핵심 주제에 대해서는 AI를 통해서 빠르게 학습하고 빠르게 적용했다.

그게 아쉽진 않다. 표준이 분명할 때는 그걸 따르는 게 맞다고 생각하는 편이고, 이번엔 중요한 걸 빠르게 가져왔다는 감각이 더 컸다.

남는 것도 분명했다. ProblemDetail과 상태 코드 분기는, 클라이언트와도 동료 서버 개발자와도 같은 말로 에러를 이야기하게 해주는 공통의 기준이었다. 다음 프로젝트에서도 이건 그대로 가져갈 것 같다. 진짜 인증과 인가는 다음 선택미션의 몫으로 남았고, 401에 WWW-Authenticate를 어떻게 줄지도 그때 다시 볼 부분이다.

다만 하나는 솔직하게 적어둔다. 직접 부딪혀가며 익힌 게 아니다 보니, 내가 직접 했으면 만났을 문제나 느꼈을 무언가를 그냥 지나쳤을 수 있다. 그게 뭔지는 나도 모른다. 후회는 아니지만, 직접 해보지 않아서 못 느낀 게 있을 거라는 짐작은 남는다. 표준이 명확할 땐 따르면 된다고 생각하면서도, 그 짐작이 이번 사이클에서 가장 솔직하게 남는 한 가지인 것 같다.
