### 서론 — 혼자 마주한 두 번째 사이클

사이클1을 마무리하고 곧바로 사이클2가 시작됐다. 이번은 페어 없이 혼자 제출하는 첫 PR이었다.

미션 요구사항은 크게 세 가지였다.

1. 궁성 이동 규칙
1. 왕이 잡혔을 때의 게임 종료
1. 지금까지 메모리에만 있던 상태를 DB로 옮기는 영속화

각각 다뤄야 할 내용이 적지 않은데, 이걸 한 사이클 안에 담아야 했다.

솔직히 말하면, 이번 미션을 처음 시작할 때 나는 구조를 먼저 고민하지 않았다. 어떤 패턴을 적용할까 같은 질문보다 일단 요구사항을 맞추는 데 집중했다.

가장 먼저 작업한 건 궁성이었다.

### PR 제출 전 — 설계한 적 없는 OCP

궁성 이동 규칙을 처음 봤을 때 고민이 시작됐다. 기존 기물의 이동은 시작 좌표와 끝 좌표의 차이(delta)로 검증하고 있었는데, 궁성 내부에서는 같은 (1, 1) 차이라도 어떤 위치에서는 허용되고 어떤 위치에서는 불가능했다. 기존의 delta 기반 검증이 통하지 않았다.

사실 연결 리스트 아이디어 자체는 처음이 아니었다. 사이클1 초창기에 보드판 구조를 짤 때도 같은 방향을 한참 고민했었다. 궁성 내 이동은 각 좌표에서 갈 수 있는 좌표 목록이 정해져 있으니 그래프로 표현하면 자연스러울 것 같았다. 하지만 차나 포처럼 수직·수평으로 쭉 뻗는 기물은 각 간선에 방향 정보까지 붙여야 했고, 기존 로직 전체를 그래프 기반으로 다시 짜야 했다. 고려할 범위가 너무 넓어져서 그때는 결국 delta 방식으로 돌아갔다.

이번엔 보드판 전체가 아니라 궁성 영역만 그래프처럼 표현해보기로 했다. 각 좌표에서 갈 수 있는 좌표 목록을 일일이 세팅하는 게 하드코딩에 가까워지긴 했지만, 일단 구현 자체는 확실히 돌아갈 것 같았다. 그렇게 궁성 내 이동을 하나씩 그려보다 보니 움직임이 크게 세 가지 종류로 묶였고, 이 세 가지를 상황에 맞게 갈아끼우면 궁성 이동 규칙은 다 표현되겠다는 생각이 들었다.

다만 연결 리스트 형태를 기물 안에 그대로 두면 기존 delta 검증 흐름과 섞여 더러워질 것 같았다. 그래서 궁성 이동 규칙 전체를 `PalaceMovement`라는 별도 인터페이스로 빼내 행위(`isPalace`, `validateRule`)만 정의하고, 좌표별로 갈 수 있는 좌표 목록을 담은 `Map>`은 각 구현체가 자기 책임 범위에 맞게 직접 들고 있도록 했다.

```
public interface PalaceMovement {
 boolean isPalace(Coordination from, Coordination to);
 void validateRule(Coordination from, Coordination to);
}
```

구현체는 세 가지(`DiagonalPalaceMovement`, `FullPalaceMovement`, `ForwardPalaceMovement`)로 정리됐고, 기물 생성 시점에 해당 기물이 쓸 구현체를 주입받았다. 사용은 이런 모양이 됐다.

```
@Override
public void validateRule(Coordination from, Coordination to) {
 if (palaceMovement.isPalace(from, to)) {
 palaceMovement.validateRule(from, to);
 return;
 }
 validateNormalRule(from, to);
}

protected abstract void validateNormalRule(Coordination from, Coordination to);
```

두 좌표가 궁성 영역 안이면 주입받은 `palaceMovement`에게 규칙 검증을 위임하고, 그렇지 않으면 각 기물이 자기만의 `validateNormalRule`로 기존 delta 규칙대로 처리하는 구조였다.

다만 이 분기가 추상 부모 한 곳에 모인 모양은 PR 제출 당시의 모습은 아니었다. 같은 분기가 각 기물 구현체에 중복되어 있었고, 리뷰를 거치며 한 곳으로 정리된 최종 형태인데, 이 정리 과정은 뒤에서 다시 이야기한다.

결과적으로 궁성이라는 새 규칙을 추가하면서 기존 기물 클래스의 이동 규칙은 거의 건드리지 않을 수 있었다. 나중에 새로운 궁성 이동 유형이 필요해도 구현체만 하나 더 만들면 됐다.

처음부터 OCP를 의식하고 짠 건 아니었다. 요구사항의 부피가 커서 우선 돌아가는 구현을 만들고 싶었을 뿐이고, 기존 코드를 덜 건드리는 길을 따라가다 보니 이 구조가 남았다. 구현을 다 끝내고 돌아보니 책에서 읽었던 OCP가 실제로 되는 게 신기했다.

### 첫 번째 리뷰 — DB라는 낯선 땅

RC 알림이 왔을 때 처음 느낀 건 당혹이었다. 내 코드에 대한 피드백이 올 줄 알았는데, 막상 받은 건 외적인 질문이 더 많았다. "이걸 왜 선택하셨어요?" 류의 질문이 신선하기도 했는데, 솔직히 말하면 **그냥 사용했는데 왜 사용했냐고 물어본 셈**이었다.

리뷰 대부분이 DB 쪽에 몰려 있었는데, 거의 전부 내가 생각한 것들 밖에 내용들이었다.

### 비슷한 줄 알았는데 달랐던 SQLite

> "왜 SQLite를 선택하셨어요?"

크게 생각하고 고른 게 아니었다. 별도 서버 설정 없이 `.db` 파일 하나로 돌아간다는 편의성만 보고 골랐고, 기존에 쓰던 MySQL이나 H2와 비슷하겠지 정도로 넘겨 짚었다. 이 질문을 받고 나서야 "내가 이걸 전혀 모르는 채로 쓰고 있었구나" 싶었고, 공식 문서부터 뒤지기 시작했다.

MySQL 같은 서버 기반 DB와의 가장 큰 차이는 DB 서버 프로세스의 유무였다. MySQL은 애플리케이션과 별개로 실행되는 DB 서버와 통신해서 연결되는 반면, SQLite는 서버 프로세스 자체가 존재하지 않는다. JNI를 통해 C로 작성된 SQLite 라이브러리가 내 애플리케이션 프로세스 안에서 직접 `.db` 파일을 읽고 쓰는 구조였다.

메서드 실행 흐름도 예상과 달랐다. `prepareStatement()`를 호출하면 JNI 경계를 넘어 SQLite 내부로 진입해서, Tokenizer와 Parser가 SQL 문자열을 분석하고, Code Generator가 이를 바이트코드로 컴파일한 뒤 `sqlite3_stmt` 객체에 담아둔다. 이어 `executeUpdate()`가 호출되면 SQLite 내부의 Virtual Machine이 그 바이트코드를 실행하고, B-Tree와 Pager를 거쳐 최종적으로 디스크의 `.db` 파일에 기록한다.

깊이까지 파고들진 않았다. 비교하면서 아키텍처를 훑어본 정도인데, 그것만으로도 DB가 파일로 나온다는 사실이 새삼 다르게 읽혔다. 파일 시스템, IO, 락 같은 주제가 자연스럽게 떠올랐고, 막연히 알던 것이 조금 구체적인 모습으로 다가왔다.

### DriverManager는 무슨 일을 하나요?

> "DriverManager의 역할은 무엇인가요?"

이 객체가 정확히 뭘 하는지 설명할 수가 없었다. `DriverManager.getConnection(...)`을 관례처럼 썼을 뿐 이 뒤에서 무슨 일이 벌어지는지 한 번도 들여다본 적이 없었다. 이것도 공부해야겠다 싶었다.

`DriverManager`는 Java 애플리케이션이 DB와 연결될 때 중간에서 알맞은 드라이버를 찾아 Connection 객체를 만들어주는 팩토리였다. 덕분에 개발자는 구체 DB의 내부 동작을 신경 쓰지 않고 쿼리를 날리는 일에만 집중할 수 있다.

드라이버를 로드하는 방식이 특히 인상적이었다. JVM의 `jdbc.drivers` 프로퍼티를 먼저 확인하고, 추가로 Java의 SPI(Service Provider Interface) 메커니즘을 통해 클래스패스 안의 `META-INF/services/java.sql.Driver` 파일을 자동 탐색한다. 거기 적힌 드라이버 클래스가 로드되면서 자기 자신을 `DriverManager`에 등록하는 구조였다. 그래서 내 코드에 `org.sqlite.JDBC` 같은 구체 클래스가 한 줄도 나오지 않아도 런타임에 SQLite 드라이버가 알아서 붙어 동작했던 것이다. Gradle에서 JDBC 드라이버를 `implementation`이 아니라 `runtimeOnly`로 선언하는 관행도 이 구조와 맞물려 있었다.

권장 방식이 `DriverManager`가 아니라 `DataSource`라는 것도 이때 알게 됐다. `DriverManager`는 호출할 때마다 새 커넥션을 만들고, `DataSource`는 커넥션 풀에서 꺼내 재사용한다. 다만 SQLite는 파일 단위 잠금 때문에 동시 쓰기가 어차피 한 번에 하나라, 이번 미션 범위에선 `DriverManager`를 그대로 뒀다.

코드 자체는 크게 바꾼 게 없었다. 대신 "내가 지금 JDBC의 어떤 부분을 다루고 있는지" 알게 되었다.

### TEXT와 VARCHAR는 같은가 다른가 (Type Affinity)

> "컬럼 타입을 왜 전부 TEXT로 하셨어요?"

"어차피 문자열이니까"라고 생각했다. 문자열 길이를 특별히 제한할 이유도 없어 보였고, 그래서 기본처럼 느껴지는 `TEXT`를 그냥 박아뒀다.

찾아보니 SQLite에는 Type Affinity라는 개념이 있어서 `VARCHAR(50)`이라고 쓰든 `TEXT`라고 쓰든 내부적으로는 같은 TEXT affinity로 취급됐다. 여기까지만 알고 있었다면 "거봐 같잖아"로 끝났을 텐데, 실제 `.db` 파일에는 어떻게 기록되는지가 궁금해져서 조금 더 팠다.

SQLite는 `.db` 파일 전체를 고정 크기 페이지(기본 4KB) 단위로 나누어 관리하고, 각 테이블마다 별도의 B-Tree가 있다. 실제 행 데이터는 리프 페이지에 저장되는데, 각 행의 앞에는 헤더가 붙어서 컬럼마다 데이터 타입과 실제 바이트 길이(Serial Type) 정보를 기록한다. 결국 선언된 길이와 무관하게 실제 데이터 바이트만큼만 저장되는 구조였다.

SQLite 안에서만 보면 여기서 끝이지만, 다른 DB로 옮기면 얘기가 달라졌다. MySQL에서는 `VARCHAR`와 `TEXT`가 엄격하게 구분되고, 실제 공간 할당과 인덱싱 방식이 달라진다. 객체지향 애플리케이션이라면 설정 하나로 DB를 교체할 수 있어야 하는데, 전부 `TEXT`로 박아두면 나중에 MySQL로 옮겼을 때 의도치 않은 문제가 생길 수 있었다.

그래서 호환성과 도메인 의도 양쪽을 살리는 방향으로, 모든 컬럼을 `VARCHAR(?)`로 명시해서 고쳤다. SQLite 안에서는 어차피 TEXT로 처리되니 현재 동작엔 영향이 없지만, 선언문 자체에 "이 값은 이 정도 길이의 문자열이다"라는 의도가 드러나는 모양이 됐다.

### Statement와 PreparedStatement는 뭐가 달랐나

> "PreparedStatement는 왜 선택하신 거예요?"

당황스러운 질문이었다. 미션 사전 학습 키워드에 `PreparedStatement`가 적혀 있어서 그냥 쓴 게 다였고, `Statement`라는 게 따로 존재하는지조차 몰랐다.

둘은 꽤 달랐다. `PreparedStatement`는 값이 들어갈 자리를 기호(`?`)로 비워둔 채 SQL 구조를 미리 컴파일해서 캐싱하는 방식이다. 같은 쿼리를 루프로 반복 실행할 때 컴파일 과정을 건너뛸 수 있어 성능상 이점이 있는데, 이 캐싱은 해당 객체가 열려 있는 동안만 유효하다. 내 코드처럼 메서드마다 쿼리를 실행하고 바로 닫는 구조에서는 이 이점을 누리기 어려웠다.

오히려 본질은 안전성 쪽에 있었다. `Statement`는 쿼리문과 파라미터 값을 문자열로 이어 붙여서 DB에 전달한다. 이 경우 파라미터에 따옴표나 특수 문자가 섞이면 DB가 어디까지가 문법이고 어디부터가 값인지 헷갈릴 수 있다. 반면 `PreparedStatement`는 쿼리 뼈대를 먼저 확정해두고 빈칸에 값을 따로 전달하기 때문에, 들어가는 파라미터는 DB 입장에서 추가 파싱 없이 무조건 단순한 데이터로만 취급된다.

이 차이가 단순한 "따옴표 이스케이프 편의성" 정도가 아니라 SQL 인젝션과 직접 연결된다는 것을 여기서 연결 지어 이해하게 됐다. 공격자가 입력창에 `' OR '1'='1` 같은 구문을 끼워 넣어도, `PreparedStatement`는 쿼리 뼈대가 이미 확정된 상태이므로 이 입력이 조건문으로 해석되지 않고 그대로 값 하나로만 들어간다.

기존에 `PreparedStatement`를 쓰던 부분은 유지했고, 파라미터가 없는 DDL 쿼리(`CREATE` 등)는 굳이 `PreparedStatement`를 쓸 이유가 없어서 `Statement`로 바꿨다. "둘 중 무엇을 쓸지 판단하는 기준"이 처음으로 생긴 셈이었다.

DB에 대한 리뷰는 전부 "이걸 왜 이렇게 쓰셨어요?"로 모였고, 내 답은 대부분 "…그냥 썼는데요"에 가까웠다. 선택을 했다고 생각했는데 사실은 선택한 적이 없었다. 이 피드백에서 건진 건 특정 지식 하나가 아니라, 내가 쓰던 도구에 대해 내가 얼마나 몰랐는지 그리고 그걸 모르는지조차 몰랐는지를 알 수 있는 시간이였다는 것이었다.

### 두 번째 리뷰 — 여기저기 흩어진 당혹

두 번째 리뷰는 숫자로 보면 가장 많았고, 대신 각각이 작고 흩어져 있었다. 이전의 피드백과 거의 동일 했는데 공통점은 하나였다. "왜 이렇게 하셨어요?" 내 답변도 거의 비슷하게 반복됐다. "…그냥 그렇게 썼던 것 같습니다."

### protected로 열어둔 이유가 있을까

> "자바에는 어떤 접근제어자의 종류들이 있고 어떤 성격이 있을까요?"

큰 생각 없이 상위 클래스의 필드·상수를 `protected`로 열어두고 있었다. "상속 구조니까 하위에서 쓸 수도 있겠지" 정도의 막연한 감각이었지, 각 필드가 실제로 하위에서 쓰이는지는 확인해본 적이 없었다.

질문을 받고 나서야 접근제어자의 4단계(`private` → `default` → `protected` → `public`)를 다시 정리해봤다. 객체지향 설계에서는 내부 구현을 숨기고 외부와의 결합도를 낮추기 위해 가능한 한 접근 범위를 **최소화하는 것이 원칙**이라는 건 알고 있었는데, 막상 내 코드에 이 기준을 적용해본 적이 없었던 것이다.

대표적인 예가 `palaceMovement` 필드였다. 세 개의 중간 추상 클래스가 모두 이 필드를 `protected`로 들고 있었다.

```
public abstract class DiagonalPalaceMovementPiece extends Piece {
 protected final PalaceMovement palaceMovement;
 // ...
}
```

"하위 클래스(Cannon, Chariot, Soldier 등)가 이걸 직접 접근할 필요가 있나?"라는 질문으로 하나씩 열어봤는데, 신기하게도 하위 기물들은 부모의 `validateRule` 흐름 안에서 **간접적으로만** 사용할 뿐 `palaceMovement`를 직접 참조하는 곳이 **단 한 군데도 없었다**. 그냥 열려 있었을 뿐이었다.

세 추상 클래스 모두 `private`으로 닫아 부모의 내부 구현을 안전하게 숨겼다.

```
public abstract class DiagonalPalaceMovementPiece extends Piece {
 private final PalaceMovement palaceMovement;
 // ...
}
```

다만 점검해보니 무조건 닫는 것이 정답은 아니었다. 예를 들어 `Piece`의 `Team team` 필드는 `Soldier`가 팀에 따라 이동 방향을 결정할 때 직접 참조해야 하므로 `protected`로 열어두는 것이 맞았다. 하위 클래스에서 오버라이드하여 구현해야 하는 `validateNormalRule` 같은 추상 메서드도 마찬가지였는데, 자바 문법상 오버라이딩 시 접근 범위를 좁힐 수 없기 때문에 `protected`를 유지하는 것이 타당했다.

```
public abstract class Piece {
 protected final Team team;
 // ...
 protected abstract void validateNormalRule(Coordination from, Coordination to);
}
```

"무조건 닫기"가 아니라 **"이 자리가 왜 이 범위여야 하는지"를 설명할 수 있는 상태**로 정리하고 나니, 같은 `protected` 키워드를 봐도 의미가 달라졌다.

### 리소스는 누가 닫는가

> "statement.close();를 호출하지 않으면 어떻게 되나요?"

얼핏 보면 단순한 질문인데, 답하려고 보니 내가 `close()`에 대해 아무것도 고민하지 않고 쿼리만 쓰고 있었다는 게 드러났다. 내 코드를 전수 검사해보니 `BoardJdbcRepository`와 `GameJdbcRepository`의 **모든 메서드에서** `Statement`, `PreparedStatement`, `ResultSet`에 대한 `close()` 처리가 완전히 누락되어 있었다.

찾아보니 이 객체들은 DB 커넥션 위에서 동작하며 내부적으로 OS 레벨 리소스(메모리, 네트워크 소켓 등)를 점유한다. `close()`를 명시적으로 호출하지 않으면 두 가지 문제가 생길 수 있었다.

1. 리소스 누수: 사용이 끝난 객체들이 GC에 의해 즉각 회수되지 않고 메모리에 쌓인다.
1. 커넥션/커서 고갈: DB 쪽에서도 해당 세션의 리소스를 계속 열어둬서, 새로운 요청을 처리하지 못하고 결국 애플리케이션 장애로 이어질 수 있다.

해결 자체는 `finally` 블록에서 일일이 닫아주는 방법도 있었지만, 코드가 길어지고 실수가 끼어들 여지가 컸다. 자바 7부터 지원하는 `try-with-resources`가 더 안전한 길이었다. `Statement`, `PreparedStatement`, `ResultSet` 모두 `AutoCloseable`을 구현하고 있어서, `try (...)` 블록 안에 선언해두기만 하면 정상 종료든 예외 발생이든 JVM이 블록을 빠져나갈 때 알아서 `close()`를 호출해준다.

```
try (PreparedStatement stmt = connection.prepareStatement("...");
 ResultSet rs = stmt.executeQuery()) {
 // ... 로직 수행 ...
} // 블록 종료 시 stmt와 rs 모두 자동으로 안전하게 close() 됨
```

두 Repository의 모든 메서드는 이 구조로 바꿨다. 다만 트랜잭션 롤백이 필요한 `FacadeService`의 `save`·`update`·`gameEnd` 쪽은 건드리지 않고 기존 흐름을 그대로 뒀다.

```
Connection connection = null;
try {
 connection = connectionProvider.getConnection();
 connection.setAutoCommit(false);
 // ... 여러 서비스 조합 ...
 connection.commit();
} catch (SQLException e) {
 rollback(connection);
 throw new RuntimeException(e);
} finally {
 close(connection);
}
```

Repository는 "쿼리 한 번 돌리고 블록을 빠져나간다"가 전부라 `try-with-resources` 한 줄로 깨끗하게 닫혔지만, Service 레이어는 중간에 **성공이면 `commit`, 실패면 `rollback`** 이라는 분기가 있어서 `catch` 블록이 반드시 필요했다. 그러다 보니 자연스럽게 "`catch`가 있는 전통적 `try-catch-finally` 구조를 유지하고 `finally`에서 `close`를 명시적으로 호출한다"는 모양으로 남겨뒀다. 거기에 대한 내 설명도 딱 그 수준이었다. "롤백이 필요해서 기존 구조를 유지했습니다."

여기에 돌아온 후속 질문이 이거였다.

> "롤백이 있더라도 try-with-resource를 사용해도 될 것 같은데요🤔 명시적으로 close()를 호출한 이유가 있을까요?"

처음엔 의아했다. 롤백 분기가 있으면 `try-with-resources`를 못 쓰는 줄 알았기 때문이다. 찾아보니 `try-with-resources`는 `catch`·`finally`와 **같이 붙여서 쓸 수 있는** 문법이었다. `try (Connection connection = ...)` 로 자원을 선언해두면 `catch`에서 여전히 `rollback`을 호출할 수 있고, 블록을 빠져나갈 때 `close()`는 JVM이 알아서 해준다. 즉 지금 내 코드의 `finally { close(connection); }`는 **없어도 되는 줄**이었던 셈이다.

머리로는 "그러네" 싶은데, 막상 지금 내 `save` 메서드를 그 모양으로 바꿔보려니 `setAutoCommit(false)` 호출 자리, `rollback` 시 상태, `commit` 이후 흐름이 머릿속에서 잘 정돈되지 않았다. PR 반영 마감도 가까웠고, 이 부분만 한 번 더 찬찬히 정리하고 싶어서 당장의 PR 범위에서는 바꾸지 못했다. 그대로 숙제로 남겨뒀다.

남은 숙제가 생겼다는 것과는 별개로, 이 라운드에서 건진 건 "리소스가 **누구 손에서 어떻게 닫히는지**"가 처음으로 내 관심 안에 들어왔다는 것이었다. 쿼리 한 줄을 짜면서 `close()`까지 같이 떠올리는 감각은 이전엔 아예 없었다.

### 서비스가 SQLite를 알아야 할까

이건 리뷰어가 콕 집어 지적한 건 아니고, `FacadeService`를 다 구현해놓고 한 번 더 돌아보다가 내 쪽에서 먼저 걸린 지점이었다.

게임 저장 흐름을 묶기 위해 `FacadeService`를 도입했었다. 이유는 두 가지였다.

1. `game 저장 → 반환된 gameId로 board 저장`처럼 여러 서비스를 특정 순서로 조합하는 흐름 제어가 필요했다.
1. `Game`과 `Board` 저장은 무조건 한 번에 같이 처리돼야 하는 작업이라, 트랜잭션 경계를 여기서 잡고 싶었다.

그런데 막상 구현하고 나서 다시 읽어보니 이 서비스가 `SQLiteConnectionProvider`를 **직접 생성**하거나 특정 DB의 커넥션 정보를 내부에서 알고 있는 모양이었다. "게임 저장·불러오기라는 비즈니스 로직을 담당하는 서비스 계층이, SQLite라는 인프라의 세부 구현을 직접 아는 것이 맞을까?" 싶었다.

예를 들어 테스트 환경에서 in-memory DB로 교체하거나 향후 다른 저장소로 옮기고 싶을 때, 서비스 코드 자체를 수정해야 하는 상황이 그려졌다. 서비스는 "커넥션이 필요하다"는 사실만 알면 되지, "그 커넥션이 SQLite에서 오는지 MySQL에서 오는지"까지 알 필요가 없었다.

커넥션 생성 책임을 서비스 바깥으로 완전히 분리하기 위해 `ConnectionProvider` 인터페이스를 도입했다.

```
public interface ConnectionProvider {
 Connection getConnection() throws SQLException;
}

public class SQLiteConnectionProvider implements ConnectionProvider {
 private static final String JDBC_URL = "jdbc:sqlite:janggi.db";

 @Override
 public Connection getConnection() throws SQLException {
 return DriverManager.getConnection(JDBC_URL);
 }
}

public class FacadeService {
 private final ConnectionProvider connectionProvider;
 // ...
}
```

트랜잭션 경계도 이 구조 위에서 자연스럽게 잡혔다. 테이블을 (행·열·기물·진영)과 (게임 종료 여부·턴) 둘로 나눠둔 상태라, 두 테이블 작업을 하나의 단위로 묶을 서비스가 필요했고 그게 파사드 자리였다.

```
public void save(List pieceSnapshots, String turn) {
 Connection connection = null;
 try {
 connection = connectionProvider.getConnection();
 connection.setAutoCommit(false);
 int gameId = gameService.save(connection, turn);
 janggiService.save(connection, gameId, pieceSnapshots);
 connection.commit();
 } catch (SQLException e) {
 rollback(connection);
 throw new RuntimeException(e);
 } finally {
 close(connection);
 }
}
```

이렇게 바꾸고 나니 `FacadeService`는 "커넥션이 필요하다"만 알고, 그 커넥션이 어디서 어떻게 만들어지는지는 몰라도 됐다. SQLite를 MySQL로 바꾸든 in-memory로 바꾸든, `ConnectionProvider`를 구현한 새 클래스를 하나 만들어 주입하면 `FacadeService` 코드는 한 줄도 수정할 필요가 없었다. 이 구조가 DIP가 말하는 바로 그 방향이라는 걸 이때 조금 더 체감했다.

한편 최근에는 JPA만 사용했던 터라, 인터페이스와 JDBC 구현체를 분리해서 나중에 JPA로 갈아끼울 수 있는 구조까지만 세팅했다. 다른 크루들이 DAO 얘기를 꺼낼 때는 솔직히 조금 신기했다. DAO는 적용하지 않았고, 리뷰어도 이 부분은 건드리지 않았다. 이건 그대로 부채로 남았다.

두 번째 리뷰에서 주신  피드백들은 하나하나 놓고 보면 다 작은 것들이었다. 그런데 작은 것들이 계속 쌓이니까 어느 순간부터는 나의 부족함이 보였던 것 같다.

### 세 번째 리뷰 — 부모가 로직을 가져도 될까, 그리고 돌아온 부메랑

마지막 리뷰 라운드에는 내가 오래 묵혀뒀던 두 가지가 한꺼번에 올라왔다. 하나는 궁성을 만들면서 자연스럽게 생긴 상속 구조에 대한 찜찜함이었고, 다른 하나는 사이클1부터 부채로 들고 있던 공개 상수 문제였다. 둘 다 내 실력으로는 당장 답이 떠오르지 않아서 한동안 막막했는데, 기론의 질문 하나하나가 내가 갇혀 있던 흑백논리를 깨주는 시간이 됐다.

### 부모가 로직을 가져도 될까

> "각 기물마다 반복되는 로직 같은데요. 중복을 제거해볼까요?"

궁성 이동을 추상화하고 나니 자연스럽게 중복 문제가 보이기 시작했다. 궁성 내 이동을 확인하는 `validateRule` 흐름과 `resolvePath` 로직이 `Cannon`, `Chariot` 같은 여러 기물에서 거의 똑같이 반복되고 있었다. 기론이 이 중복을 짚어줬고, 각 구현체에 흩어져 있던 공통 흐름을 상위 추상 클래스 `DiagonalPalaceMovementPiece`와 `ForwardMovementPiece`로 끌어올렸다. 하위 기물들은 자신만의 고유한 일반 이동 규칙인 `validateNormalRule`만 신경 쓰면 되는 구조가 됐다.

```
public abstract class DiagonalPalaceMovementPiece extends Piece {

 @Override
 public void validateRule(Coordination from, Coordination to) {
 if (palaceMovement.isPalace(from, to)) {
 palaceMovement.validateRule(from, to);
 return;
 }
 validateNormalRule(from, to);
 }

 protected abstract void validateNormalRule(Coordination from, Coordination to);
}
```

그런데 중복을 없앴다는 후련함과 동시에 설계적인 찜찜함이 따라붙었다. 그동안 학습하면서 **"상속보다는 조합을 사용하라"**, **"상위 클래스의 변경이 하위 클래스를 깨뜨릴 수 있다"** 같은 상속의 단점을 많이 읽어왔기 때문에, 추상 클래스가 **구체적인 구현 로직을 직접 가지는 모양**이 혹시 OCP 위반이 아닐까 하는 걱정이 들었다.

더 신경 쓰였던 건 구현 위치의 일관성 문제였다. `DiagonalPalaceMovementPiece`에서는 일반 이동 규칙을 **상위 클래스에서 `private`으로 직접 구현**한 반면, `ForwardMovementPiece`에서는 **하위 클래스에 `abstract`로 위임**하고 있었다. 같은 결의 상위 추상 클래스인데 구현 위치가 다른 게, 뭔가 원칙에 어긋나는 것이 아닌가 하는 불안감이 떨어지지 않았다.

기론은 여기서 바로 답을 주는 대신 질문을 던졌다.

> "티뉴가 생각하시기에 상속 구조에서는 부모가 로직을 가지면 안 된다고 생각하실까요? 인터페이스로 구현한 것과 상속한 것은 어떤 차이가 있나요?"

이 질문을 받고 나서야 내가 **흑백논리**에 빠져 있었다는 걸 알게 됐다. '상위 클래스가 구체적인 구현 로직을 가지면 무조건 설계적 결함'이라는 식으로 밀어붙이고 있었던 것이다.

기론의 또 다른 조언인 **"변하는 것과 변하지 않는 것을 분리한다"**는 기준으로 내 코드를 다시 분석해보니, 표면적인 위치만 다를 뿐 사실은 일관된 원칙이 적용되어 있었다. `DiagonalPalaceMovementPiece`의 일반 이동 규칙(수평/수직만 허용)은 하위 기물 간에 동일하므로 상위에서 `private`으로 고정한 것이 맞았고, `ForwardMovementPiece`의 일반 이동 규칙은 기물마다 달라질 수 있으므로 하위로 위임한 것이 맞았다. **변하지 않는 것은 상위에 고정하고, 변하는 것은 하위에 위임한다.** 나는 이 원칙을 무의식적으로 따르고 있었으면서도, 상속의 단점만 의식한 나머지 스스로를 의심하고 있었던 것이다.

가장 걱정했던 "부모 클래스가 로직을 가지면 하위 클래스와 결합도가 높아져 깨지기 쉽다"는 문제도, `private`으로 닫아두면 하위 클래스가 무분별하게 오버라이드하거나 의존할 수 없으므로 구조적으로 오히려 안전했다.

이 과정에서 내가 정리하게 된 인터페이스와 상속의 본질적인 차이는 이것이었다.

- 인터페이스 — "무엇을 할 수 있는가(Can-do)": 행위의 규약(계약)을 정의하는 데 초점. 구체적인 상태나 구현 로직을 가질 수 없으며, 외부 협력을 위한 API 명세서 역할.
- 상속 / 추상 클래스 — "무엇인가(Is-a) & 공통 로직의 상속": 하위 객체들이 근본적으로 같은 종류임을 묶어주면서, 공유하는 상태와 핵심 로직을 물려주기 위해 존재.

이 기준을 내 코드에 적용해보니, 궁성 내 이동 로직은 단순히 덧붙여지는 부가 기능이 아니라 **여러 기물이 구조적으로 공유해야 하는 '본질적인 특징'**이었다. 따라서 인터페이스보다는 추상 클래스에 구체적인 로직을 두는 것이 올바른 방향이었다. 공통된 전체 흐름(궁성 이동 검증)은 상위 클래스에서 뼈대를 잡아두고, 기물마다 달라지는 구체적인 일반 이동 규칙만 하위 클래스에 위임하는 지금의 방식이 **템플릿 메서드 패턴(Template Method Pattern)**의 전형적인 모습이라는 것도 이때 알게 됐다.

단순히 중복을 제거했다고 생각했는데, 기론의 질문 하나가 상속에 대한 흑백논리를 부수고 나만의 기준을 세우게 해준 셈이었다.

### 공개 상수는 정말 어쩔 수 없었을까

> "ErrorMessage 상수들의 접근 제어자가 public으로 열려 있는 특별한 이유가 있을까요? 테스트 검증의 편의성 때문에 프로덕션 코드의 캡슐화가 깨지는, 이른바 주객이 전도된 상황은 아닐지 고민해 보면 좋겠습니다."

이건 사이클1부터 내가 **"어쩔 수 없다"**는 입장을 꽤 오래 끌고 온 부분이었다. 초기엔 `ErrorMessage`라는 전역 클래스에 예외 메시지를 모아뒀다가, "예외가 발생하는 도메인 내부에 메시지가 함께 있는 게 가독성·응집도 면에서 낫다"는 판단으로 각 도메인 내부 상수로 옮겼다. 문제는 그 과정에서 테스트 코드가 `assertThatThrownBy(...).hasMessage(Piece.ERROR_MESSAGE)` 형태로 검증하고 있었다는 점이었다. `private`으로 닫으면 테스트에서 참조할 수 없으니 별 고민 없이 `public`으로 열어뒀다.

사이클2에서도 같은 지적이 반복됐다. 나는 개인적으로 **"테스트는 의도한 대로 동작하는지 검증해야 한다"**는 가치관을 갖고 있었다. 예외 상황에 맞는 메시지를 통해 사용자가 **왜 이 움직임이 불가능한지**를 알 수 있어야 한다고 생각했고, 이를 테스트에서 분명히 검증하는 것이 응집도를 높이는 길이라고 믿었다. 그래서 "private으로 닫으면 테스트가 큰 예외 타입 정도만 체크하게 되고 **의미가 퇴색**된다"는 입장을 고수했다.

다만 리뷰어가 계속 같은 자리를 건드린다는 건 내가 놓치고 있는 게 있다는 신호였다. 거의 마지막 라운드 쯤이 되어서야 슬랙 DM으로 내 고민의 맥락을 길게 풀어서 보냈고, 기론에게서 돌아온 답이 지평을 키워줬다

> "모든 메시지를 검증하면 더 안정적인 테스트가 될 수는 있어요. 다만 현실적으로는 시간과 자원이 한정되어 있기 때문에, 모든 케이스를 그렇게까지 촘촘하게 검증하기는 어렵죠. 특히 에러 메시지는 언제든 변경될 수 있기 때문에, 메시지를 기준으로 테스트를 작성하면 그때마다 테스트 코드도 함께 수정해야 하는 부담이 생깁니다. 이런 맥락에서 보면, 메시지를 기준으로 검증하는 방식과 각 상황에 맞는 커스텀 Exception 클래스를 만들어 비교하는 방식, 이 둘 사이에는 어떤 차이가 있을지 고민해볼 수 있을 것 같아요."

그동안 내 머릿속엔 "메시지 검증 vs 큰 예외 하나로 뭉뚱그리기" 두 선택지뿐이었는데, 기론은 그 사이에 **"실패 원인별로 예외 클래스를 나눈다"**는 제3의 길이 있다는 걸 보여줬다. 이 방향이면 테스트가 더 이상 문자열 메시지에 의존하지 않아도 되고, 프로덕션 코드의 상수를 억지로 열어둘 필요도 없었다.

문제는 내가 이걸 어떻게 **내 코드 구조 위에서** 구체화할 수 있느냐였다. 엣지 케이스마다 예외 클래스를 만들면 클래스가 무한정 늘어날 것 같았다. 게다가 내 코드는 기본 기물을 상속받고 궁성 이동 규칙은 합성으로 풀고 있어서, 예외 발생 지점이 여러 위치에 흩어져 있었다. 단위를 어떻게 나눠야 할지가 금방 보이지 않았다.

힌트는 전혀 다른 자리에서 왔다. `Board.move`의 구조를 다시 보던 중이었다.

```
public void move(Coordination from, Coordination to) {
 Piece piece = board.get(from);
 validateRule(from, to, piece); // 기물의 이동 규칙
 validatePiecesOnPath(from, to, piece); // 경로 위 다른 기물 체크
 validateTarget(to, piece); // 도착지 검증
 resolve(from, to, piece);
}
```

이 구조를 보고 있는데, 검증이 **실패 원인별로 이미 단계적으로 나뉘어 있다는 것**이 눈에 들어왔다. 각 단계는 서로 다른 종류의 실패를 막고 있었다. `validatePiecesOnPath`에서 막히는 것은 "경로가 막혔다"는 의미고, `validateRule`에서 막히는 것은 "이 기물이 이런 식으로는 못 움직인다"는 의미였다. **실패의 종류가 이미 코드 구조에 새겨져 있었던 것이다.**

그 단위를 그대로 예외 계층으로 올리면 될 것 같았다. 기물이나 세부 케이스가 아닌, **"실패 원인(동작 카테고리)"**을 기준으로 예외를 추상화하는 방향으로 기준을 세웠다.

```
- 경로 막힘 (장애물, 포가 포를 넘으려 할 때 등)
 → PathBlockedException
- 기물 고유 규칙 위반 (졸이 뒤로 갈 때 등)
 → PieceRuleViolationException
```

이렇게 묶으니 예외 클래스가 무한정 늘어나는 문제를 막으면서도, 테스트가 문자열이 아닌 **예외 타입**만으로 "이 상황에선 이 종류의 실패가 나와야 한다"는 걸 명확히 검증할 수 있었다. 프로덕션 코드의 메시지 상수는 더 이상 테스트를 위해 열어둘 필요가 없어졌다. 에러 메시지가 바뀌어도 테스트는 흔들리지 않게 됐다.

다만 이 해법을 만들어준 `Board.move`의 단계 구조 자체에는 문제를 발견 했다. 보드가 "기물의 행위 단계"를 잘게 쪼개서 직접 호출하는 모양이기 때문에, 엄밀히 말하면 **기물의 행위를 보드가 너무 잘 아는 상태**다. 이게 캡슐화를 부분적으로 깨뜨리는 구조라는 것은 적용하면서도 계속 신경 쓰였다. 지금의 내 실력으로는 마땅한 대안이 떠오르지 않았고, 기물이 보드를 알아야 하는 상황이 되는 것보다는 보드와 기물 사이의 **핑퐁이 낫다**고 판단해 타협했다. 그래도 이건 캡슐화를 일부 양보한 것이 맞고, 그대로 부채로 남겼다.

그래서 이 라운드의 마무리는 묘하게 양면이었다. 사이클1부터 "어쩔 수 없다"로 밀어뒀던 공개 상수 문제가 처음으로 **닫혔고**, 동시에 그걸 닫게 해준 구조 자체가 새로운 부채를 **열었다**. 기론이 내 흑백논리를 부수면서 만들어준 지평이 생각보다 넓었고, 그 안에는 아직 내가 못 읽은 부채가 같이 들어 있었다.

### 비로소 보이는 것 — 그리고 여전히 보이지 않는 것

머지됐을 때 가장 먼저 든 감정은 후련함이었다. 다만 이 후련함은 내가 잘해서 얻은 결과라기보다는 미션과 시간적 제약 안에서 **"배워야 할 부분까지는 다뤘다"**는 느낌에 가까웠다. 이번 라운드에서도 리뷰어가 짚어준 자리들은 대부분 내가 인지조차 못하고 있던 것들이었으니, 아직 내가 인지하지 못한 자리도 그만큼 남아 있을 거라고 생각하는 쪽이 자연스러웠다.

이번 사이클을 관통하는 한 문장을 꼽으라면 이거였던 것 같다. **의도해서 설계한 게 아니라, 리뷰가 "왜 그랬냐"고 묻기 시작했을 때에야 비로소 내가 무엇을 했는지, 그리고 무엇을 모르는지조차 몰랐는지가 보이기 시작했다.** 궁성에서 OCP가 되는 것도 어쩌다 그렇게 된 쪽에 가까웠고, DB 쪽은 말할 것도 없었고, 상속 구조에 대한 기준도 기론의 질문을 받고 나서야 겨우 세워졌다. 하나같이 내가 **먼저 의도해서 만든 게 아니었다.**

객체지향에 대해서 솔직히 말하면 아직도 잘 모르겠다. SRP와 OCP 정도는 이번 사이클을 거치면서 조금 체감했고, DIP는 `ConnectionProvider`를 분리하면서 감을 잡기 시작한 수준이다. ISP와 LSP는 여전히 머리로도 잘 와닿지 않고 코드에서 체감한 자리도 아직 없다. 원칙 이름을 안다는 것과 그게 코드 안에서 어떻게 숨 쉬는지를 안다는 건 꽤 다른 일이라는 생각이 든다.

남은 부채도 선명하다. `DAO`를 끝까지 적용하지 못한 것, `Board.move`의 단계 구조가 캡슐화를 부분적으로 양보하고 있는 것, 그리고 무엇보다 "기능이 추가되거나 수정되는 경험"을 이 미션에서 **궁성 추가 한 번**밖에 겪지 못한 것. 객체지향스러운 설계가 체화되려면 같은 코드 위에서 요구사항이 반복적으로 바뀌고 그 압력 속에서 구조가 드러나야 할 텐데, 이번엔 그 기회가 많지 않았다.

그래서 이번 회고의 착지는 "무엇을 배웠다"보다는 **"무엇을 아직 모르는지 조금 더 알게 됐다"** 쪽이다. 어쩌다 된 구조들을, 이제는 "왜 이랬는지" 스스로 설명하려고 해보는 습관이 조금 생겼을 뿐이고, 설명이 막히는 자리마다 내가 모르는 자리가 있다는 것만 겨우 알게 됐다.

객체지향을 더 공부하고 싶다. 지금으로서는 그게 이 사이클이 남긴 가장 정직한 문장인 것 같다.
