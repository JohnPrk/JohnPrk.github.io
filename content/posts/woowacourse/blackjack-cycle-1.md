## 나는 뭘 짜고 있는 건가?

블랙잭 미션이 시작됐을 때, 나는 사실 기대가 컸다.

이전 우테코 레벨에 들어오기 전부터 객체지향 설계에 관심이 있었고, 이 미션이 그걸 직접 부딪혀 볼 수 있는 기회라는 게 느껴졌다. 미션 요구사항 자체가 예사롭지 않았다.

![](https://blog.kakaocdn.net/dna/XDpO9/dJMcaflEwO5/AAAAAAAAAAAAAAAAAAAAAOaSyGBzvxq8RD17-9ZEdz1xUP_Qe67ZuT9SodLlQEiE/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1777561199&allow_ip=&allow_referer=&signature=hIoEb8apUDlGGWgMlFZ3p6N3ozE%3D)

지금 생각해보면 이것들을 전부 지키면서 블랙잭 게임을 구현하라는 게 미션의 핵심이었던 것 같다.

사실 나는 ADHD 성향이 있어서 이것저것 해야할 일이 많다보면 하나에 집중을 잘못하는 편인데, 여러 이유(연극을 준비하고 난 뒤의 체력 이슈 및 자잘한 활동 등)로 제일 중요한 요구사항을 제대로 읽지 않았던 것 같다.

그리고 바로 팀 토론 활동을 시작했다. 물론 다른 팀원들은 그렇게 느끼지 않았을 수도 있는데, 나는 '왜 토론 활동을 해야하는지' 잘 못 느꼈던 것 같다. 팀이 구성이 되었지만, 사실 처음 보는 크루들이였고 토론 활동을 위한 여러 주제와 미션들이 있었지만, '**굳이**'라는 생각이 많이 들었다.

이후에 바로 페어 프로그래밍을 시작했다. 지금 돌이켜보면 이게 출발점부터 잘못된 거 같다. 페어를 시작하기 전에 도메인을 먼저 이해하고, 어떻게 설계할지 각자 생각을 맞춰보고, 페어 진행 방식에 대한 룰이라도 하나 정했어야 했다. 근데 그런 과정이 없었다. **그냥 시작했다.**

페어와 나는 15분씩 돌아가면서 진행하기로 했다. 한 명이 코드를 짜는 동안 다른 한 명이 옆에서 보는 방식으로 했다. 나는 다른 사람이 어떻게 생각하고 코드를 짜는지 옆에서 보는 걸 원래 좋아했고 배울 것이 분명히 있다고 생각했다. 이번에도 그 기대로 시작했다.

**그런데** 페어가 나와 많이 다를 수 있다는 것을 간과했다. 페어는 요구사항을 AI에게 먼저 학습시키고, AI가 코드를 생성하면 이를 검토하는 방식으로 코드를 작성했다. 하지만 나는 평소에 도메인 설계부터 시작해서 각 객체가 어떤 책임을 가질 것인지, 이름은 어떻게 할 것인지 생각한 다음에 코드를 작성하는 편이였다.

하지만, 페어 프로그래밍을 위해 중간 지점 어디에서 만날지를 협의를 하지 않았다. 원래 페어 프로그래밍을 할 때 상대방의 방식을 따라가는 편이기도 했고, 요구사항도 제대로 안 읽었으니 내가 먼저 설계 방향을 제시할 근거도 부족했다. 도메인을 이해하지 못한 채로 AI가 만들어주는 흐름에 자연스럽게 올라탔다.

코드가 생겼다. 클래스가 생기고, 메서드가 채워지고, 테스트도 붙었다. 속도는 빨랐다.

근데 어느 순간 이런 생각이 들었다. '이게 내가 짜는 코드인가?' '카드 덱이 왜 이 구조인가?' 등등 읽고 이해할 수는 있겠지만, 근데 내가 이 선택을 한 게 아니라는 생각을 들었다.

뭘 짜고 있는지 모르는 채로 코드를 치고 있었던 것 같다.

## 근데 이게 페어 프로그래밍인가?

페어 프로그래밍을 통해서 구현이 끝나자마자 '이제 같이 검토하자고' 페어가 말했다. 

근데 나는 그 말을 듣는 순간 '**이게 잘 될까?'**라는 생각을 했다. 이유는 단순하긴 한데, 나는 이 코드가 어떻게 돌아가는지를 모른다고 느꼈다. 실제로 요구사항도 제대로 안 읽었고, 코드는 AI가 만들었고, 나는 그걸 그냥 복붙했다. 하지만 동작은 했다. 근데 왜 동작하는지는 몰랐다. 추상 클래스가 왜 필요한지, GameResult의 계산 로직이 왜 저 자리에 있는지, 내가 그 선택을 한 게 아니니까 어떻게 검토를 해야할 지 모르겠다고 느꼈다.

그런데 신기했던 건 페어였다.

페어는 코드를 꽤 잘 이해하고 있는 것 같았다. 같이 AI 결과물을 복붙했는데, 페어는 코드를 보며 수정할 부분을 찾고 있었다. 나는 물음표로 가득 찬 채로 화면을 바라보고 있는데, 페어는 흐름을 따라가면서 "여기는 이렇게 하면 좋을 것 같다"는 식으로 말하고 있었다. 이게 어떻게 가능한 건지 지금도 잘 모르겠다. 코드를 보면 그냥 구조가 읽히는 사람과, 나처럼 내가 직접 고민한 코드가 아니면 체화가 잘 안 되는 사람의 차이인 걸까? 뭐 그런 생각이 들었다.

아무튼 그 상황에서 또 다른 생각이 따라붙었다.

우리가 검토를 같이 하면 어떤 결과가 나올까? 나는 이 부분이 이상하게 느껴졌다. 예를 들어, 나는 내가 배웠던 방식으로 이런 코드 스타일을 지향하는데 페어는 자신의 생각으로 다른 코드 스타일을 지향할 수 있다고 생각했다. 서로 선호하는 방향이 다르고, 무엇보다 우리가 '객체지향 원칙을 어떻게 적용할 것인가'라는 공통된 목표를 합의한 적도 없었기에 15분씩 돌아가면서 각자 손을 대면, 충돌이 나거나 이상한 결과물이 나올 것 같았다.

그럼 '차라리 페어 프로그래밍에서 만든 코드 그대로 내는 게 맞지 않을까?' 이런 생각을 했다. 또한 페어 프로그래밍을 해놓고 각자 다 손대면, 애초에 같이 한 이유가 사라지는거라고 생각했다.

더구나 미션 구현 원칙에는 이렇게 써 있었다.

> "빠르게 구현하고, 빠르게 PR을 보내라. 완벽한 코드가 아니라 피드백을 받을 수 있는 코드가 목표다."

실제로 구현은 됐다. 그럼 지금 상태에서 우리(?) 혹은 나의 생각을 리뷰어에게 전달하는 게 맞다고 판단했다. 그래서 PR을 보냈다. 코드보다 질문들을 더 생각했던 것 같다.

페어 프로그래밍에서 AI를 쓰는 게 우테코 과정에서 어떻게 받아들여지는지가 궁금했다. 현업에서는 AI가 생산성을 올려준다는 게 명확한데, 학습하는 시점에서도 그게 맞는 방향인지 리뷰어의 생각이 알고 싶었다.

기록을 남기지 않은 것도 솔직하게 썼다. AI 덕분에 막히는 순간이 없었으니 기록할 것도 없었다고. 기록 자체가 의미 있는 건지에 대한 고민도 그대로 담았다.

지금 다시 읽어보니, 내 코드도 아니고, 내 기록도 없고, 내 설계도 없는 상황을 어떻게 이해해야 할지 몰라서, 질문 형식으로 리뷰어에게 물어봤던 것 같다.

## 객체지향 생활체조, 자가 점수 1점

PR 본문에 체크리스트가 있었다.

> "객체지향 생활체조 요구사항을 얼마나 잘 충족했다고 생각하시나요? 1~5점 중에서 선택해주세요."

나는 1점을 냈다.

솔직히 그 질문 자체가 처음엔 당황스러웠다.

LMS 어디에도 '객체지향 생활체조'라는 말이 명시적으로 나오지 않았고, 이 미션이 그것에 대한 교육과정이라는 걸 인식하지 못했다. 프로그래밍 요구사항이 그 원칙들을 담고 있다는 건 어렴풋이 느꼈지만, 1점을 낸 건 사실상 '나는 잘 모르겠다'에 가까운 답이었다.

## 리뷰어가 답했다.

리뷰어 로빈의 첫 리뷰가 왔다.

코드 코멘트보다 먼저, PR 본문에 남긴 질문들에 대한 답변이 눈에 들어왔다.

> "결론부터 말씀드리면, 우테코 프로그래밍 미션에서 AI를 사용하는 것은 허용되어서는 안 된다고 생각합니다."

생각보다 강하게 말했다.

리뷰어는 현업에서 본인이 직접 Claude Max, ChatGPT Pro, Gemini Pro를 유료 구독해 업무에 사용한다고 했고, AI가 생산성을 올려준다는 건 당연한 사실이고, 쓰지 않는 게 오히려 이상한 시대라는 것도 인정했다. 거기까지는 내 생각이랑 같았다.

근데 그다음 문장이 달랐다.

> "쉽게 배운 것은 더 쉽게 잊힙니다. AI를 사용해 쉽게 넘어갔다면, 그건 학습이 아니라 일을 한 것일 뿐입니다."

반박할 말이 없지는 않았다. 하지만 구구절절 다 맞는 말이라고 생각했다.

사실 코드를 작성하면서 막히는 순간이 없었던 것 같다. 기록도 물론 없었고, AI를 통해 쉽게 넘어갔으니 뭔가를 고민했다는 흔적도 없었다. 그러니 뭘 배웠는지를 설명하는 것도 어색할 수 밖에 없던 것 같다.

리뷰어의 답변을 읽으면서 든 생각이 두 가지였다.

첫 번째는 AI로 빠르게 결과물을 내는 것보다, 내가 직접 고민해서 이해할 수 있는 코드를 짜는 게 맞다는 확신이 생겼다. 이건 사실 페어 프로그래밍을 하는 내내 어딘가 불편했던 감각과 연결된 것이었다. 뭘 짜고 있는지 모르겠다는 느낌, 내 코드가 아니라는 감각, 그게 왜 불편했는지를 리뷰어가 정리해준 느낌이였다.

두 번째는 다음에 페어 프로그래밍을 할 때는 반드시 원칙을 먼저 세워야겠다는 생각이었다. 이번에는 아무것도 합의하지 않은 채로 시작했다. 어떻게 진행할지, 각자의 방향이 다를 때 어떻게 맞출지, 무엇을 목표로 할지, 이런 것들이 없으니 페어의 흐름에 그냥 쓸려갔던 것 같고, 내 생각이 어디 있는지도 모르는 채로 코드가 쌓였던 것 같다. 내 생각을 지키려면 그 생각을 먼저 분명히 해두어야 한다는 걸 이번에 몸으로 배웠다.

사실 솔직히 말하면, 리뷰어의 말이 충격이라기보다는 확인에 가까웠다.

내가 페어 프로그래밍 내내 어색하게 느꼈던 것들, 뭘 짜고 있는지 모르겠다는 감각, 이게 맞는 방향인가 싶었던 순간들이 착각이 아니었다는 걸 리뷰어를 통해 다시 한 번 확인한 느낌이었다.

기록에 대한 답변도 따로 있었다.

> "기록하지 않으면 과거의 생각과 지금의 생각을 비교할 수 없습니다. 레벨 1에서의 티뉴와 레벨 4에서의 티뉴, 1년차 프로 개발자인 티뉴를 비교할 수 없습니다. 비교할 수 없으면 성장했다고 할 수 있을까요?"

그 말도 꽤 오래 남았다. 사실 지금 이 글을 쓰는 것도 그 질문에 대한 나름의 답이긴 하다.

## 질문들이 쏟아졌다

코드 코멘트들은 대부분 질문 형식이었다. 처음엔 친절한 방식처럼 느껴졌는데, 하나씩 읽다 보니 이게 오히려 더 날카롭다는 걸 알았다. 답을 주지 않고 질문을 던진다는 건, 내가 스스로 생각해야 한다는 뜻이다. 그리고 차근차근 리뷰를 바탕으로 코드를 수정하며 내 생각을 정리해봤던 것 같다.

첫 번째로 피드백은 아주 작은 데서 시작했다.

```
public enum Suit {
 HEART("하트"),
 DIAMOND("다이아몬드"),
 SPADE("스페이드"),
 CLUB("클로버");
}
```

> "줄여 쓰지 않는다(축약 금지) 요구사항을 지키지 않은 이유는 무엇인가요?"

처음엔 '뭘 줄인 거지?' 싶었다. CLUB이 축약어라는 생각을 해본 적이 없었다. AI를 사용하긴 했지만 도메인을 검색하다 발견한 자료에서 CLUB을 봤고, 그게 공식 용어인 줄 알았다. 그래서 다시 찾아봤다. 그랬더니 실제로 카드 문양의 공식 명칭은 CLUB이 맞았다. 클로버는 일상에서 부르는 이름이고, 정식 용어는 CLUB이라고 했다. 리뷰어도 나중에 이 부분은 본인이 잘못 알고 있었다며 직접 인정해줬다.

> "요 부분은 제가 잘못 알았네요. Club이 공식 용어가 맞다고 하네요. 그냥 냅두고 진행하면 될 것 같아요."

작은 에피소드였지만 인상에 남았다. 리뷰어도 틀릴 수 있고, 내가 직접 확인하고 근거를 가져가는 게 맞다는 걸 이 작은 순간을 통해서 알 수 있었다.

두 번째는 더 큰 문제를 만났다.

```
public class Player extends Participant {
 private boolean wantsHit = true;
}
```

> "Player 클래스는 Participant를 상속받았기 때문에 인스턴스 변수가 3개가 됩니다. 지키지 않은 이유가 무엇인가요?"

Player 자체에는 변수가 하나밖에 없으니 괜찮다고 생각했는데, Participant를 상속받으면 부모의 name, hand까지 포함해서 3개가 된다는 게 보이지 않았다. 상속받은 클래스의 인스턴스 변수까지 함께 세야 한다는 걸 인식하지 못했다.

이를 해결하기 위해 히트 여부 관리를 BlackjackController로 이동시켰다. Map<Player, Boolean> 형태의 hitDecision을 컨트롤러가 갖는 방식으로 하더라도 크게 책임을 벗어나진 않는다고 생각했다. 그랬더니 이번엔 컨트롤러가 inputView, outputView, hitDecision으로 딱 3개가 됐다. 

그런데 다른 문제가 생겼다. 초기 카드 배분 수(2장)를 생성자에서 주입받으면 테스트가 유연해지는데, 그렇게 하면 컨트롤러 변수가 4개가 된다. 결국 이부분은 INIT_ROUND라는 상수로 타협했다.

```
public class BlackjackController {
 private static final int INIT_ROUND = 2;
 private final InputView inputView;
 private final OutputView outputView;
 private final Map hitDecision = new HashMap<>();
}
```

리뷰어의 반응이 예상 밖이었다.

> "저 규칙들이 정말 꼭 지켜야 하는 규칙일까요? 정말 그것이 좋은 방법이라 생각한다면, 그 의도를 설명하기를 원했어요."

이 말이 꽤 오래 머릿속에 맴돌았다. 나는 규칙을 지키기 위해 코드를 구겨 넣고 있었는데, 리뷰어는 규칙 자체를 의심하라고 했다. 규칙의 취지를 더 잘 달성하는 방법이 있다면, 형태를 어기는 것이 오히려 규칙을 따르는 것보다 나을 수 있다는 뜻이었다.

인스턴스 변수를 3개 이하로 유지하는 규칙은 결국 하나의 클래스가 너무 많은 책임을 갖지 않도록, 응집도를 높이기 위한 수단인데 나는 그 취지를 이해하지 못한 채 숫자를 맞추는 데만 집중했던 것 같다. 그러니 hitDecision을 컨트롤러로 옮기는 게 좋은 설계인지, 아니면 그냥 규칙을 피하기 위한 꼼수인지를 스스로 판단하지 못했던 것 같다.

리뷰어의 말을 듣고 나서야 앞으로는 기준과 타협점을 잡아야겠다는 생각을 했다. 규칙을 지키느냐 마느냐가 아니라, 이 클래스가 가지고 있는 값(인스턴스 변수)들이 서로 응집되어 있는가를 먼저 따져봐야 한다는 것이고, 그 기준 위에서 요구사항과의 타협점을 찾아야겠다는 생각으로 정리되었다.

세 번째로, 리뷰어 질문 중 나를 가장 오래 붙잡아둔 게 있었다.

```
public static GameResult of(final Score playerScore, final Score dealerScore) {
 if (playerScore.isBust()) {
 return LOSE;
 }
 if (dealerScore.isBust()) {
 return WIN;
 }
 return compare(playerScore, dealerScore);
}
```

> "왜 정적 팩토리 메서드를 사용하셨나요?"

> "게임 결과를 표현하는 것과, 그것을 계산하는 것을 분리하지 않은 이유는 무엇인가요?"

첫 번째 질문에 대한 답을 PR에 그대로 남겼다.

> "정적 팩토리 메서드를 사용한 이유에 대해서는 솔직히 깊이 고민하지 않고 작성한 부분이었습니다. of라는 네이밍이 관례적으로 많이 사용되는 것을 보고 따라 쓴 것에 가까웠고, 생성자 대신 정적 팩토리 메서드를 선택해야 하는 명확한 이유를 스스로 설명하지 못했습니다."

솔직한 답변이었지만, 쓰면서 불편했던 것 같다. 사실 두 번째 질문이 더 당황스러웠다. GameResult가 결과를 표현하면서 동시에 점수를 비교해 계산하는 역할까지 갖고 있다는 것 자체를 문제로 인식하지 못했다. 리뷰를 받기 전까지 이 코드에 두 가지 책임이 혼재되어 있다는 걸 몰랐다.

'왜 인지하지 못했는지?'를 곰곰히 생각해봤다.

먼저는 코드를 내가 설계한 게 아니기 때문이라고 생각했다. AI가 만들었고 나는 검토했다. 검토하는 사람의 시선은 '이 코드가 동작하는가', '요구사항을 충족하는가'에 먼저 향하지 않았을까? 그런 생각을 했다. '이 코드가 왜 이 모양이어야 하는가', '더 좋은 구조는 없는가'를 물으려면 설계 단계부터 직접 고민한 흔적이 있어야 할 것 같았다. 사실 이 코드를 내 것으로 만들지 않은 상태에서 PR을 보낸 것이다.

질문을 받고 나서야 GameResult에서 계산 책임을 GameResultCalculator로 분리하고 GameResult을 enum 클래스로 만들어서 값을 들고 있는 책임만 가질 수 있도록 만들었다. 또한, 딜러 결과를 필드 대신 호출 시마다 플레이어 결과를 역전시켜 도출하는 방식으로도 바꿨다.

이러한 과정을 통해서 코드가 바뀐 것보다, 수정을 하면서 처음으로 '왜 이렇게 해야 하는지'를 내 말로 설명할 수 있고 코드를 이해할 수 있게 되었다는 것이 달라진 점이라고 느꼈다.

마지막으로, 머지 직전에 리뷰어가 한 가지를 더 짚었다.

```
@Override
public boolean equals(Object o) {
 if (o == null || getClass() != o.getClass()) return false;
 Card card = (Card) o;
 return suit() == card.suit() && rank() == card.rank();
}
```

> "record에서 equals와 hashCode는 자동으로 정의되는데, 특별히 재정의한 이유가 있나요?"

이것도 큰 이유가 없었던 것 같다. record의 자동 생성 메서드를 믿지 못해서 명시적으로 재정의한 건지, AI가 class를 생성했을 때 이미 있었던 건지, 솔직히 기억도 나지 않았다. 아마 후자였을 것이다. AI가 만든 코드에 이미 있었고, 나는 왜 있는지 따지지 않고 그대로 뒀던 것 같다. 이게 AI를 사용하면서 무심코 생기는 문제의 전형이라고 느꼈다.

@DisplayName과 한글 메서드명을 동시에 쓴 것도 비슷했다. 개발을 하는 중간에 페어와 의견 차이가 있었는데 기존에 있던 부분을 합의된 방식대로 정리하지 못한 채 올려버렸다. 이에 대해서 리뷰어가 이유를 물었고 그제서야 발견했다. 유지보수 시 하나만 수정하면 불일치가 생길 수 있다는 것을 잘 알고 있었지만, AI와 테스트코드를 믿고 코드를 찬찬히 읽어보지 않아서 생긴 문제였다.

## 머지 이후 남겨진 것들

코드는 머지됐다. 리뷰어가 마지막 코멘트를 남겼다.

> "코멘트 하나 하나에 고민하고 생각해본 흔적이 잘 보이네요."

그 말이 완전히 기쁘지 않았다.

고민의 흔적이 보이는 건 맞다. 근데 그게 처음부터 있었던 게 아니라, 리뷰를 받고 나서야 생긴 것들이었다. 처음부터 내가 그 고민을 하고 코드를 짰다면 어떤 PR이 나왔을까, 하는 생각이 들었다.

머지와 함께 추가 피드백도 왔다. 다음 사이클에서 반영하면 좋을 것들이었다. 추상 클래스에서 재정의를 고려하지 않은 메서드에는 final을 붙여야 한다는 것과 셔플 전략은 생성자에서 받아서 필드에 저장하고 생성 시점에 실행하는 게 더 깔끔하다는 것, 그리고 Consumer<List<Card>>처럼 추상적인 타입 대신 전용 인터페이스를 선언해서 의도를 드러내야 한다는 것이 좋다고 했다.

```
// 기존
public void run(final Consumer> shuffleStrategy) { ... }

// 개선 방향
@FunctionalInterface
public interface ShuffleStrategy {
 void shuffle(List cards);
}
```

## 사이클1을 마치며

피드백들은 대체적으로 납득이 됐다. 근데 내가 먼저 생각해서 나온 게 하나도 없었다고 느꼈다. 전부 리뷰어가 보여준 뒤에야 '아, 그렇구나'가 됐다.

곰곰이 생각해보니 이건 단순히 AI를 썼기 때문만은 아니었다.

근본적으로 내가 좋은 코드에 대한 기준 자체가 없었다. Consumer 대신 전용 인터페이스를 써야 한다는 걸 몰랐던 게 아니라, 그게 문제가 될 수 있다는 것 자체를 몰랐다. 모른다는 걸 모르는 상태였다.

리뷰를 받고 수정하는 건 할 수 있다. 근데 그게 반복되다 보면 리뷰어가 없으면 판단을 못 하는 구조가 되지 않을까? 그런 생각을 했다. 내 코드를 스스로 평가할 기준이 없으면, 결국 누군가가 문제를 짚어줄 때까지 그냥 지나치게 된다고 느꼈고 이번 사이클에서 계속 그랬던 것 같다.

그래서 오브젝트를 처음부터 읽어보기로 했다. 책을 읽으면서 좋은 코드를 작성할 수 있는 기준을 만들어봐야겠다.

또한, 미션을 되돌아보면 후회가 남는 것들이 많았다.

요구사항을 제대로 안 읽고 시작했고, 페어와 방향을 맞추지 못했고, AI가 만든 코드를 내 것으로 만들지 못한 채 PR을 보냈다. 리뷰를 받으면서 질문들이 내 것이 되기 시작했고, 수정하면서 처음으로 코드를 이해했다.

순서가 거꾸로였다.
