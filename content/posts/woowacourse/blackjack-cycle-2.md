## 책임을 어디에 둘 것인가?

베팅 기능을 추가하라는 요구사항을 받았을 때, 처음엔 단순하게 생각했다.

> '돈을 걸고, 이기면 받고, 지면 잃는다.'

하지만 막상 코드를 건드리기 시작하자 예상치 못한 문제들이 폭포수처럼 쏟아졌다. Money를 어디에 두어야 하는지, 승패 판정은 누가 해야 하는지, 메서드 하나를 추가할 때마다 "이게 정말 이 객체의 책임이 맞는가?"라는 근본적인 질문에 부딪혔다.

### 1. 일급 컬렉션의 책임 범위는 어디까지인가?

처음에는 객체지향의 핵심인 '정보 전문가(Information Expert)' 패턴과 '묻지 말고 시켜라(Tell, Don't Ask)' 원칙 관점에서 접근했다. 각 플레이어의 이름을 호명하며 베팅 금액을 묻기 위해서는 어찌 됐든 전체 플레이어 목록을 순회해야 한다. 여기서 플레이어 목록(List<Player>)이라는 데이터를 온전히 소유하고 있는 객체는 Players 일급 컬렉션뿐이다.

만약 외부(컨트롤러)에서 책임을 진답시고 players.players()처럼 리스트를 통째로 꺼내와 for문을 돌린다면, 이는 객체에게 일을 시키는 것이 아니라 데이터를 뺏어와서 밖에서 직접 처리하는 수동적인 구조처럼 느껴졌다.

게다가 이번 미션에는 'indent(인덴트, 들여쓰기) depth를 1까지만 허용한다 , 그리고 함수(또는 메서드)의 길이가 10라인을 넘어가지 않도록 구현한다'라는 제약 조건이 있었다. 만약 컨트롤러에서 반복문을 열고, 뷰를 호출해 입력을 받고, 파싱을 거쳐 Money 객체를 매핑하는 일련의 과정을 넣다보면 이 제약 조건들을 지키기가 어려워진다고 생각했다.

따라서 순회라는 행위 자체를 플레이어 정보를 가장 잘 아는 Players 내부로 깊숙이 숨기는 것이 맞다고 판단했다. 컨트롤러는 밖에서 그저 "네가 가진 플레이어들의 베팅 금액을 수집해서 결과만 줘"라고 메시지만 던지는 것이 훨씬 객체지향적이고, 인덴트 제약도 우아하게 해결하는 방법이라고 굳게 믿었던 것이다.

단, 도메인 객체인 Players가 UI(입출력) 로직을 직접 알게 할 수는 없었다. 그래서 고안해 낸 것이 @FunctionalInterface인 WagerReader였다.

```
// Players.java - participant 패키지가 Money(domain.money)에 의존
public record Players(List players) {
    public Map placeWagers(WagerReader wagerReader) {
        Map wagers = new LinkedHashMap<>();
        players.forEach(player -> {
            Money wager = wagerReader.wagerOf(player);
            wagers.put(player, wager);
        });
        return wagers;
    }
}

@FunctionalInterface
public interface WagerReader {
    Money wagerOf(Player player);
}
```

이렇게 설계하면 컨트롤러에서 inputView::readWager를 넘겨준다. Players가 내부적으로 순회를 돌며 player를 던져주면, View 계층에서는 "%s의 배팅 금액은?%n" 메시지를 띄우고, 사용자의 입력을 받아 파싱한 뒤 Money 객체로 만들어 다시 반환하는 흐름이었다.

Players 내부에서 순회를 캡슐화하면서도 UI 책임은 외부로 깔끔하게 밀어낼 수 있는 꽤 괜찮은 구조라고 여겼다.

하지만 이 구조는 치명적인 단점이 있었다. 순회를 위임하여 캡슐화는 지켰지만, participant 패키지에 있는 Players와 WagerReader가 Money 객체에 강하게 의존하게 되는 도메인 간 결합 문제가 발생했다.

가만히 생각해보니, '**참여자 목록을 관리하는 책임**'과 '**게임의 베팅 금액을 관리하는 책임**'은 완전히 별개의 도메인이었다. 만약 베팅 규칙이 바뀌거나 금액 관련 로직이 변경되었을 때, 참가자를 관리하는 Players 클래스까지 영향을 받는 것은 단일 책임 원칙(SRP)에도 어긋났다.

결국 베팅 수집 책임을 애플리케이션의 흐름을 제어하는 컨트롤러(Controller)로 빼냈다 .

도메인 객체들은 서로의 존재를 모른 채 순수하게 자신의 책임만 다하고, 그 독립적인 도메인들을 중간에서 연결하고 조율(Coordinate)하는 것이 바로 컨트롤러의 본질적인 역할이라고 판단했기 때문이다. 또한 컨트롤러가 중간 객체로서 뷰(View)를 통해 플레이어의 입력을 받고, 이를 Money 객체로 생성하여 매핑해 주는 흐름이 자연스럽다고 느껴졌다.

```
// 컨트롤러 - 배팅 수집 책임을 가짐
private Map placeWagers(Players players) {
    Map wagers = new LinkedHashMap<>();
    for (Player player : players.players()) {
        int amount = inputView.readWager(player);
        wagers.put(player, new Money(amount));
    }
    return wagers;
}
```

하지만 코드를 이렇게 수정하여 제출하고 나서도 마음 한구석이 몹시 찝찝했다. 도메인 간의 의존성은 성공적으로 끊어냈지만, 그 대가로 컨트롤러에서 players.players()를 호출해 내부 리스트를 바깥으로 꺼내어 순회해야 했기 때문이다.

> "캡슐화를 깨뜨리면서까지 도메인을 분리하는 게 정말 맞을까? 일급 컬렉션이 도메인 외의 관심사까지 품어야 할까, 아니면 순수하게 컬렉션 관리만 해야 할까?"

이 트레이드오프 사이에서 어느 쪽이 객체지향적으로 더 나은 방향인지 확신이 서지 않았고, 결국 이 고민의 흔적을 PR 리뷰 요청에 첫 번째 질문으로 남기게 되었다. 그리고 리뷰어님의 "배팅이 하나의 도메인 개념은 아닐까요?"라는 답변을 통해, 내가 컨트롤러에서 각각 순회하여 조합하기로 한 결정이 구조적으로 올바른 방향이었다는 것을 확인할 수 있었다.

하지만 도메인 간의 결합을 끊어내고 일급 컬렉션의 책임을 명확히 한 것까지는 좋았으나, 이 결정은 곧 예상치 못한 부메랑이 되어 돌아왔다.

> 입력부터 도메인 매핑, 객체 간 조율까지 모든 흐름을 컨트롤러가 떠안게 되면서 또 다른 문제의 씨앗이 심어지고 있었던 것이다.

이것이 바로 미션 후반부, 컨트롤러가 흐름 제어, 입출력, 협력 도메인 연결, DTO 변환까지 모두 알아야 하는 비대한 구조('Fat Controller')를 마주하며 파사드(Facade) 객체인 BlackjackGame의 도입을 치열하게 고민하게 만든 문제의 서막이었다.

### 2. 값 객체(VO)와 도메인의 구분점: 가변과 불변의 경계

Money 객체를 다루면서 버그를 경험했다.

처음 베팅 금액과 수익금을 객체로 분리할 때, 현실 세계의 지갑을 떠올렸다. 지갑에 돈이 들어오면 원래 있던 금액에 돈이 '더해지는' 것이니, Money 객체 역시 자기 자신의 상태(값)를 변경하는 것이 직관적이라고 생각했다.

그래서 처음 설계한 Money 객체는 내부의 value를 직접 변경하는 가변(Mutable) 객체였다.

```
// Before: 상태를 직접 변경하는 가변 Money
public class Money {
    private int value; // final이 아님

    public void add(Money money) {
        this.value += money.value; // 자기 자신의 상태를 직접 변경
    }

    public void multiply(int multiplier) {
        this.value *= multiplier; // 자기 자신의 상태를 직접 변경
    }
}
```

이렇게 만들고 나니 로직을 작성할 때는 꽤 편했다. 그저 add()나 multiply()를 호출하기만 하면 값이 척척 바뀌었기 때문이다 . 하지만 이 사소해 보이는 결정은 수익 계산 로직(calculateProfits)을 구현할 때 문제가 되었다.

블랙잭 게임이 끝나고 딜러의 수익을 계산하기 위해 딜러가 가진 Money 객체에 add()를 호출하는 순간, 예상치 못한 문제가 발생했다.

> 딜러와 동일한 Money 객체(예를 들어, 기본 베팅금이나 초기 상태의 돈)를 참조하고 있던 다른 플레이어들의 금액까지 모조리 함께 바뀌어버린 것이다.

객체는 '참조(Reference)'로 전달된다는 사실을 잘 몰랐다. A와 B가 같은 10,000원짜리 지폐(객체)를 바라보고 있는데, A가 지폐에 5,000원을 더해 15,000원으로 덧칠해버리니 B의 돈도 강제로 15,000원이 되어버린 셈이다.

당연히 테스트 코드는 실패했다. 값이 같아야 하는데, 메모리 주소가 달라졌거나 엉뚱한 값을 가리키고 있다는 뜻이었다 .

```
org.opentest4j.AssertionFailedError:
expected: blackjack.domain.money.Money@2710
but was: blackjack.domain.money.Money@ffffd8f0
```

이 에러를 마주하고 나서야 내가 엔티티(Entity)와 값 객체(Value Object, VO)의 성질을 완전히 혼동하고 있었다는 사실을 깨달았다. Player 같은 엔티티는 카드를 새로 받으면서 상태가 변하지만, '10,000원'이라는 값 자체는 결코 변하지 않는다. 10,000원에 5,000원을 더하면 10,000원짜리가 변신하는 것이 아니라, '15,000원'이라는 완전히 새로운 값이 탄생하는 것이다.

결국 Money를 불변(Immutable) 타입인 record로 전면 수정했다. 모든 연산 메서드가 기존 객체를 건드리지 않고, 새로운 Money 객체를 생성하여 반환하도록 바꾼 것이다 .

```
// After: 새로운 객체를 반환하는 불변 Money
public record Money(int value) {

    public Money add(Money money) {
        return new Money(this.value + money.value()); // 완전히 새로운 객체 반환
    }

    public Money multiply(double multiplier) {
        return new Money((int) (this.value * multiplier)); // 완전히 새로운 객체 반환
    }
}
```

이렇게 수정하고 나서야 참조 공유 버그가 깔끔하게 사라졌다.

이 경험을 PR 리뷰에 남겼을 때, 리뷰어님은 이렇게 답변해 주셨다.

> "불변을 기본값으로 하고 그게 영 안 될 거 같으면 가변으로 하면 됩니다. 그 이유는 여러 가지가 있을 테지만 그중 하나가 경험하신 사례입니다."

엔티티는 상태가 변할 수 있지만, 값 객체는 반드시 불변이어야 한다는 이론. 머리로만 알고 있던 지식을 런타임 에러를 통해 체득한 순간이었다.

### 3. 게임 결과 판정 로직의 응집도 vs 추상화 수준

블랙잭의 승패 판정은 요구사항이 추가되면서 단순 점수 비교로 끝나지 않게 되었다.

사이클 1에서는 승, 무, 패 3가지 결과만 있었고, 이는 두 참여자의 Score 점수만 비교하면 충분했다.

하지만 사이클 2에서 베팅 기능과 함께 '처음 두 장의 카드 합이 21일 경우 블랙잭'이라는 새로운 승패 조건이 생겼다. 단순히 점수가 21점인지 여부만으로는 그게 카드 두 장으로 만든 진짜 블랙잭인지, 카드를 여러 장 뽑아서 만든 21점인지 Score 객체만 봐서는 알 길이 없었다.

판정 로직을 한 곳으로 모으기 위해 GameResultCalculator가 Player와 Dealer 객체를 직접 받도록 리팩터링했다. 하지만 이렇게 하니 파라미터가 Score였을 때 유지되던 추상화 수준이 깨지는 것 같아 몹시 불안했다.

처음에는 기존 설계를 최대한 유지하려고 했다. 블랙잭 여부를 판정하는 로직은 GameResults.create에 두고, 일반적인 점수 비교 로직은 기존처럼 GameResultCalculator가 Score 객체를 받아 처리하도록 역할을 분산시켰다.

```
// GameResults.java (블랙잭 판정)
if (player.isBlackjack() && dealer.isBlackjack()) {
    gameResults.put(player, GameResult.DRAW);
} // ...

// GameResultCalculator.java (일반 Score 비교)
public GameResult calculate(final Score playerScore, final Score dealerScore) {
    // 점수 비교 및 버스트 판정 로직
}
```

하지만 승패 판정 로직이 두 곳으로 쪼개지니 코드를 파악하기 어려워졌다 . 결과 판정을 한 곳에서 응집력 있게 관리해야 한다는 필요성을 느꼈고, 결국 Calculator가 승패 로직 전체를 담당하도록 리팩터링했다 .

이를 위해 GameResultCalculator의 calculate 메서드는 Score 대신 Player와 Dealer 객체를 직접 파라미터로 받도록 변경되었다 . 블랙잭 여부(isBlackjack())를 확인하려면 도메인 객체 자체가 필요했기 때문이다.

```
// GameResultCalculator.java (블랙잭 포함 전체 판정)
public GameResult calculate(Player player, Dealer dealer) {
    if (player.isBlackjack() && dealer.isBlackjack()) {
        return GameResult.DRAW;
    }
    if (player.isBlackjack()) {
        return GameResult.BLACKJACK;
    }
    // ...버스트 및 점수 비교
}
```

판정 로직은 한 곳에 모여 응집도가 높아졌지만, 이 결정을 내리고 나서도 마음이 편치 않았다 .

Score라는 인터페이스/값 객체만 받아서 계산하던 Calculator가 Player와 Dealer라는 구체적인 타입에 직접 의존하게 되었기 때문이다 .

나는 이것이 '객체지향에서의 추상화 수준이 깨진 것'이라고 생각했고, 이 트레이드오프 사이에서 응집도와 추상화 중 무엇을 우선해야 할지 고민이 되어 리뷰를 남겼다.

이 고민은 PR 리뷰에서 리뷰어님이 남겨주신 한마디로 완전히 해소되었다.

> "본질적으로 GameResult에 단순히 점수 계산만으론 알 수 없는 BlackJack 상태가 추가되었고, 당연히 시그니처에서 Score를 사용할 수 없게 된 것뿐입니다. 즉, 추상화 수준이 깨진 게 아니라 요구사항이 바뀌면서 필요한 추상화 수준 자체가 달라진 것입니다."

내가 지키려던 Score라는 추상화는 사이클 1의 요구사항에만 맞았던 것이였다. 새로운 도메인 규칙(블랙잭)이 추가되었다면 거기에 맞춰 로직을 판단할 수 있는 수준(Player, Dealer 혹은 Hand)으로 추상화의 기준점을 다시 잡는 것이 필요했다.

과거의 구조에 얽매여 억지로 분산시켜 둔 로직을 하나로 응집시킨 나의 리팩터링이, 결국 유지보수하기 좋은 설계를 향한 올바른 방향이었음을 알 수 있게 되었다.

### 4. enum에 행위를 넣는 것은 어디까지 적절한가?

GameResult를 설계하면서 자바의 enum이 가질 수 있는 행위의 범위에 대해 깊이 고민하게 되었다.

처음 설계했던 GameResult는 WIN, DRAW, LOSE만을 가지는 순수한 상수 묶음이었다 . 그러다 보니 게임이 끝난 후 플레이어의 수익을 계산할 때, 이 enum을 가져다 쓰는 외부(GameResults)에서 분기 처리를 해야만 했다 .

```
// Before: 외부(GameResults)에서 if문으로 수익 계산
private int calculatePlayerProfit(Player player, int wager) {
    GameResult gameResult = playerResults.get(player);
    if (gameResult == GameResult.WIN) {
        return wager;
    }
    if (gameResult == GameResult.LOSE) {
        return -wager;
    }
    return 0; // DRAW
}
```

하지만 이런 방식은 객체지향적이지 않다고 느꼈다. 만약 새로운 결과 타입(예: 1.5배 배당을 받는 BLACKJACK)이 추가된다면 외부의 if 분기문을 일일이 찾아서 수정해야 하고, 자칫 하나라도 빠뜨리면 버그로 이어지기 때문이다.

이를 해결하고자 자바 enum의 강력한 기능인 '상태와 행위의 응집'을 활용했다. GameResult 내부에 배율(multiplier) 상태를 갖게 하고, 직접 Money 객체를 받아 계산된 수익을 반환하는 profitOf 메서드를 추가한 것이다 .

```
// After: enum이 배율 상태와 계산 행위를 가짐
public enum GameResult {
    BLACKJACK(1.5), WIN(1), DRAW(0), LOSE(-1);

    private final double multiplier;

    GameResult(double multiplier) {
        this.multiplier = multiplier;
    }

    public Money profitOf(Money wager) {
        return wager.multiply(multiplier);
    }
}
```

이렇게 리팩터링을 거치자 외부의 보기 싫던 분기문이 사라지고 return gameResult.profitOf(wager); 단 한 줄로 깔끔하게 위임할 수 있게 되었다 . 코드는 훨씬 선언적으로 변했고, 새로운 결과가 추가되어도 enum 내부만 수정하면 되니 안전해 보였다.

하지만 코드를 작성해 놓고 보니 또 다른 찜찜함이 밀려왔다. 분기는 사라졌지만, 승패라는 '게임 결과'를 나타내는 도메인(GameResult)이 '돈'을 다루는 외부 도메인(Money)에 직접적으로 의존하게 된 것이다. 수익 계산 로직을 하나 편하게 만들자고 전혀 다른 성격의 객체를 enum 안으로 끌고 들어오는 것이 과연 올바른 설계인지 의문이 들었다.

이 고민을 PR에 남겼을 때, 리뷰어님은 아주 날카로운 질문을 던지셨다.

> "reverse()와 profitOf() 중 무엇이 더 GameResult의 본질에 가까운 행위일까요? 둘 중 하나를 뺀다면 어떤 걸 뺄 것 같나요? 그 근거가 무엇인가요?"

당시 GameResult 안에는 플레이어의 결과를 반전시켜 딜러의 결과를 구하는 reverse() 메서드도 함께 있었다 . 가만히 생각해 보니, 승패를 뒤집는 reverse()가 GameResult라는 개념 그 자체에 더 가까운 본질일지도 모른다는 생각이 들었다. 하지만 내부의 상태값(multiplier)을 사용해서 계산을 도와주는 profitOf() 역시 객체의 응집도를 높여준다는 측면에서 포기하기 아쉬웠다.

결국 나는 고민 끝에 reverse()를 GameResults 내부 메서드로 이동시키고, profitOf()만 GameResult enum에 남겨두는 선택을 했다.

솔직히 말해 이게 최선의 선택이었는지는 아직도 확신이 없다. profitOf() 역시 GameResult의 본질인 multiplier를 기반으로 계산을 수행하는 것이니 데이터와 행위를 한곳에 모은다는 관점에서 enum 안에 있는 것이 자연스럽다는 생각과, 동시에 Money라는 외부 타입에 대한 의존성을 만들어냈다는 찜찜함이 여전히 내 안에 공존하고 있기 때문이다 .

### 5. 메서드 하나를 추가할 때의 판단 기준

"수익을 계산한다"는 단 하나의 행위를 추가해야 했다. 그런데 이 메서드를 대체 어디에 두어야 할지 결정하는 것이 이번 미션에서 가장 막막했던 순간 중 하나였다 .

객체지향에서는 데이터를 가진 쪽에 행위를 두어야 한다고 배웠다. 하지만 수익 계산에 필요한 핵심 데이터인 '배팅 금액(wager)'과 '배당률(multiplier)'이 서로 다른 객체에 나뉘어 있다 보니 선택지가 여러 개로 갈렸다 .

1. GameResult가 계산한다: gameResult.profitOf(wager); (배당률을 가지고 있으니 계산 책임을 진다. 하지만 Money라는 외부 타입에 의존해야 한다.)
1. Money가 계산한다: wager.profitBy(gameResult); (돈을 가지고 있으니 돈이 스스로 계산하게 한다. 하지만 Money가 게임의 결과 규칙을 알아야 한다.)
1. GameResults에서 직접 계산한다: (참여자들의 결과를 묶어서 관리하는 곳이니 직접 계산한다. 하지만 내부에서 if 분기문이 늘어난다.)

어느 곳에 두어도 나름의 타당한 이유가 있었다. 하지만 동시에, 어느 곳에 두어도 무언가 하나씩 불편하고 어색한 느낌을 지울 수 없었다. 새로운 메서드를 추가할 때 대체 어떤 객체에 두는 게 맞는지, "이 행위는 누구의 책임인가"를 판단하는 기준이 매번 달라지는 것 같아 혼란스러웠다 .

이 답답함을 PR에 남겼을 때, 리뷰어님은 설계의 방향을 잡아주는 명쾌한 피드백을 주셨다.

> "절대적인 기준은 없습니다... 1. 어떤 요구사항이 변경되었을 때 영향 범위를 최소화할 것이고, 어떤 변경은 전면 수정을 각오할 것인가? 2. 어디에 넣어도 어색하면 그건 새로운 객체를 만들라는 신호다. ... 매번 답이 달라지는 게 정상이고, 오히려 항상 같은 규칙으로 결정하고 있다면 그게 더 의심스러운 겁니다."

덧붙여 "세 선택지 모두 어색하게 느껴졌다면 그 감각이 맞습니다"라는 말씀이 인상적이였다. 나는 내가 이미 만들어둔 객체들(GameResult, Money, GameResults) 안에서만 억지로 정답을 찾으려 하고 있었다. 수익을 계산하는 행위가 기존 객체들의 본질과 어울리지 않아 어색했다면, '수익 계산'이라는 책임을 온전히 감당할 새로운 도메인을 도출해 내는 것이 객체지향적인 해결책이었다.

결국 나는 GameResults와 GameResult 주변을 맴돌던 수익 계산 로직을 덜어내어, ProfitCalculator라는 독립적인 객체로 책임을 분리해 냈다.

```
// blackjack.domain.profit.ProfitCalculator
public class ProfitCalculator {

    public ProfitResults calculate(GameResults gameResults, Wagers wagers) {
        Map playerProfits = new LinkedHashMap<>();

        // 1. 플레이어들의 수익 계산 (게임 결과와 베팅 금액을 조합)
        for (Player player : gameResults.getPlayers()) {
            GameResult result = gameResults.getResultOf(player);
            Money wager = wagers.getWagerOf(player);

            playerProfits.put(player, result.profitOf(wager));
        }

        // 2. 딜러의 수익 계산 (플레이어들 수익의 반대)
        Money dealerProfit = calculateDealerProfit(playerProfits.values());

        return new ProfitResults(playerProfits, dealerProfit);
    }

    private Money calculateDealerProfit(Collection playerProfits) {
        // 플레이어들이 딴 돈만큼 딜러는 잃고, 잃은 만큼 얻는다
        int totalPlayerProfit = playerProfits.stream()
        .mapToInt(Money::value)
        .sum();
        return new Money(-totalPlayerProfit);
    }
}
```

이렇게 ProfitCalculator를 도입하니 기존 객체들이 객체들의 책임에 더 집중할 수 있게 되었다.

GameResults는 순수하게 '게임의 승패 결과'만 관리하면 되었고, Wagers는 '베팅 금액'만 관리하면 되었다. 그리고 두 객체의 정보를 조합하여 '최종 수익'을 계산하는 복잡한 비즈니스 로직은 오롯이 ProfitCalculator가 책임지게 되었다.

### 6. 설계와 구현의 적절한 균형점

사이클 2를 시작하면서, 이번에는 다이어그램도 그려보고 완벽한 설계를 마친 뒤에 코딩을 시작하리라 마음먹었다. 블랙잭 승리 시 1.5배의 수익을 지급하라는 요구사항을 마주했을 때, 머릿속으로 아래와 같이 구현할 것들을 미리 정리했다 .

```
// 구현 전 머릿속 정리
- GameResult가 블랙잭인지도 알아야 한다.
- 플레이어의 경우 카드 2개로 블랙잭인지 아닌지도 알아야 한다.
- Player에게 카드 2개이면서(&&) 점수가 21인지 확인하는 메서드가 필요하다.
- 플레이어는 1.5배이지만, 딜러는 1.5배가 아니다.
- 그럼 분기 처리를 GameResults 안에서 해야겠네.
- 만약 딜러가 21을 넘어서 버스트될 경우, 남아있는 플레이어들의 수익 계산은 어떻게 처리하지?
```

나름대로 논리적인 흐름을 세웠다고 생각했다. 하지만 실제로 코드를 짜보기 시작하자, 예상과 전혀 다른 문제들이 사방에서 튀어나왔다 .

- isBlackjack() 메서드를 Hand 객체에 두어야 할지, Participant에 두어야 할지 설계도만으로는 판단이 서지 않았다.
- GameResults.create 내부의 if-else 분기 순서를 잘못 짜는 바람에 결과가 덮어씌워지는 버그가 발생했다.
- 앞서 언급했던 가변 Money 객체의 참조 공유 문제가 터지면서 수익 계산 로직이 통째로 흔들렸다.
- 'else 예약어 금지' 규칙을 지키려다 보니 내가 생각했던 제어 흐름을 처음부터 다시 고민해야 했다.

완벽한 설계라고 믿었던 것들은 실제 객체들이 협력하는 과정에서 쉽게 무너졌다. 그렇다고 코드를 먼저 짜는 방식이 정답인 것도 아니었다. 일단 돌아가게만 만들어 놓으면, "작동하니까 나중에 고치자"며 리팩터링을 미루게 되는 유혹에 빠지기 쉬웠기 때문이다.

도대체 설계와 구현 사이의 적절한 균형점은 어디일까? PR에 남긴 이 막막한 질문에 리뷰어님은 이렇게 답변해 주셨다 .

> "간단합니다. 그 중간을 해야 합니다. 설계를 아예 안 하고 접근하면 중구난방인 코드가 작성되기 쉽고, 설계를 완벽하게 한다고 하면 시간도 오래 걸리고, 결국 프로그램의 복잡도가 어느 수준 이상으로 넘어가면 완벽한 초기 설계는 가능하지 않습니다."

설계를 완벽하게 마쳐야 코딩을 시작할 수 있다"는 나의 생각은 사실 불가능에 수렴한다는 것으로 받아들여졌다. 요구사항은 언제든 변하고, 기획은 수정되며, 복잡도는 팽창한다. 따라서 큰 그림과 핵심 도메인의 역할 정도만 스케치한 뒤, 작은 단위로 테스트를 작성하고 코드를 짜면서 점진적으로 개선해 나가는 것이 유연함이 필요하다는 것을 배웠다.

### 7. 두 번째 리팩터링

1차 리뷰에서 내가 던졌던 무거운 질문들에 대해 리뷰어님은 나름 명쾌한 해답과 힌트를 주셨다. 사실 리뷰 자체에서 아키텍처를 크게 뒤엎으라는 식의 강한 수정 요청은 없었다. 사소한 버그나 놓쳤던 예외 처리 등 부분적인 수정 요청이 주를 이루었다.

하지만 그 자잘한 수정들을 반영하기 위해 전체 코드를 다시 찬찬히 훑어보던 중, 리뷰어님이 굳이 지적하지 않았음에도 내 눈에 심하게 거슬리는 구조적인 문제들이 보이기 시작했다. 코드가 돌아가게 만들고 책임을 어느 정도 분리하고 나니, 그제서야 시스템 전체의 큰 그림에서 발생하는 아키텍처의 '냄새'를 맡게 된 것이다.

#### 첫째, 컨트롤러가 너무 비대해졌다.

앞선 고민에서 베팅 수집 책임을 Players 일급 컬렉션에서 컨트롤러로 옮긴 것은 올바른 방향이었다. 하지만 그 대가로 컨트롤러는 너무 많은 것을 알게 되었다. 흐름 제어, 입출력 호출, 협력 도메인 연결 및 계산, 심지어 View에 넘겨줄 DTO 변환까지 모두 컨트롤러의 몫이 되어버렸다 .

이 비대한 컨트롤러를 줄이기 위해, 도메인들의 협력을 캡슐화하는 파사드(Facade) 객체인 BlackjackGame을 도입했다. 컨트롤러는 전체 흐름 제어와 View와의 소통만 담당하고, 복잡한 비즈니스 로직은 BlackjackGame 내부로 숨겼다 .

하지만 완벽한 해결책은 아니었다. BlackjackGame이 GameResults를 인스턴스 변수로 상태처럼 들고 있게 되면, 게임이 아직 끝나지 않은 중간 시점에도 '결과'가 존재하는 어색한 도메인 상태가 만들어질 수 있다고 판단했다 . 결국 상태를 저장하지 않고 매번 생성하는 방식을 택했는데, 이로 인해 수익 계산을 할 때와 결과를 출력할 때 GameResults.create()가 두 번 중복 호출되는 비효율적인 구조를 감수해야 했다.

#### 둘째, View가 도메인을 너무 깊이 알고 있다.

초기 코드에서는 OutputView가 Player, Dealer, GameResults 같은 도메인 객체를 파라미터로 직접 넘겨받아 출력했다. 처음에는 객체를 그대로 넘기는 것이 편하다고 생각했지만, 도메인이 바뀌거나 추가될 때마다 문제들이 발생했다.

예를 들어 Player 객체가 카드를 관리하는 내부 자료구조를 변경하거나, 수익을 반환하는 메서드의 이름이 조금만 바뀌어도 비즈니스 로직과는 전혀 상관없는 화면 출력 클래스(OutputView)까지 함께 고쳐야하는 문제가 생겼다. 뷰에서는 도메인의 각 값을 getter로 들고와서 사용할 수 밖에 없는데, 도메인의 사소한 변경 여파에도 수정 범위가 외부로 퍼져나가는 모습이라고 할 수 있다.

이를 해결하기 위해 계층 간 데이터를 전달하는 순수 데이터 객체, DTO(Data Transfer Object)를 도입했다. 정적 팩토리 메서드를 통해서 도메인을 매개변수로 전달받아 DTO로 변환할 수 있도록 했고, 이를 통해서 뷰에서 필요한 값이 변하는 변경사항이 발생거나 도메인이 바뀌더라도 DTO 내부에서만의 변경 범위를 제한할 수 있었다. 또한 OutputView는 도메인을 전혀 모른 채 순수하게 출력 책임만 갖게 만들었다.

하지만 여기서도 예상치 못한 요구사항의 벽에 부딪혔다. '딜러의 수익을 먼저 출력하고, 플레이어들의 수익을 나중에 출력해야 한다'는 제약 때문이었다. 이 순서를 맞추기 위해 DealerProfitDto와 PlayerProfitsDto를 분리하다 보니, 하나의 BlackjackGame 객체에서 수익 결과를 뽑아내는 메서드를 또다시 두 번 호출하는 구조가 되어버렸다.

이부분에 대해서 다음과 같이 피드백을 주셨는데 추후에 수정을 해봐야할꺼 같다.

> 이 부분은 적용한 아키택처나 구조가 가지는 특징이 아니라, 적용하면서 약간 잘못된게 있는걸로 보는게 맞습니다. DTO 자체의 설계나 BlackjackGame 에서 쓰는 객체들의 상호작용을 다듬으면 문제가 없어질걸로 보입니다.

#### 셋째, 도메인을 쪼개는 것이 항상 맞을까?

Players나 GameResults 같은 일급 컬렉션을 도입했을 때, 그 장점은 명확했다. 객체 내부 데이터에 대한 검증, 반복문을 통한 순회, 그리고 다른 협력 객체의 도움을 받아 계산하는 등의 행위가 자연스럽게 일급 컬렉션 내부로 캡슐화되는 것을 체감했다. 이 경험을 바탕으로, 베팅 요구사항이 추가되었을 때도 Wager와 Wagers를 별도의 도메인으로 분리하며 동일한 패턴을 적용했다. 나아가 수익 계산을 전담하는 ProfitCalculator, 결과를 담는 ProfitResults, 금액을 표현하는 Money 객체까지 책임을 나누어 분리했다.

각 객체가 단일 책임을 가지며 개별적인 응집도는 높아졌지만, 전체 구조를 파악하기 위해 인텔리제이(IntelliJ)에서 클래스 다이어그램을 추출해 보았을 때 조금 불편함을 느꼈다. 화면에는 핵심 도메인뿐만 아니라 협력을 돕는 중간 도메인, 일급 컬렉션, 데이터 전달을 위한 DTO 등 수많은 클래스들이 나타났다. 이 수많은 도메인들이 서로 주고받는 연관 관계와 의존 관계(화살표)가 복잡하게 얽혀 있어, 시스템의 전체 흐름을 한눈에 파악하기가 어려워진 상태라고 느껴졌다.

여기서 설계에 대한 근본적인 의문이 들었다. 도메인을 분리하고 객체를 쪼개는 것이 개별 클래스의 설계 복잡도를 낮추는 것은 맞다. 하지만 반대로, 파악해야 할 객체의 절대적인 수가 늘어나면서 시스템 전체의 복잡도를 높이는 결과를 낳았다. 객체를 잘게 부수어 분리하는 것만이 항상 능사인지, 아니면 전체 복잡도 관점에서 적절한 크기로 객체를 유지하는 선이 존재하는지 아직 명확한 판단 기준을 세우지 못했다.

판단 기준은 여전히 모호하지만, 이 과정 자체가 무의미하지는 않았다. 다이어그램 상에 나타난 객체 간의 화살표(의존성) 방향과 개수를 시각적으로 확인하면서, 각 도메인이 적절한 객체를 의존하고 있는지 점검하고 도메인의 역할과 책임을 객관적으로 다시 생각해 볼 수 있는 시간이었다.

#### 넷째, 도메인 추출 시 무너지는 테스트 코드

책임을 분리하기 위해 GameResults에 있던 수익 계산 로직을 ProfitCalculator라는 새로운 도메인으로 추출했다. 하지만 도메인 구조를 개선하자마자 기존에 작성해 두었던 수많은 테스트 코드가 일제히 컴파일 에러와 실패를 발생시켰다.

원인은 테스트 코드 내부에 파편화된 객체 생성 로직에 있었다. 기존에는 각 테스트 메서드 내부에서 new GameResults(...), new Player(...) 등을 직접 호출하여 상태를 세팅했다. 수익 계산 책임을 분리하면서 관련 객체들의 생성자 시그니처가 바뀌고 새로운 의존성(Wagers 등)이 추가되자, 이 객체들을 직접 생성하고 있던 수십 개의 테스트 코드를 일일이 찾아다니며 수정해야만 했다.

리팩터링을 안전하게 진행하기 위해 작성했던 테스트 코드가, 정작 도메인 구조를 변경하려 할 때는 도리어 수정을 방해하는 무거운 짐이 되어버린 것이다.

이 과정을 통해 테스트 코드 역시 프로덕션 코드와 마찬가지로 유지보수의 대상이라는 점을 체감했다. 테스트 코드가 리팩터링의 진정한 지원군 역할을 하려면, 테스트용 객체의 생성 지점을 단일화하는 픽스처(Fixture)나 팩토리 메서드를 도입하여 프로덕션 코드의 생성자 변경에 따른 테스트 코드의 결합도를 낮춰야 한다는 실질적인 교훈을 얻을 수 있었다.

## 마치며: 완벽한 정답 대신 나만의 기준을 세워가는 과정

수많은 고민을 안고 제출한 마지막 PR에, 리뷰어님은 "첫 술에 배부르랴?"라는 코멘트를 남겨주셨다. 이번 미션 하나만으로 객체지향의 모든 기준을 완벽하게 세우려 한다면 오히려 그것이 더 문제가 될 것이라는 조언이었다.

생각해 보면 나는 이번 미션 내내 책임을 나눌 '단 하나의 완벽한 정답'을 찾으려 했다. 하지만 도메인 분리에 따른 복잡도 증가나 패키지 결합 문제에 대해 리뷰어님은 "실무에서도 매번 하는 고민이며 정답이 없다. 프로젝트의 성격이나 상황에 따라 다를 수 있다"는 현실적인 시각을 제시해 주셨다.

책임을 어디에 두어야 하는가? 도메인은 어디까지 쪼개야 하는가? 솔직히 말해 이 질문들에 대한 완벽한 해답은 아직 내리지 못했다. 다음 미션에서도 분명 비슷한 문제로 고민하게 될 것이다.

하지만 중요한 것은 완벽한 설계란 존재하지 않으며, 모든 기술적 결정에는 득과 실(Trade-off)이 따른다는 사실을 배웠다는 점이다. 좋은 설계란 누군가 정해준 정답을 맞히는 것이 아니라, 현재의 요구사항과 제약 조건 속에서 타당한 근거를 바탕으로 최선의 구조를 선택하고 조율해 나가는 과정 그 자체라는 것을 배웠다.
