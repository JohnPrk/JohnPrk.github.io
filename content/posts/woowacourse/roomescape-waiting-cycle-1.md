사이클1의 요구사항은 이미 예약된 슬롯에 대기를 신청하고, 본인의 예약과 대기를 함께 관리하는 예약 대기 기능이었다. 직전 방탈출 사용자 예약 미션까지는 한 슬롯, 그러니까 날짜와 시간과 테마가 정해진 한 자리에 한 명만 예약할 수 있었고, 이미 예약된 슬롯은 사용자에게 아예 보이지 않았다. 이번 사이클부터는 이미 찬 슬롯에도 대기를 걸 수 있고, 신청한 순서대로 순번이 매겨진다. 같은 사람이 같은 슬롯에 중복으로 대기할 수는 없고, 본인 대기는 직접 취소할 수 있다. 내 예약 목록을 열면 예약과 대기가 상태로 구분되어 함께 보이고, 대기에는 내 순번도 같이 나온다.

그런데 미션 명세가 맨 앞에 박아 둔 목표는 기능 자체가 아니었다.

> 단순히 예약 대기 기능을 만드는 것이 아니라, "이걸 어떻게 테스트할 것인가"의 판단 근거를 가지는 것이 핵심이다.

명세는 기능 목록 옆에 테스트 이야기를 같이 붙여 뒀다. 토론에서 정한 테스트 전략을 코드에 적용하고, 테스트를 어디에 어떻게 둘지 정할 때마다 "왜 이 방식으로 테스트했는가"를 PR 본문에 한두 줄로 남기라고 했다. 그러니까 이 사이클의 초점은 대기 기능이 도는지가 아니라, 테스트를 어디에 둘지 내가 내린 판단에 근거가 있느냐에 있었다.

이번에는 준비를 해서 들어갔다. 페어와 코드를 합치기 전에, 내가 지키려는 철칙 여덟 개와 예약 생성 흐름을 그린 시퀀스 다이어그램을 미리 만들어 갔다. 미션이 끝나고 보니 그 준비물이 이 회고의 출발점이 됐다. 들고 간 철칙 중 어떤 것은 미션을 거치며 더 분명해졌고, 어떤 것은 내가 제대로 알지도 못하면서 안다고 여겼다는 게 드러났기 때문이다.

### 들고 들어간 것

미션은 페어와 함께 시작했다. 페어인 밀란과 코드를 어떻게 합칠지 고민이 됐다. 서로의 코드 철학을 공유해서 중간에서 합의하면, 시작 코드가 누구 것이든 나중 코드는 상관없겠다고 생각했다. 그래서 나는 아예 준비를 해서 갔다. 내가 지키려는 철칙 여덟 개를 글로 정리하고, 예약 생성 흐름을 시퀀스 다이어그램으로 그렸다. 막상 맞춰 보니 밀란은 정해 둔 철학이 많지 않아서, 결국 내 코드를 시작점으로 진행했다.

철칙 여덟 개에는 테스트에 관한 것도 있었다. 다만 그게 정확히 무슨 뜻인지 또렷해진 건 미션이 거의 끝나갈 무렵이었고, 처음부터 알고 있던 건 아니었다. 들어갈 때의 나는 그냥 "E2E를 가장 믿는다" 정도를 적어 둔 상태였다.

처음부터 의심 없이 들고 있던 쪽은 오히려 설계 철칙이었다. 그중 하나가 "여러 곳을 거쳐야 하는 일은 조율 전용 자리가 책임진다"였다. 예약 하나를 만들려면 시간, 테마, 매장, 예약을 다 거쳐야 하는데, 이 흐름을 컨트롤러나 한 서비스에 몰아넣지 않고 조율만 하는 자리를 따로 둔다는 생각이었다. 나는 그 자리를 Facade라고 부르고 있었고, 다이어그램에서도 ReservationFacade를 한가운데에 그렸다. 이 철칙은 미션 전까지 의심해 본 적이 없었다.

### 정한 것과, 못 정한 것

코드를 짜면서 정한 것 중 먼저 공유하고 싶었던 건 데이터 모델이었다. 예약 대기를 어디에 둘지 두 갈래를 두고 고민했다. 예약 테이블에 다 넣고 순번 컬럼으로 확정과 대기를 구분하는 방법과, 대기를 별도 테이블로 빼고 예약을 FK로 가리키는 방법이었다. 나는 별도 테이블 쪽을 골랐다. 슬롯 정보를 예약 한 곳에만 두면 "대기는 확정된 슬롯에만 붙는다"는 규칙이 FK 한 줄로 강제되고, 예약과 대기의 생명주기가 다르다고 봤기 때문이다.

순번도 비슷하게 두 갈래였다. 대기마다 순번 컬럼을 두고 저장 시점에 채우는 방법은, 앞 순번이 빠질 때 뒤를 다 갱신해야 하는 일이 새로 생겼다. 그래서 컬럼 없이 신청 시각을 기준으로 매 조회 때 SQL로 순번을 세는 쪽을 골랐다. 그런데 막상 구현해 보니, 저장 직후 돌려주는 순번과 이후 조회의 순번이 서로 다른 기준으로 계산되고 있었다. 같은 시각에 두 건이 들어오면 둘이 어긋날 수 있는 구조였다. 이건 내가 깔끔하게 닫지 못해서 질문으로 남겼다.

테스트는 토론에서 정한 기준을 그대로 코드에 옮겼다.

- 도메인은 순수 단위 테스트
- 서비스는 Mockito
- 리포지토리는 실제 SQL이 도는 @JdbcTest
- API는 서버를 띄우는 @SpringBootTest와 RestAssured

그리고 컨트롤러와 인터셉터, 핸들러는 단위 테스트를 일부러 생략했다. 그 이유도 PR에 적어 뒀다. 받아서 넘기는 일만 하는 코드에 단위 테스트를 붙이면 사실상 프레임워크 동작을 검증하게 되고, 거기서 깨질 만한 결함은 E2E가 같은 경로에서 같이 잡는다고 봤다. 같은 분기를 두 레벨에서 중복으로 잡지 않는다는 게 토론에서 정한 규칙이었다.

마지막으로 동시성을 질문으로 남겼다. 같은 슬롯에 두 사람이 동시에 대기를 신청하면 중복으로 들어가거나 같은 순번을 받을 수 있는데, 그때 코드는 둘 다 막지 않고 있었다. 이걸 DB 제약으로 풀지, 애플리케이션 락으로 풀지, 아니면 이번 사이클에선 다루지 않아도 되는 범위인지 의견을 듣고 싶었다. 설계 자체에는 자신이 있었지만, 닫지 못한 질문 두 개를 일부러 열어 둔 채로 리뷰를 기다렸다.

### Facade가 아니었다

리뷰어는 처음부터 이 클래스를 그냥 넘어가지 않았다. 1차 리뷰에서는 검증을 도메인으로 옮길 수 있지 않냐고 물었고, 나는 옮길 수 있는 검증을 도메인 생성자로 넣었다. 그런데 2차 리뷰에서 질문이 더 정면으로 들어왔다.

> 그리고 Facade를 둔 이유가 궁금합니다~ 티뉴가 생각하시는 Facade는 무엇이고 서비스랑 무엇이 다른가요? 그리고 왜 사용했나요?

비슷한 질문이 리뷰마다 돌아왔다. 그쯤 되니 이건 코드가 스스로를 설명하지 못한다는 신호로 보였다. 솔직히 나는 Facade의 정확한 정의를 모르면서 안다고 여기고 있었다. 여러 도메인을 한자리에서 묶는다는 느낌만으로 이름을 Facade라고 붙여 두고 있었다.

정의를 다시 찾아보고 나서야 이게 Facade가 아니라는 걸 알았다. Facade는 안쪽으로 전달만 하는 패턴인데, 내 클래스는 트랜잭션 경계를 쥐고 지난 시각과 충돌을 검증하며 규칙을 강제하고 있었다. 이 층에 더 맞는 이름은 Application Service였다. 정의를 하나씩 따라가 본 과정은 [따로 글로 정리해 뒀다](https://johnprk.github.io/spring/facade-vs-application-service/).

그래서 로직은 그대로 두고 이름만 코드에 맞췄다. ReservationFacade를 ReservationApplicationService로 바꾸고, 패키지도 facade에서 application으로 옮겼다. 행동이 그대로라 전체 테스트는 변경 없이 통과했다.

바꾼 건 이름 한 줄이지만, 그 순간에는 내가 믿고 있던 게 통째로 무너지는 느낌이었다. 미션 전까지 의심 없이 들고 있던 철칙이, 사실은 내가 뜻도 정확히 모르는 단어에 기대고 있었기 때문이다. 적어 간 철칙 중에는 "몰라서 틀린 것과 알고 타협한 것은 다르다"는 게 있었는데, Facade는 알고 타협한 게 아니라 모르면서 안다고 믿은 쪽이었다.

### 순번은 신청이 가진 값이 아니었다

②에서 열어 둔 질문 중 하나가 순번이었다. 순번 컬럼을 따로 두지 않고 신청 시각을 기준으로 매 조회 때 세는 쪽을 골랐는데, 막상 짜 보니 저장 직후 돌려주는 순번과 이후 조회의 순번이 서로 다른 기준으로 계산되고 있었다. 같은 시각에 두 건이 들어오면 둘이 어긋날 수 있다는 걸 알면서도 깔끔하게 닫지 못한 채 질문으로 남겨 두고 리뷰를 기다렸다.

리뷰어는 이 부분을 두 갈래로 짚었다. 먼저 순번을 매기는 규칙이 한 군데에만 있어야 한다고 했다.

> 순번을 매기는 규칙은 한 군데에만 있어야 깨지지 않을 것 같아요. save 직후에도 같은 서브쿼리로 다시 조회해서 채우면 알고리즘이 자연스럽게 하나로 모이지 않을까요?

내가 남긴 질문에 대한 답이기도 했다. 저장 경로에서 따로 세던 계산을 지우고, 저장 직후에도 조회와 똑같은 서브쿼리를 한 번 더 타게 했다. 한 번 저장할 때 조회가 한 번 더 붙지만, 두 경로가 같은 SQL을 지나니 순번이 한 가지로만 정해졌다.

다른 한 갈래가 더 묵직했다.

> 아직 순번이 정해지지 않은 상태를 0으로 표현하고 계신데요, 0이 '순번 없음'인지 '0번'인지 읽는 사람이 헷갈릴 수 있을 것 같아요 😿 순번은 저장 시점에 DB가 계산해주는 값이니, 신청 단계의 도메인이 order를 아예 안 가지는 게 더 정직하지 않을까요?

맞는 말이었다. 신청을 만드는 시점에는 순번을 아직 모르니, 나는 생성자에서 order를 일단 0으로 채워 두고 있었다.

```java
// before: 신청 시점에 순번을 0으로 채워서 만들었다
public class ReservationWaiting {
    private final Long id;
    private final String name;
    private final LocalDateTime createdAt;
    private final Reservation reservation;
    private final int order;

    public ReservationWaiting(String name, LocalDateTime createdAt, Reservation reservation) {
        this(null, name, createdAt, reservation, 0); // 0이 '순번 없음'인지 '0번'인지 알 수 없다
    }

    public int getOrder() {
        return order;
    }
    // ...
}
```

그 0은 '아직 순번이 없다'는 뜻으로 넣은 거였는데, 코드만 보면 '0번'으로도 읽혔다. 게다가 순번은 저장 시점에 DB가 다른 신청들과 견줘서 매기는 값이라, 신청 객체 하나가 혼자 들고 있을 수 있는 값이 아니었다. 신청이 항상 지키는 성질도 아닌 값을 신청 도메인 안에 박아 둔 셈이었다.

그래서 order 필드를 ReservationWaiting에서 들어냈다. 순번이 매겨진 조회 결과는 WaitingWithOrder라는 읽기 전용 모델로 따로 분리했다.

```java
// after: ReservationWaiting은 순번을 모른다
public class ReservationWaiting {
    private final Long id;
    private final String name;
    private final LocalDateTime createdAt;
    private final Reservation reservation; // order 필드 없음

    public ReservationWaiting(String name, LocalDateTime createdAt, Reservation reservation) {
        this(null, name, createdAt, reservation);
    }
    // getOrder() 도 함께 사라졌다
}

// 순번은 조회 결과를 감싼 이 읽기 모델에만 있다
public class WaitingWithOrder {
    private final ReservationWaiting waiting;
    private final int order;

    public WaitingWithOrder(ReservationWaiting waiting, int order) {
        this.waiting = waiting;
        this.order = order;
    }
    // getWaiting(), getOrder()
}
```

이제 ReservationWaiting은 "누가, 언제, 어떤 예약에 신청했는가"만 안다. 순번은 조회할 때 DB가 세어 주는 값이고, 그게 필요한 자리에서만 WaitingWithOrder가 들고 다닌다. 저장과 조회가 같은 SQL을 지나게 한 앞의 수정과 합쳐서, 순번은 한 곳에서만 정해지고 신청 도메인은 자기가 모르는 값을 더는 들고 있지 않게 됐다.

이건 파사드만큼 크게 흔들린 일은 아니었다. order를 0으로 채워 둔 게 어딘가 어색하다는 건 짜면서도 어렴풋이 느끼고 있었고, 그래서 질문으로도 남겨 둔 자리였다. 리뷰어의 지적은 그 어색함이 어디서 오는지, 신청이 자기가 모르는 값을 들고 있다는 걸 정확한 말로 바꿔 줬다.

### 중복은 선검증과 제약으로 나눠 막았다

②에서 함께 열어 둔 다른 질문은 동시성이었다. 같은 슬롯에 두 사람이 동시에 신청하면 중복이나 같은 순번이 생길 수 있는데, 코드가 그걸 막지 못하는 상태였다. 나는 이게 이번 사이클에서 다뤄야 할 범위인지부터 확신이 없었다.

리뷰어는 범위 밖으로 미루기보다 한 번 고려해 보자고 했다. 애플리케이션 락보다 DB unique 제약을 먼저 떠올릴 것 같다고, 최소한 중복으로 들어가는 것만큼은 막아 두는 선을 권했다. 그래서 reservation_waiting 테이블에 (name, reservation_id) 조합을 unique로 묶었다. 한 사람이 같은 예약에 두 번 대기할 수 없다는 규칙을 DB가 직접 보장하게 한 것이다. 제약을 어기면 터지는 DuplicateKeyException은 핸들러에서 409로 매핑했다. 그 예외가 어디서 어떻게 만들어지는지 따라가 본 내용은 [따로 정리해 뒀다](https://johnprk.github.io/spring/duplicate-key-exception-translation/).

그러자 리뷰어가 한 번 더 물었다. 이미 신청 전에 existBy로 중복을 검사하는데 unique 제약까지 두면, 둘 중 하나는 굳이 필요하지 않냐고 했다. 정합성만 보면 맞는 말이라, 나는 선검증을 지우는 대신 둘의 역할을 나눴다. existBy 선검증은 '이미 대기 중인 예약입니다' 같은 친절한 메시지를 주려고, 정상 흐름에서 흔한 중복(이미 대기 중이거나 버튼을 두 번 누른 경우)을 거르는 자리다. unique 제약은 그 선검증을 빠져나가 거의 동시에 들어오는 신청을 막는 마지막 자리다. 흔한 거부는 선검증으로, 드문 경합은 제약으로 나눠 두는 게 낫다고 봤다.

이 질문은 끝까지 깔끔하게 닫지 못했고, 그건 리뷰어도 마찬가지였다. 승인하면서 리뷰어가 남긴 의견은 정답이 정해진 문제는 아니라는 거였다. 프론트에서 중복 요청 자체를 막을 수 있으면 unique 제약만 두고, 그게 안 되면 선검증으로 의도한 예외를 내는 쪽을 택하겠다고 했다. 내가 닫지 못하고 남긴 자리를 리뷰어도 '상황에 따라 다르다'로 받아 준 셈이라, 이건 틀려서 고친 게 아니라 기준을 같이 정리한 자리로 남았다.

### 작게 고친 것들

나머지는 비교적 작은 지적이었지만, 그중 하나는 좀 뜨끔했다. 한 리포지토리에는 구현 메서드마다 @Override가 붙어 있는데 다른 리포지토리에는 하나도 없다는 지적이었다. @Override가 없어도 컴파일이 되니, 나는 당연히 다 붙어 있다고 생각하고 누락된 줄 전혀 모르고 있었다. @Override가 있어야 인터페이스 시그니처가 바뀌었을 때 컴파일러가 구현이 어긋난 걸 잡아 준다는 것도 이때 분명히 알았다. 빠진 곳에 전부 붙여서 통일했다.

내 예약 목록 조회는 형식만 페이징이었다. 응답 모양을 관리자 조회와 맞추려고 totalCount와 page를 채워 넣었는데, 정작 조회는 이름으로 전체를 한 번에 가져와 메모리에 올리고 있었다. 한 사람의 예약이 쌓이면 그대로 다 퍼 올리는 구조였다. 조회 자체를 offset과 limit을 받는 진짜 페이징으로 바꾸고, 전체 개수는 따로 세도록 고쳤다.

'찾을 수 없습니다' 메시지는 도메인마다 따로 상수로 들고 있었다. 비슷한 문구가 여러 곳에 흩어져 있었고, 그게 중복이라는 걸 의식하지 못하고 있었다. 메시지를 NotFoundException의 정적 팩터리 한 곳으로 모으고 'ID %d번 %s 정보를 찾을 수 없습니다'라는 하나의 템플릿으로 통일했다. 고치다 보니 대기를 못 찾았는데 '예약을 찾을 수 없습니다'로 잘못 나가던 것도 같이 바로잡았다.

### 트랜잭션이 도는 건 알지만, 어떻게 도는지는 몰랐다

리뷰어가 ReservationApplicationService에서 물은 건 이름만이 아니었다. 같은 클래스의 트랜잭션도 짚었다.

> 클래스 단위로 @Transactional를 작성하면 어떨까요?

그때 내 코드는 쓰기 메서드마다 @Transactional을 하나씩 붙여 둔 상태였다. 예약을 추가하거나 대기를 신청하는 메서드에는 @Transactional이 있었지만, 조회 메서드에는 아무것도 없었다. 그래서 조회는 트랜잭션 경계 밖에서 돌고 있었고, 나는 클래스 레벨에 기본값을 두는 선택지가 있다는 것 자체를 생각하지 못하고 있었다.

```java
// before: 쓰기 메서드마다 @Transactional을 직접 붙였고, 조회엔 아무것도 없었다
@Service
public class ReservationApplicationService {

    @Transactional
    public WaitingWithOrder addWaiting(ReservationWaitingRequest request) { ... }

    public List<TimeWithStatusResponse> getTimesWithAvailability(LocalDate date, Long themeId) { ... } // 트랜잭션 경계 밖
}
```

리뷰어 말대로 클래스에 @Transactional(readOnly = true)를 기본으로 걸고, 쓰기 메서드에만 @Transactional을 다시 붙여 기본값을 덮었다. 이제 따로 표시하지 않은 조회 메서드는 클래스의 readOnly 트랜잭션 안에서 돈다.

```java
// after: 클래스에 readOnly 기본값, 쓰기만 메서드에서 다시 지정
@Service
@Transactional(readOnly = true)
public class ReservationApplicationService {

    @Transactional
    public WaitingWithOrder addWaiting(ReservationWaitingRequest request) { ... }

    public List<TimeWithStatusResponse> getTimesWithAvailability(LocalDate date, Long themeId) { ... } // 클래스 기본값 적용
}
```

여기까지는 리뷰어가 짚어 준 대로 고쳤고, 코드만 보면 정리가 됐다. 문제는 그다음이었다. 왜 클래스에 붙인 어노테이션이 따로 표시하지 않은 메서드까지 적용되는지, readOnly가 정확히 무엇을 바꾸는지 알고 싶어서 따라가 봤는데, 파고들수록 끝이 없었다. 스프링이 프록시로 메서드 호출을 감싸서 트랜잭션을 연다는 데까지는 갔지만, 거기서부터는 내가 이해했다고 말할 수 있는 수준이 아니었다.

솔직히 말하면, 나는 트랜잭션이 도는 건 알지만 그게 어떻게 도는지는 몰랐다. @Transactional을 붙이면 한 단위로 함께 커밋되고 함께 롤백된다는 결과는 알고 썼지만, 스프링이 그걸 어떤 방식으로 만들어 내는지는 표면만 알고 있었다. 리뷰에 답은 적을 수 있었는데, 적으면서도 이건 외워서 적는 거지 이해해서 적는 게 아니라는 느낌이 들었다.

그래서 이 부분은 적용만 하고 멈췄다. 더 파고들려다 너무 깊어서 끝을 못 봤고, 표면적으로만 안 채로 넘어갔다. 트랜잭션과 readOnly를 따라가 본 일부는 [따로 글로 정리해 뒀다](https://johnprk.github.io/spring/spring-transactional-readonly/). 그 글을 쓰고도 여전히 다 안다고는 못 하겠다.

### 한 줄이던 테스트 기준이 자리를 잡았다

미션에 들어갈 때 테스트에 관해 또렷하게 적어 둔 건 "E2E를 가장 믿는다" 한 줄 정도였다. ②에서 토론에서 정한 4계층 기준을 코드에 옮겼다고 했지만, 그 기준이 왜 그렇게 갈리는지 내 기준으로 납득된 건 코드를 짤 때가 아니라 미션을 지나면서였다. 리뷰가 짚어 준 자리들이 그 납득을 거들었다.

리뷰가 짚은 것 중 하나는 테스트 한 개가 두 가지를 한꺼번에 보고 있던 자리였다. 대기 조회 테스트가 '본인 것만 골라온다'와 '순번을 맞게 센다'를 한 번에 확인하고 있었는데, 정작 메서드 이름은 순번 계산이라고만 돼 있었다.

> 이 테스트가 '내 것만 골라온다'와 '순번을 맞게 계산한다' 두 가지를 한 번에 보고 있어요. 깨졌을 때 필터가 틀린 건지 순번이 틀린 건지 바로 안 보일 것 같아요.

맞는 지적이라 테스트를 둘로 나눴다. 하나는 본인 대기만 돌아오는지를 이름까지 확인하고, 다른 하나는 순번이 맞게 매겨지는지를 확인한다. 이렇게 나누니 테스트가 깨졌을 때 필터가 문제인지 순번이 문제인지 바로 보였다. 단위와 통합 테스트를 내가 짠 코드의 방어선이라고 본다면, 어디가 깨졌는지 바로 짚어 줄 때 그 방어선이 제 역할을 한다.

이 과정을 다 지나고 나서야, 처음엔 한 줄이던 "E2E를 믿는다"가 구체적인 기준으로 바뀌었다. 어느 레벨에 무엇을 둘지, 그리고 시간이 빠듯할 때 어디까지 양보할지가 같이 정해졌다. 안 바쁘면 디테일하게 검증하고, 진짜 바쁘면 E2E만 한다. 기능이 정상적으로 도는 게 제일 중요하기 때문이다. 단위와 통합은 내가 짠 코드가 나중의 수정이나 변경에 깨지지 않게 하는 방어선이라, 시간이 있을 때 함께 챙긴다. 그리고 내가 짜지 않은 것, 프레임워크나 라이브러리처럼 믿고 쓰는 건 테스트하지 않는다. 미션이 끝나고 가장 좋았던 건 이 기준을 스스로 세웠다는 점이었다.

### 마치며

이번 미션에서 제일 크게 남은 건, 테스트를 어디까지 해야 충분한지와 바쁠 때 무엇부터 양보할지에 대한 내 기준이 생겼다는 점이다.

또 하나 남은 건 파사드다. 미션에 들어갈 때 적어 간 철칙 여덟 개 중에는 "몰라서 틀린 것과 알고 타협한 것은 다르다"는 것도 있었다. 정작 그 철칙을 못 지킨 게 파사드였다. 트랜잭션이 어떻게 도는지 물었을 때 "아직 이해가 부족하다"고 적어 둔 건 모른다는 걸 알고 남긴 거였지만, 파사드는 안다고 착각한 거였다. 둘 다 정확히 알지는 못했는데, 한쪽은 모른다는 걸 알았고 한쪽은 몰랐다.

남은 숙제도 분명하다. 동시성은 선검증과 제약으로 당장 급한 부분만 막았고, 어디까지 막아야 하는지는 여전히 열려 있다. OFFSET이나 인덱스, 조회 성능은 답을 외워 둔 수준이라 더 봐야 한다. 여러 도메인을 가로지르는 규칙을 응용 서비스가 다 들고 있는 것도, 언젠가 갈라낼 자리라고 생각한다.

다음에 또 무언가를 안다고 적게 되면, 그게 정말 아는 것인지 한 번 더 의심해 보려고 한다.
