우테코 사이클은 사전학습, 토론, 페어 프로그래밍 순서로 진행됐다. 이번 미션은 지난 사이클에서 만든 방탈출 예약 관리(admin) 코드 위에 기능을 얹는 구조였다. 테마를 만들고, 사용자가 자기 이름으로 예약하고, 최근 일주일간 인기 있었던 테마를 보여주는 것. 기능 목록만 보면 어렵지 않아 보였다.

페어(와이제리)와 먼저 정한 건 누구의 admin 코드로 시작할지였다. 내 코드로 갔다. 다투거나 길게 조율한 기억은 없다. 그냥 그때 내가 더 많이 고민하고 있었고, 자연스럽게 그렇게 됐다. 지금 보면 고민의 양이 아니라 선택 기준의 문제였던 것 같다. 요구사항만 채우고 멈출지, 키워드를 더 파서 따져볼지. 내 코드엔 그 기준이 조금 더 있었다.

들어갈 때 정해둔 원칙이 하나 있었다. 개념을 일단 원저자의 의도대로 정확히 적용해보고, 프로젝트에 안 맞으면 그때 팀과 협의해서 바꾼다는 것이다. 과거에 명확한 레퍼런스 없이 주관적인 경험으로 의견이 갈리거나 컨벤션 기준이 모호해지는 걸 자주 봤기 때문이다. 명확한 기준이 있어야 나중에 타협해서 만든 규칙도 설득력을 가진다고 봤다.

그런데 이번 미션의 핵심은 기능이 아니었다. API 명세가 주어지지 않았다. URL과 HTTP 메서드, 요청과 응답의 형태를 직접 정하고, 왜 이렇게 설계했는지를 근거로 남기는 일이었다.

솔직히 여기서부터 막막했다. API라는 주제를 제대로 다뤄본 적이 없었다. 넥스트 스텝에서도 못 해본 주제였고, 당연히 있을 줄 알았던 로그인조차 없어서 사용자를 이름 하나로 식별해야 했다. 어디서부터 내 근거를 세워야 할지 감이 잘 안 왔다.

### 근거를 대고 물었다

PR을 올리면서 설계 의도와 질문을 함께 적었다. 막 짠 게 아니라, 결정마다 공식 문서나 원저자가 말한 의도를 근거로 두려고 했다.

가장 오래 붙들고 있던 건 Repository와 DAO를 둘 다 둔 부분이다. 도메인 주도 설계(DDD)를 정리한 에릭 에반스는 "Repository는 도메인 모델의 컬렉션처럼 동작한다"고 했다. 그 말을 그대로 따르면 DAO는 DB에 접근해 데이터를 꺼내는 역할만 하고, Repository는 그 데이터를 받아 완전한 도메인 객체로 조립하는 역할을 맡아야 할 것 같았다. 역할을 그렇게 나누는 게 원저자의 의도에 가깝다고 봤다.

막히는 건 그걸 실제 코드로 옮길 때였다. 도메인 객체를 제대로 조립하려면, Repository가 여러 DAO에 각각 쿼리를 날려서 결과를 DTO로 받고, 그걸 다시 조합해야 하나 싶었다. 예약 하나를 만들려고 해도 시간과 테마를 먼저 조회해서 끼워 넣어야 하니까. 그런데 막상 짜보면 DAO가 이미 도메인 객체를 다 만들어 버리고, Repository는 그걸 그대로 넘겨주기만 하는 한 줄짜리가 됐다. 이게 맞는 건지, 아니면 내가 생각한 조립 책임을 Repository에 줘야 하는 건지 리뷰어인 웨지에게 물어봤다.

도메인 객체도 마음에 걸렸다. Reservation, Theme, ReservationTime은 사실상 getter만 가진 데이터 덩어리였고, 중복 예약을 막는 규칙 같은 건 도메인이 아니라 서비스 쪽에 흩어져 있었다. 마틴 파울러가 "빈약한 도메인 모델(Anemic Domain Model)"이라고 부르며 객체지향의 기본과 배치되는 안티패턴이라고 지적한 그 형태였다. 풍부한 도메인을 만들고 싶었지만 트랜잭션과 DB 의존성 때문에 서비스에서 처리하는 쪽으로 타협했다고 적었다.

REST도 마찬가지였다. 시간 조회 API를 설계하면서, 단순 시간 목록(`GET /times`)과 특정 날짜와 테마에 대해 예약 가능 여부까지 계산해서 주는 목록을 어떻게 가를지 고민했다. 후자는 단순한 테이블 데이터가 아니라 조인과 비즈니스 로직으로 계산된 "가공된 상태"라, 별도 리소스(`/availabilities`)로 빼는 게 맞나 싶었다. 그런데 새 이름을 만들자니 리소스의 정체성이 모호해지는 것 같아서, 결국 쿼리 파라미터(`GET /times?date=&themeId=`)로 타협하고 이것도 웨지에게 물어봤다.

돌아보면 한 미션 안에서 이렇게 타협을 많이 한 적이 없었다. 질문은 셋 다 비슷한 모양이었다. 공식 문서는 이렇게 하라는데, 끝까지 따라가면 비용이 너무 커져서 어딘가에서 멈췄다. 근거는 댔지만, 정작 어디에 기준을 세워야 할지는 감을 못 잡고 있었다.

### "DDD를 왜 적용해야 하나요?"

웨지의 첫 리뷰는 Repository와 DAO를 짚었다.

> 레이어드를 적용하다보면 100% 규칙에 맞출수는 없습니다. 대략 70% 정도는 들어맞고, 30% 정도는 아무것도 없이 위임을 하는 코드가 되면 어느정도 성공인데요.
>
> 구현하신 내용에서는 100% 위임을 하고 있으니 실익이 없는 코드이고, 기계적인 패턴 적용으로 안티패턴입니다.
>
> DDD를 왜 적용해야 하나요? 여기에 대한 답변부터 해보셔야 할거 같네요

올 게 왔다는 느낌에 가까웠다. 다만 막상 답을 하려니 막혔다. 트레이드오프라는 것도 정답이 없다는 것도 알지만, 내가 아는 지식으로는 뭐가 내 상황에 더 맞는지 알 수가 없었다.

나는 PR에 이미 내 입장을 적어뒀다. 에반스를 근거로, DAO는 데이터만 반환하고 Repository가 그 데이터를 완전한 도메인 객체로 재조립해야 한다고 봤다. 그래서 "DDD를 왜 적용해야 하나요?"라는 물음은 나에게 "왜 굳이?"처럼 들리기도 했다.

내 생각은 이랬다. 관심사가 다른 Repository와 DAO를 혼용하고 싶지 않았다. 게다가 예약은 테마를 비롯한 다른 객체까지 들고 있는 강결합 구조라 DB에서 JOIN을 쓸 수밖에 없었는데, 그걸 피하려고 쿼리를 따로따로 날려서 조립하는 것도 이상했다. 그렇다고 DDD를 접고 그냥 타협하면 너무 DB 중심이 되어 객체지향이 사라지는 것 같았다. 마땅히 내놓을 답은 없었지만, 그렇다고 마냥 수긍하고 싶지도 않았다.

돌아보면 코치 강의에서 들은 "스프링은 DDD에서 영감을 받았다"는 말이 머리에 박혀 있었다. 그래서 Repository라는 이름을 쓰면 DDD를 하는 거라고 막연히 믿었다.

답을 찾기 시작할 무렵 『오브젝트』를 쓴 조영호 님의 강연을 들었다. Controller, Service, Repository 구조는 사실 절차지향에 가깝고, 객체지향이 진짜 적용되어야 할 곳은 도메인 단이라는 이야기였다. 강연이 답을 준 건 아니었다. 다만 내가 당연하게 여기던 계층 구조부터 다시 의심해봐야겠다는 힌트는 됐다.

그제야 내 이해가 어디서 어긋났는지 보였다. 나는 스프링이 @Repository라는 어노테이션을 제공하니까, Repository는 당연히 DDD의 것이고, 도메인 객체와 DB를 매핑하려면 반드시 있어야 하는 장치라고 여겼다.

그래서 직접 찾아봤다. @Repository가 정말 DDD에서 온 건지, Repository와 DAO를 둘 다 두는 게 맞는지. 짧게만 옮기면, 내가 믿던 것만큼 근거가 분명하지는 않았다. 어노테이션이 처음 나왔을 때 설명에는 DDD 이야기가 없었고, 한참 뒤에야 덧붙은 문구였다. 3계층 구조 역시 DDD에서 온 게 아니라 다른 계보를 따라 굳어진 구조였다. 이름은 DDD를 빌렸지만 구조는 아니었다. 무엇보다 Repository는 스프링이 강제하는 구조가 아니라, 어떻게 쓸지는 내가 정하는 개념적인 용어였다. (이 추적은 길어서 따로 정리해 뒀다. [스프링은 DDD에서 영감을 받았을까](https://johnprk.github.io/spring/spring-annotation-ddd-myth/), [Repository와 DAO 둘 다 두지 않기로 했다](https://johnprk.github.io/spring/repository-dao-aggregate-root/).)

그러고 나서 내 코드를 다시 봤다. Repository는 DAO를 그대로 호출하는 한 줄짜리였고, 웨지 말처럼 하는 일이 아무것도 없었다. 형태만 DDD였다.

알고 나니 오히려 더 헷갈렸다. 정답이 있는 줄 알았는데 기준 자체가 없는 셈이라, 처음엔 어디서부터 봐야 할지 막막했다.

정리는 결국 이름에서 됐다. 이름이 마인드를 끈다. DAO라고 쓰면 메서드가 SQL 어휘로 흘러가고, Repository라고 쓰면 도메인 어휘로 흘러간다. 둘 다 두면 100% 위임이라 실익이 없으니 하나로 합쳐야 했고, 그러면 어느 이름을 남기느냐가 단순한 취향 문제가 아니었다. 나는 Repository를 남기기로 했다.

웨지는 빈약한 도메인 모델에 대해서도 따로 답을 줬다. 내가 트랜잭션과 DB 의존성을 근거로 들었던 부분이다.

> 그 선택의 근거가 무엇이냐가 중요한데, 트랜잭션과 DB 의존성을 근거로 들어주신 부분은 공감이 잘 안 됩니다. ... repository를 DB 접근 계층이라고 생각하지 말고 도메인 컬렉션이라고 접근하면서요.

이 말 앞에서는 솔직해질 수밖에 없었다. 트랜잭션과 DB 의존성은 사실 핑계였다. 도메인에 행위를 넣기가 어려웠던 게 아니라 어떻게 넣어야 하는지를 몰랐고, 그걸 인프라 문제로 포장했던 거였다.

### DAO를 걷어내고 객체에게 묻기로 했다

1차 리뷰를 받고 코드를 다시 손봤다.

먼저 DAO를 없앴다. JdbcTemplate은 Repository가 직접 들게 하고, DAO를 거쳐 한 줄로 위임하던 부분을 걷어냈다. Repository를 DB 접근 계층이 아니라 도메인 컬렉션으로 보기 시작했다.

가장 크게 바뀐 건 "이 시간에 예약이 있나?"를 확인하는 방식이다. 원래는 예약된 시간의 ID를 `Set<Long>`으로 꺼낸 다음, 그 집합을 서비스가 직접 뒤져서 비교했다.

```java
// before: 예약된 시간 ID를 꺼내서, 서비스가 직접 비교
Set<Long> reservedTimeIds = repository.findReservedTimeIdsByDateAndThemeId(date, themeId);
boolean occupied = reservedTimeIds.contains(time.getId());
```

데이터를 꺼내서 내가 절차적으로 처리하는 형태였다. 이걸 Reservations라는 일급 컬렉션으로 바꾸고, 컬렉션에게 직접 물었다.

```java
// after: 도메인 컬렉션을 받아서, 컬렉션에게 묻는다
Reservations reservations = repository.findOn(date, themeId);
boolean occupied = reservations.isOccupied(time);
```

줄 수는 비슷한데 책임이 옮겨갔다. before에서는 "예약 데이터를 꺼내 오는 일"과 "점유를 판단하는 일"이 서비스에 같이 있었다. after에서는 판단이 Reservations 안으로 들어가서, 중복 예약을 막을 때도 예약 가능 시간을 조회할 때도 같은 객체에게 같은 질문을 한다.

사실 이 방향은 웨지가 먼저 짚어준 거였다.

> reservationService니까 Reservation 컬렉션을 응답했으면 "TimeAvailability"라는 도메인적으로 객체간 협력할 수 있는 여지가 생기고 ... 예를 들어 Reservations가 컬렉션 일급 객체가 있고 reservations.findOccupiedTimes() 같은 메서드를 활용한다던지요.

그러면서 "`Set<Long>` 같은 데이터 자료구조가 호출자에게 노출되는 자리가 보이면 거기에 도메인 협력이 빠진 것"이라는 기준도 세웠다.

불필요한 쿼리에 대한 지적도 있었다. 시간을 저장한 뒤, 반환된 id로 다시 findById를 호출하고 있었다. 쿼리가 두 번 나갔다.

> 굳이 findById로 2번의 쿼리를 발생시킬 필요가 없어보여요. ... 방법은 여러가지가 있을텐데 쿼리를 2번 조회하는 것보다 유익이 확실한 방법들 입니다

JPA를 오래 쓰다 보니 save한 뒤 그 id로 다시 조회하는 패턴이 손에 배어 있었다. JdbcTemplate에서는 그럴 필요가 없는데 무심코 가져온 거였다. KeyHolder로 생성된 id를 받아, 저장하면서 완전한 객체를 바로 돌려주게 바꿨다.

```java
// before: 저장하고, 그 id로 다시 조회 (쿼리 2번)
Long id = timeRepository.save(reservationTime);
ReservationTime saved = timeRepository.findById(id);
```
```java
// after: 저장하면서 완전한 객체를 반환 (쿼리 1번)
ReservationTime saved = timeRepository.save(reservationTime);
```

비슷한 결의 지적이 더 있었다. 전체를 다 꺼내는 findAll은 데이터가 쌓이면 위험하다고 해서 예약 목록에 페이징을 붙였고, 개수가 사실상 정해져 있는(카디널리티가 확실한) ReservationTime과 Theme은 웨지 말대로 그냥 뒀다. 인기 테마 조회의 기준 날짜는 now를 파라미터로 받게 했는데, 단순히 유연성 때문이 아니라 그래야 테스트에서 '오늘'을 고정할 수 있어서 필요한 거였다. 시간 삭제와 테마 삭제가 같은 예외 메시지를 쓰던 것도 유즈케이스별로 나눴다.

한 가지, REST 질문에 대한 웨지의 답은 이 라운드에서 놓쳤다. 인라인 코멘트가 아니라 리뷰 본문에 적혀 있어서 뒤늦게야 봤다.

### 또 한 번의 리뷰, 그리고 머지

2차 리뷰가 왔다. "변화 요구가 큰 리뷰였는데 잘 반영해주셨어요"로 시작했지만, 새 리뷰가 더 붙어 있었다.

가장 길게 남은 건 REST였다.

사실 나는 표준을 좋아한다. 협업에서 기준이 없으면 서로 맞춰가는 데 드는 시간과 에너지가 크고, REST는 그 비용을 줄여주는 공통 규칙이라고 본다. 그런데 이번엔 그 표준을 우리 상황에 맞게 살짝 비틀고 싶었다. 예약 가능 여부까지 계산된 목록을 위해 `/availabilities` 같은 새 리소스를 만들자니 정체성이 모호해 보여서, 같은 `/times`에 쿼리 파라미터를 붙이는 쪽을 택했다.

웨지는 1차부터 그걸 반대했는데, 이유가 구체적이었다.

> 클라이언트가 파라미터 여부에 따라 기대하는 건 필터링이나 정렬인데, api 동작 자체가 달라지는 건 예측하기 어려워요. 그리고 파람에 따라 응답 객체가 다른데, 이건 X표 드리겠습니다. (클라 입장에서 파싱 코드 만들어보면, 파라미터에 따라 응답 객체 파싱을 분기해서 하는 게 유지보수성이 매우 떨어집니다.)

2차에서 한 번 더 짚였다.

> 꼭 API를 분리해주셔요. REST의 본질은 'API 규칙을 정해서 서로 편하자' 인데, 규칙을 벗어나려면 기술적으로 타당한 이유가 있어야 합니다. '리소스 개념상 비슷한거 같으니까 api 하나면 표현 가능하지 않을까' 이건 타당한 이유가 아닙니다. 받는 입장에서 불편하거든요.

결국 엔드포인트를 분리했다.

```
// before: 같은 URL인데 파라미터 유무로 응답 모양이 갈림
GET /times
GET /times?date={date}&themeId={themeId}
```
```
// after: 계산된 결과는 별도 엔드포인트로
GET /times
GET /times/availability?date={date}&themeId={themeId}
```

여기서 배운 건 분명했다. 같은 URL인데 파라미터에 따라 응답 모양이 갈리면, 그걸 받아 파싱하는 쪽이 분기를 떠안는다. "리소스가 비슷하니까"는 내 편의지 받는 쪽의 편의가 아니다. 이 부분은 다음에 비슷한 상황을 만나도 헷갈리지 않을 것 같다.

다만 거기까지였다. 처음 내가 물었던 "계산된 상태를 어떻게 RESTful하게 표현하나"라는 더 큰 질문의 답은 여전히 모르겠다. 내 규칙(쿼리 파라미터)이 틀렸다는 건 알겠는데, 그럼 뭐가 맞는지는 지금도 못 정했다. 확신이 없으니 웨지를 설득할 수도 없었고, 그냥 따른 쪽에 가까웠다. 표준을 좋아한다면서도, 정작 이 경우의 표준은 내 손으로 세우지 못했다.

3차 리뷰에서 웨지는 승인을 눌렀다.

> 요번 사이클은 여기서 머지할게요. ... 수고하셨습니다!

머지는 늘 기분이 좋다. 다만 이번엔 리뷰가 세 차례 오가서, 후련한 것만큼 심적으로도 체력적으로도 지쳐 있었다.

### 마치며

들어갈 때 나는 "공식 문서대로 먼저"라는 원칙을 갖고 있었다. 그건 지금도 유효하다. 협업에서 주관이 부딪힐 때 원저자의 의도라는 공통 기준이 있으면 가장 빠르게 합의에 닿는다고 보고, 그래서 이 원칙은 계속 가져갈 생각이다.

다만 한 가지는 인정해야 한다. DDD를 "적용했다"던 처음의 나는 근거 없이 형태만 따라 한 것에 가까웠다. 웨지의 "왜?"가 그걸 드러냈고, 이번에 비로소 내 말로 답할 근거가 생겼다. 근거가 보강된 게 아니라, 없던 근거가 생긴 거다.

그리고 인용과 판단은 다르더라. 나는 개념을 최대한 원저자의 의도대로 적용하려 했고, 웨지는 "70%만 맞아도 성공"이라는 말처럼 그걸 현실에서 쓸 만한 선까지 끌어내렸다. 그래서 DDD도 끝까지 이상적으로 가기보다 내가 할 수 있는 만큼까지만 바꿨다. 근거는 또렷해졌지만 구현은 거기서 멈췄다.

REST는 거기까지도 못 갔다. 내가 규칙을 잘못 만들었다는 것까지는 알았지만, 그럼 뭐가 맞는지는 지금도 모른다. 숙제로 남았다기보다, 아직 내가 못 푼 문제다.

사실 이 사이클은 테코톡 준비와 겹쳐 있었다. 발표가 머지 이틀 뒤였으니, 미션 내내 정신이 없었다. 그래서 회고를 쓰기 전까지는 미션도 대충 넘겼다고 기억하고 있었다. 그런데 기록을 다시 보니 아니었다. 리뷰 답변을 길게 달았고, 같은 주에 글 두 편을 따로 정리해 뒀더라. 생각보다 놓친 것 없이 진행했던 것 같다.

AI도 많이 썼다. 어노테이션의 출처를 거슬러 올라갈 때처럼 빠르게 찾고 확인하는 데는 분명히 도움이 됐다. 다만 무엇을 근거로 삼고 어디서 멈출지 판단하는 건 결국 내 몫이었다.

정답을 다 찾은 사이클은 아니었다. 오히려 내가 어디를 모르는지가 또렷해진 사이클이었다는 생각이 든다.
