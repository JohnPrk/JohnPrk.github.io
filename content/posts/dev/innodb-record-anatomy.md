B+트리를 공부하고 있었다. 인덱스가 B+트리고, 트리의 노드가 곧 페이지고, 페이지는 16KB다. 여기까지는 말할 수 있었다.

그런데 그게 암기 이상은 아니었다. 페이지 안에 데이터가 어떤 모양으로 들어 있는지, 그걸 어떻게 읽어내는지는 모르는 상태였다. 아는 걸 말해보라고 하면 문장은 나오는데, 그 문장이 실제로 무엇을 가리키는지는 설명하지 못했다.

그래서 방향을 바꿔서 아래부터 다시 내려갔다. 레코드 한 줄이 바이트로 어떻게 생겼는지부터 확인하고, 그 위에서 INSERT와 DELETE와 UPDATE가 무슨 일을 하는지까지 따라갔다. 이 글은 그 기록이다.

확인 환경은 도커에 띄운 MySQL 8.4.10이다. 테이블을 몇 개 만들고 `.ibd` 파일을 직접 덤프해서 바이트를 읽었다. 본문의 16진수 값과 주소는 그 덤프에서 읽은 값이다.

### 레코드가 담기는 곳, 16KB 페이지

InnoDB의 페이지는 16384바이트로 고정이다. 안쪽은 이렇게 나뉜다.

```
0     +------------------------------+
      | FIL Header            38B    |
      | Page Header           56B    |
      | Infimum . Supremum    26B    |
      +------------------------------+
      | User Records                 |
      +------------------------------+
      | Free Space                   |
      +------------------------------+
      | Page Directory               |
      +------------------------------+
      | FIL Trailer            8B    |
16384 +------------------------------+
```

레코드는 User Records 영역에 쌓인다. User Records는 앞에서 뒤로 자라고, Page Directory는 페이지 끝에서 앞으로 자란다. 둘이 Free Space에서 만난다.

여기서 궁금한 게 생겼다. 페이지는 16KB로 고정인데 레코드 하나의 크기는 고정이 아니다. `VARCHAR`가 있으면 행마다 길이가 다르고, `NULL`이 들어가면 또 달라진다.

> 그러면 이 바이트 덩어리에서 한 레코드가 어디서 시작해서 어디서 끝나는지를 무엇이 알려주는가.

이게 이 글에서 계속 따라간 질문이다.

### 확인에 쓴 테이블

앞으로 나오는 바이트 값이 어디서 나온 건지 알 수 있게 테이블부터 적어둔다.

```sql
CREATE TABLE fmtlab.simple (
  id   INT         NOT NULL,
  name VARCHAR(20) DEFAULT NULL,
  age  INT         DEFAULT NULL,
  PRIMARY KEY (id)
) ROW_FORMAT=DYNAMIC;

INSERT INTO fmtlab.simple VALUES (1, 'tinu', 29), (2, 'abc', NULL), (3, NULL, 7);
```

가변 컬럼과 `NULL`이 둘 다 있는 경우를 보려고 만든 테이블이다. 그리고 그 반대쪽으로 하나 더 만들었다.

```sql
CREATE TABLE fmtlab.chain (
  id INT     NOT NULL,
  v  CHAR(4) NOT NULL,
  PRIMARY KEY (id)
) ROW_FORMAT=DYNAMIC;

INSERT INTO fmtlab.chain VALUES (10, 'aaaa'), (30, 'cccc'), (50, 'eeee');
```

전부 고정길이에 전부 `NOT NULL`이라서 모든 행의 크기가 26바이트로 똑같다. 여기에 나중에 20을 끼워 넣을 참이다.

### 레코드는 연결 리스트다, 그런데 바이트 덩어리다

처음 들었을 때 이 두 문장이 안 붙었다. 연결 리스트라고 하면 노드 객체가 다음 노드의 참조를 들고 있는 그림이 떠오르는데, 여기는 그냥 파일에서 읽어온 16384바이트다. 객체도 포인터도 없다.

답은 레코드 헤더 안에 있었다. 헤더의 마지막 2바이트가 `next_record`인데, 이 값은 **다음 레코드까지의 거리**다. 주소를 통째로 담고 있는 게 아니라, 지금 위치에 이 값을 더하면 다음 레코드의 위치가 나오는 형태다.

덤프에서 읽은 값이다.

```
simple  00 20  ->  +32   ->  현재 127 + 32 = 159 가 다음 레코드
chain   FF B7  ->  -73   ->  현재 185 - 73 = 112 가 다음 레코드
```

처음에 나는 `next_record`가 "이 레코드의 총 길이"라고 생각했다. 127에서 32를 더해 159가 나오니까 그 해석으로도 앞뒤가 맞았다. 그런데 두 번째 값이 음수다. 길이가 음수일 수는 없으니 그 해석은 틀렸다.

### 논리 순서와 물리 순서는 다르다

음수가 나온다는 건 다음 레코드가 지금보다 앞쪽 주소에 있다는 뜻이다. 이게 처음에 제일 안 받아들여졌다. 키 순서대로 저장되어 있다고 알고 있었기 때문이다.

정렬되어 있다는 말이 두 가지로 나뉜다.

```
논리 순서   next_record 를 따라가면 나오는 순서.  이건 항상 키 오름차순이다
물리 배치   파일에 실제로 적힌 순서.             이건 그냥 들어온 순서다
```

키 순서대로 정렬되어 있는 건 논리 순서 쪽이다. 물리 배치는 삽입된 순서 그대로 쌓이고, 한번 자리를 잡으면 옮겨지지 않는다. 그래서 `id`가 10, 30, 50, 20 순으로 들어왔으면 파일에도 그 순서로 적혀 있고, 키 순서인 10, 20, 30, 50은 `next_record`를 따라가야 나온다.

> InnoDB는 레코드를 물리적으로 정렬하지 않는다. 순서는 `next_record`가 만든다.

이 문장 하나가 뒤에 나오는 INSERT와 DELETE의 동작을 거의 다 설명한다. 정렬을 바이트를 옮겨서 하는 게 아니라 2바이트짜리 값을 고쳐서 하기 때문에, 레코드를 넣거나 지울 때 주변을 건드릴 일이 없다.

### 원점

`next_record`가 가리키는 지점을 원점이라고 부른다. 그 레코드에서 **데이터가 시작하는 지점**이고, 페이지 안에서의 바이트 번호로 나타난다.

레코드 하나를 펼치면 이렇게 생겼다.

![InnoDB 레코드 레이아웃](/images/innodb/record-layout.svg)

원점을 기준으로 왼쪽은 거꾸로, 오른쪽은 순서대로 읽는다. 그리고 왼쪽 머리는 크기가 고정이 아니다. 세 조각을 하나씩 본다.

**헤더 5바이트.** 어떤 테이블이든 항상 5바이트다. 덤프에서 읽은 값은 `00 00 10 00 20`이었다. 안에 다섯 개가 들어 있는데, 이 글에서 쓰는 건 둘이다.

- `info_bits` 안의 삭제 표시 비트다. `DELETE`가 켜는 게 이 비트다.
- `next_record`다. 방금 본 그 2바이트다.

나머지 셋(`n_owned`, `heap_no`, `record_type`)은 페이지를 다룰 때 쓰이는 값이라 이름만 적어두고 넘어간다.

중요한 건 크기가 항상 5바이트라는 점이다. 위치가 고정이니까 테이블 정의를 몰라도 이 5바이트는 읽을 수 있다.

**NULL 비트맵.** `NULL`이 될 수 있는 컬럼마다 1비트씩 쓴다.

이게 왜 필요한지가 처음엔 이해가 안 갔다. `NULL`이면 빈 값을 넣으면 되는 것 아닌가 싶었다. 그런데 `NULL`은 데이터 영역에 아무것도 안 쓴다. 0바이트다. 빈 값을 채우는 게 아니라 그 컬럼을 통째로 건너뛴다. 그러면 읽는 쪽에서는 그 컬럼이 빠졌다는 걸 알아야 나머지를 제대로 끊어 읽을 수 있다. 그 표시가 비트맵이다.

크기는 `NULL` 가능 컬럼 수를 8로 나눠 올림한 값이다. `simple`은 `name`과 `age` 둘이라 1바이트다.

세 행의 실측값이다. 비트는 컬럼 정의 순서대로 붙는다.

```
(1, 'tinu', 29)   ->  00   둘 다 값이 있다
(2, 'abc', NULL)  ->  02   두 번째 비트, age 가 NULL 이다
(3, NULL, 7)      ->  01   첫 번째 비트, name 이 NULL 이다
```

`chain`처럼 `NOT NULL`만 있는 테이블은 비트맵 자체가 없다. 0바이트다.

**가변길이 배열.** `NULL`이 아닌 가변 컬럼마다 실제 길이를 적어둔다.

`VARCHAR(20)`이라고 해도 실제로 저장되는 건 그때그때 다르다. `'tinu'`는 4바이트고 `'abc'`는 3바이트다. 고정길이 컬럼은 정의만 보면 몇 바이트인지 알지만, 가변 컬럼은 저장해 두지 않으면 알 방법이 없다. 그래서 이 자리에 적는다.

길이가 127 이하면 1바이트, 넘으면 2바이트를 쓴다. 첫 바이트의 최상위 비트가 1이면 2바이트짜리로 읽는다.

```
04     ->  'tinu' 가 4바이트다
81 2C  ->  최상위 비트가 1이므로 2바이트로 읽어서 300이다
```

여기에도 안 들어가는 게 있다. 고정길이 컬럼은 정의로 아니까 안 적고, `NULL`인 컬럼은 데이터가 없으니 안 적는다. `chain`은 전부 고정길이라 이 배열도 0바이트다.

그리고 이 배열은 역순으로 들어간다. 원점에서 거꾸로 읽으니까 첫 번째 가변 컬럼이 원점에 제일 가까운 자리에 있다.

**그래서 머리 크기가 행마다 달라진다.** 덤프로 확인한 값이다.

| | NULL 비트맵 | 가변길이 배열 | 헤더 | 머리 합계 |
|---|---|---|---|---|
| `chain` 전체 | 0B | 0B | 5B | **5B** |
| `simple` (1, 'tinu', 29) | 1B | 1B | 5B | **7B** |
| `simple` (3, NULL, 7) | 1B | 0B | 5B | **6B** |

같은 테이블 안에서도 다르다. 세 번째 행은 `name`이 `NULL`이라 가변길이 배열이 통째로 없어졌다.

### DB_TRX_ID와 DB_ROLL_PTR

도해의 오른쪽을 보면 PK 바로 뒤에 내가 만든 적 없는 컬럼이 두 개 껴 있다. 처음 봤을 때 이게 뭔지 몰라서 넘어갔는데, 뒤에 계속 나와서 짚고 간다.

- `DB_TRX_ID`는 6바이트이고, 이 행을 마지막으로 건드린 트랜잭션의 번호가 들어간다.
- `DB_ROLL_PTR`은 7바이트이고, 그 변경 직전의 값이 적혀 있는 언두 로그의 주소가 들어간다.

둘이 붙어 있으니까 레코드 하나가 지금 값과 직전 값으로 되돌아가는 길을 같이 들고 있는 셈이다. 뒤에 나오는 `UPDATE`와 `DELETE`가 하는 일이 대부분 이 두 개를 고치는 것이다.

PK를 만들지 않아도 이 자리는 생긴다. 그때는 `DB_ROW_ID` 6바이트가 하나 더 붙어서 그게 PK 역할을 한다. PK가 없는 InnoDB 테이블은 없다.

### 왜 하필 원점인가

여기서 한동안 막혔다. 기준점을 레코드의 진짜 첫 바이트, 그러니까 가변길이 배열의 시작으로 잡으면 안 되나 싶었다. 앞에서부터 순서대로 읽는 게 자연스럽지 않나 싶었다.

안 된다. 머리는 거꾸로만 읽을 수 있기 때문이다.

순서를 따져보면 이렇다.

```
1. 가변길이 배열이 몇 개인지 알려면  ->  NULL 비트맵을 먼저 읽어야 한다
                                        (NULL 인 컬럼은 여기 자리를 안 차지하니까)
2. NULL 비트맵의 크기를 알려면       ->  테이블 정의를 봐야 한다
3. 그런데 주소 순으로는 가변길이 배열이 NULL 비트맵보다 앞에 있다
```

앞에서부터 읽으면 첫 바이트에서 막힌다. 그 바이트가 가변길이 배열의 몇 번째 값인지 알 방법이 없기 때문이다.

> 그래서 기준점이 머리의 끝, 즉 데이터가 시작하는 지점에 있어야 한다. 원점은 이 레코드에서 위치가 고정된 유일한 지점이다.

덤으로 따라오는 것도 있다. 5바이트 헤더는 항상 원점 바로 앞이다. 위치가 고정이라서 테이블 정의를 몰라도 `next_record`를 읽을 수 있다. 체인만 따라가는 작업은 스키마 없이도 된다.

### infimum과 supremum

페이지마다 가짜 레코드가 두 개씩 있다. 위치는 고정이다.

```
infimum    94 ~ 106   원점 99    이 페이지의 어떤 키보다 작은 값이다
supremum  107 ~ 119   원점 112   이 페이지의 어떤 키보다 큰 값이다
```

둘 다 실제 데이터가 아니라 경계 표시다. infimum이 체인의 출발점이고, supremum이 체인의 끝이다.

이게 있으면 예외 처리가 사라진다. 맨 앞에 레코드를 넣는 것도 "infimum의 `next_record`를 고친다"로 처리되고, 마지막 레코드도 그냥 다음을 가리키면 되니까 여기가 끝인지를 따로 검사할 필요가 없다. 빈 페이지에서도 구조가 그대로 성립한다.

### 다음 레코드가 다른 페이지에 있으면

여기까지 보고 나서 걸린 게 있었다. `next_record`는 원점에서 다음 원점까지의 거리인데, 그건 같은 페이지 안에서나 되는 얘기다. 페이지가 넘어가면 어떻게 되는지 궁금했다.

넘어갈 수 없다. `next_record`는 16비트고 페이지 안의 위치를 나타내기 때문에 16KB 바깥을 가리킬 수가 없다. 페이지의 마지막 레코드는 supremum을 가리키고, 거기서 그 페이지의 체인은 끝난다.

페이지 사이를 잇는 건 다른 장치인데, 그건 페이지를 공부할 때 다루려고 한다.

### 목적에 따라 읽는 범위가 다르다

레코드 하나를 다룰 때 항상 전체를 읽는 게 아니다.

| 하려는 일 | 읽는 범위 |
|---|---|
| 다음 레코드로 이동 | 헤더 5바이트만 읽는다 |
| 삭제됐는지 확인 | 헤더 5바이트만 읽는다 |
| 실제 값 꺼내기 | 헤더에서 NULL 비트맵, 가변길이 배열, 데이터까지 읽는다 |

첫 줄이 실제로 언제 쓰이는지가 잘 안 떠올랐는데, 뒤에 나올 `DELETE`를 보고 나서 이해했다.

`DELETE`는 레코드를 지우지 않고 헤더의 비트만 켠다. 그래서 지워진 레코드도 한동안 체인에 그대로 매달려 있다. 스캔이 그 자리를 지날 때는 헤더 5바이트만 읽고 삭제 표시를 확인한 다음, 값은 한 바이트도 안 읽고 바로 다음으로 넘어간다.

그리고 값을 전부 꺼내는 것과 키만 비교하는 것도 다르다. 찾는 도중에는 데이터의 앞쪽 PK만 읽고 나머지 컬럼은 건드리지 않는다.

이 순서는 레이아웃과도 맞아떨어진다. 사전 정보가 덜 필요한 것이 원점에 가깝게 놓여 있다. 헤더는 아무것도 몰라도 읽히고, NULL 비트맵은 테이블 정의가 필요하고, 가변길이 배열은 테이블 정의와 비트맵이 둘 다 필요하다. 필요한 정보가 많을수록 바깥으로 밀려 있다.

### 끝은 저장되어 있지 않다

마지막까지 안 풀렸던 질문이 이거였다. 시작은 원점이 알려준다고 치고, 끝은 무엇이 알려주는지가 안 보였다. 종료 표시 바이트 같은 게 있나 싶었다.

없다. 끝은 계산된다.

재료가 셋이다.

```
테이블 정의     고정길이 컬럼의 길이를 알려준다
NULL 비트맵     빠진 컬럼을 알려준다
가변길이 배열   가변 컬럼의 실제 길이를 알려준다
```

덤프에서 확인한 계산이다. 원점 127에서 시작하는 `(1, 'tinu', 29)`는 이렇게 끝난다.

```
127 + (id 4 + DB_TRX_ID 6 + DB_ROLL_PTR 7 + name 4 + age 4) = 152
```

그리고 이 셋 중 하나라도 없으면 계산이 안 된다. 컬럼 사이에 구분자도 없어서, 정의를 모르면 어디서 끊어야 할지조차 알 수 없다.

> 테이블 정의 없이는 `.ibd` 파일이 해독 불가능한 바이트 덩어리다.

MySQL 8.0이 `.ibd` 파일 안에 테이블 정의를 넣는 SDI 페이지를 만든 이유가 여기 있다. 그 전에는 정의가 `.frm`이라는 별도 파일에 있었다. 데이터와 정의가 따로 놀면 하나만 잃어버려도 나머지가 쓸모없어진다.

### INSERT는 어디에 바이트를 쓰는가

여기서부터는 레코드 위에서 일어나는 일이다.

먼저 짚어둘 게 있다. PK가 `auto_increment`여야 하는 게 아니다. `id`를 직접 넣으면 아무 순서로나 들어간다. 그래서 아래 같은 상태가 특별한 경우가 아니라 흔한 경우다. `chain` 테이블도 10, 30, 50을 먼저 넣고 나중에 20을 끼워 넣었다.

```
논리 순서 (next_record 링크)
  infimum -> 10 -> 20 -> 30 -> 40 -> supremum

물리 배치 (삽입된 순서대로 쌓인다)
  [30][10][40][20][      빈 공간      ]
```

이 페이지는 30, 10, 40, 20 순으로 들어온 것이다.

INSERT 한 건이 실제로 건드리는 것을 늘어놓으면 이렇게 된다.

```
1. 트리 탐색            루트 -> 브랜치 -> 리프. 들어갈 페이지를 찾는다
2. 페이지 안 위치 결정   이 키의 바로 앞 레코드를 찾는다
3. 물리 공간 확보        바이트를 실제로 어디에 쓸지 정한다
4. 레코드 조립           헤더 + 숨은 컬럼 + 데이터를 쓴다
5. 링크 연결             next_record 두 개를 고친다
6. 디렉토리 갱신
7. 언두 . 리두 기록      롤백 대비와 크래시 대비
8. (공간이 없으면) 분할
```

이 중에서 이 글이 따라가는 건 3번 하나다. 나머지는 조건을 붙여서 빼놨다. 페이지에 자리가 남아 있어서 8번 분할이 안 일어나고, 트랜잭션은 하나만 돌고 있고, 세컨더리 인덱스는 없는 경우로 한정한다. 조건이 붙으면 이야기가 커지는데 거기까지는 아직 안 봤다.

가장 단순한 경우만 보겠다는 뜻이다. 여기에 25를 넣는다고 하자. 논리적 위치는 20과 30 사이로 정해졌다. 그러면 25의 바이트를 물리적으로 어디에 쓸까.

이걸 예측 문제로 받았을 때 나는 "빈 공간 맨 앞에 그냥 붙인다"고 답했다. 답은 맞았는데 이유가 틀렸다. 내가 댄 이유는 "힙 메모리라서 주소값이 더 작아질 수는 없지 않나"였다.

여기서 말하는 힙은 프로세스 메모리의 힙이 아니다. 16KB 페이지 안에서 레코드가 쌓이는 영역을 부르는 이름일 뿐이고, 페이지 헤더에 여기까지 썼다는 표시가 따로 있다. `malloc`과는 관계가 없고 우선순위 큐 자료구조도 아니다.

정답의 진짜 이유는 다른 데 있었다.

> 기존 레코드를 움직이면 안 된다. 주소가 커져야 해서가 아니라, 남의 자리를 건드릴 수 없어서 빈 데를 쓰는 것이다.

움직이면 안 되는 이유는 `next_record`가 상대 오프셋이기 때문이다. 레코드 하나를 밀면 그 레코드를 가리키던 값도, 그 레코드가 가리키던 값도 전부 다시 계산해야 한다. 한 건 넣으려다 페이지 안의 링크를 줄줄이 고치게 된다.

그리고 그렇게까지 할 이유가 없다. 논리 순서는 이미 `next_record`가 들고 있고, 물리 순서를 보는 코드가 없다.

이건 덤프로 확인했다. `chain` 테이블에 10, 30, 50을 넣은 뒤 20을 추가했다.

```
주소 125   id=10   next_record = +78  ->  203
주소 151   id=30
주소 177   id=50
주소 203   id=20   next_record = -52  ->  151
```

20의 바이트는 맨 뒤인 203에 적혔다. 그리고 바뀐 것은 `id = 10`의 `next_record` 하나뿐이었다. 원래 `+26`으로 바로 뒤의 30을 가리키던 값이 `+78`로 덮어써졌다. 30과 50은 한 바이트도 안 움직였다.

모든 행이 26바이트로 똑같은 테이블인데도 `next_record`가 `+78`과 `-52`로 튀는 게 인상적이었다. 크기를 아는 것과 순서를 아는 것이 별개라서, 크기가 전부 같아도 이 2바이트는 여전히 필요하다.

### 재시작하면 정렬될까

물리 배치가 계속 뒤죽박죽이면 언젠가 정리하지 않을까 싶었다. 서버를 껐다 켜면 맞춰주지 않을까 생각했다.

안 한다. 껐다 켜도 그대로다.

디스크에 저장되는 것은 레코드 목록이 아니라 페이지 이미지 자체다. 16384바이트를 통째로 쓰고 통째로 읽는다. 정렬하려면 모든 페이지를 읽어서 다시 써야 하는데, 큰 테이블이면 기동에만 몇 시간이 걸린다. 그리고 얻는 게 없다. 페이지 안에서 물리 순서를 보는 코드가 없기 때문이다.

### 디스크 I/O는 언제 일어나나

`.ibd`에 들어 있는 게 그 뒤죽박죽 배치가 맞다. 그리고 메모리로 올라올 때 변환하지 않는다. 디스크 바이트와 메모리 바이트가 같다.

다만 통째로 올라오지 않는다. 버퍼 풀이라는 메모리 공간이 있고, 여기에 필요한 페이지만 16KB 단위로 올라온다.

읽기는 버퍼 풀에 없을 때만 디스크로 간다. 트리 탐색이 루트, 브랜치, 리프 3단계여도 루트와 브랜치는 거의 항상 버퍼 풀에 있어서 실제 디스크 접근은 리프 한 번인 경우가 많다.

쓰기는 예상과 달랐다. `INSERT`를 해도 `.ibd`에 바로 안 쓴다. 버퍼 풀의 페이지만 고치고 더러움 표시를 하고 끝이다. 커밋해도 안 쓴다. 커밋 시점에 디스크로 확실히 나가는 것은 `.ibd`가 아니라 리두 로그다.

```
커밋  ->  리두 로그를 디스크에 내린다   순차 쓰기라 빠르다
      ->  .ibd 는 나중에               랜덤 쓰기라 느리다
```

> 느린 랜덤 쓰기를 빠른 순차 쓰기로 바꿔치기한 구조다.

### DELETE는 지우지 않는다

`DELETE FROM member WHERE id = 35`를 실행하면 페이지 안에서 일어나는 일은 이게 전부다.

```
레코드 35 헤더의 info_bits 중 비트 하나  ->  1
레코드 35의 DB_TRX_ID                    ->  지운 트랜잭션 번호
레코드 35의 DB_ROLL_PTR                  ->  언두 로그 주소
```

데이터 바이트는 그대로 있고 링크에도 그대로 매달려 있다.

```
infimum -> 10 -> 20 -> 30 -> [35 삭제표시] -> 40 -> supremum
                              여전히 체인 안에 있다
```

이유는 둘이다. 롤백하면 비트만 다시 끄면 되기 때문이 하나고, 나보다 먼저 시작한 트랜잭션은 아직 35를 봐야 하기 때문이 다른 하나다. 앞에서 본 `DB_TRX_ID`와 `DB_ROLL_PTR`이 여기서 쓰인다.

한참 뒤에 purge 스레드가 지나가면 그때 체인에서 떨어져 나오고, 그 자리는 페이지 안의 빈 자리 목록에 매달려서 다음 삽입이 재사용한다.

그러면 `.ibd` 파일에 빈 공간이 생기는지가 궁금했는데, 파일은 줄어들지 않는다. 지운 자리는 페이지 안에 남아서 `PAGE_GARBAGE`라는 값으로 잡히고, 페이지 자체가 파일에서 빠지지는 않는다. 10만 행짜리 테이블에서 일부를 지우고 6번 페이지를 읽어봤다.

```
6번 페이지   살아있는 레코드 214개   PAGE_GARBAGE 7,490 바이트
```

35바이트짜리 레코드 214개 분량이 페이지 안에 그대로 남아 있었다. 파일 크기는 960페이지 그대로였다.

> 삭제한 만큼 디스크가 비는 게 아니라, 페이지 안에 재사용 가능한 자리가 생기는 것이다.

그래서 purge가 오기 전까지는 스캔이 이 레코드들을 밟고 지나간다. 안 읽는 게 아니라 헤더만 읽고 버린다. 100만 건을 지웠으면 100만 번 그렇게 한다.

여기서 제일 큰 비용은 조회가 느려지는 것보다 페이지 수가 그대로라는 점이다. 900만 건을 지워도 페이지가 안 줄면 트리 높이도 그대로고 버퍼 풀도 계속 그만큼 차지한다.

### UPDATE는 길이 두 개다

`UPDATE`가 `DELETE`와 다른 점은 상황에 따라 완전히 다른 일을 한다는 것이다.

**길 A는 제자리 수정이다.** `age`를 30에서 31로 바꾸는 것처럼 크기가 안 변하면 그 자리 바이트를 덮어쓴다. `next_record`도 안 건드리고 위치도 그대로다. 제일 싼 경로다.

**길 B는 삭제 표시 후 새로 삽입이다.** `VARCHAR` 컬럼이 길어져서 그 자리에 안 들어가면, 기존 레코드에 삭제 표시를 켜고 빈 공간에 새로 쓴다. `UPDATE` 한 번에 레코드가 두 개가 된다. 하나는 지워진 것이고 하나는 살아있는 것이다.

PK를 바꾸면 무조건 길 B다. 클러스터 인덱스가 PK 순서로 정렬되어 있으니 논리적 위치가 완전히 달라지고, 다른 페이지로 가야 할 수도 있다.

그러면 길 A에서 덮어쓴 옛날 값 30은 어디로 갔는지가 남는다. 언두 로그에 있다.

```
레코드 25 (현재)                     언두 로그
  age = 31
  DB_TRX_ID   = 300
  DB_ROLL_PTR ------------------->   age였던 값 30, trx 200
                                       |
                                       +------------->  age였던 값 20, trx 100
```

`DB_ROLL_PTR`이 언두 로그를 가리키고, 언두 로그가 또 그 전 언두를 가리킨다. 연결 리스트가 하나 더 있는 셈이고, 이걸 버전 체인이라고 부른다.

그리고 언두에는 바뀐 컬럼만 들어간다. `age`만 고쳤으면 `age`의 옛날 값만 적는다.

> 언두 로그는 옛날 사본이 아니라 되돌리는 방법이다.

### 언두 로그는 두 종류뿐이다

```
insert undo   INSERT 용이다
update undo   UPDATE 와 DELETE 용이다
```

`DELETE`가 update 쪽에 묶인 게 힌트다. InnoDB 입장에서 `DELETE`는 삭제 표시 비트를 바꾸는 `UPDATE`다.

둘을 나눈 기준은 수명이다. insert undo는 커밋하는 순간 버리고, update undo는 커밋해도 한참 남는다.

**insert undo에는 PK만 들어간다.** 롤백하려면 그 레코드를 찾아서 없애면 되니까 찾을 수단만 있으면 된다. `INSERT` 이전의 상태는 그 행이 없는 상태라서 보존할 옛날 값이 애초에 없다. 그래서 커밋하면 바로 버려도 된다. 내 `INSERT`를 못 보는 옛날 트랜잭션은 그 행을 그냥 안 보면 되지, 되돌려서 보여줄 이전 버전이 없기 때문이다.

**그래서 `INSERT` 롤백은 진짜 물리 삭제다.** 커밋 안 된 내 트랜잭션이 넣은 행은 누구도 볼 수 없다. 남겨둘 이유가 없으니 삭제 표시를 하지 않고 페이지에서 떼어내 빈 자리 목록에 매단다.

**update undo에는 예전 `DB_TRX_ID`와 `DB_ROLL_PTR`, 그리고 바뀐 컬럼의 옛날 값이 들어간다.** 헤더 값을 같이 적어두는 이유는 버전 체인 때문이다. 언두 하나를 복원해서 나온 상태의 `DB_ROLL_PTR`이 그 앞 언두를 가리켜야 계속 거슬러 올라갈 수 있다.

**delete undo에는 세컨더리 인덱스 키에 들어가는 컬럼들이 같이 들어간다.** 이게 롤백용이 아니라 청소용이라는 게 제일 의외였다.

`DELETE`는 지운 적이 없으니 롤백할 때 복원할 게 없다. 비트만 끄면 된다. 그런데 나중에 이 레코드를 진짜 제거할 때는 클러스터 인덱스만 치우면 끝이 아니다. `name`에 인덱스가 걸려 있으면 그 인덱스에서도 해당 항목을 지워야 하는데, 세컨더리 인덱스 항목은 `(name, PK)` 형태라서 그때의 `name` 값을 알아야 찾을 수 있다.

```
id 35 를 치워야 한다
그런데 idx_name 에서 뭘 지우지
  -> 언두 로그를 본다 -> name 은 '홍길동'이었다
  -> idx_name 에서 ('홍길동', 35) 를 찾아서 제거한다
```

세컨더리 인덱스가 많은 테이블일수록 `DELETE` 언두가 커지는 이유가 롤백이 아니라 청소에 있었던 것이다.

세 개를 놓고 보면 기준이 하나로 모인다.

> 지금 물리적으로 지워도, 이걸 볼 수 있는 트랜잭션이 하나도 없는가.

```
INSERT 롤백  아무도 못 본다              ->  즉시 물리 삭제한다
DELETE       옛날 트랜잭션이 아직 본다   ->  비트만 켜고 나중에 치운다
UPDATE       마찬가지다                  ->  옛날 값은 언두에 둔다
```

이 정리는 한 번 틀렸다가 고친 것이다. 처음에는 `DELETE` 언두가 레코드 전체를 담는다고 알고 넘어갔는데, 하나씩 뜯어보니 복원할 게 없어서 전체를 담을 이유가 없었다.

### 미뤄둔 일을 치우는 쪽, purge

지금까지 나온 걸 모아보면 전부 나중으로 미뤘다.

```
DELETE      비트만 켠다.   실물은 안 치운다
UPDATE 길B  레코드를 남긴다. 실물은 안 치운다
언두 로그   계속 쌓인다.   안 버린다
```

그 나중을 담당하는 게 purge 스레드다. 여기서는 이런 게 있다는 정도만 짚고 간다.

미루는 이유는 판단 시점 때문이다. 트랜잭션 B가 `DELETE`를 하고 커밋했어도, B보다 먼저 시작한 A가 아직 그 행을 봐야 할 수 있다. 그런데 B 입장에서는 A가 언제 끝날지 알 수 없다. 그래서 판단을 다른 쪽으로 넘긴 것이다.

purge가 판단하는 기준은 단순하다. 그 레코드를 볼 수 있는 트랜잭션이 하나도 안 남았을 때 치운다. 실제로는 트랜잭션 번호를 비교한다. 번호가 계속 증가하니까 먼저 시작했다는 말이 번호가 작다는 말과 같아지고, 복잡한 판단이 숫자 비교 한 번으로 끝난다.

하는 일은 삭제 표시된 레코드를 체인에서 떼어내고, 그 자리를 재사용 목록에 넣고, 다 쓴 언두 로그를 버리는 것이다.

막히는 경우도 하나다. 오래 열려 있는 트랜잭션이 있으면 기준이 거기 묶여서 아무것도 못 치운다. 그동안 삭제 표시된 레코드와 언두 로그가 계속 쌓인다. `SHOW ENGINE INNODB STATUS`의 History list length가 계속 커지면 그 상태를 의심하면 된다.

### 정리

바이트를 하나씩 따라가면서 알게 된 건, 대단한 기법이 층마다 따로 있는 게 아니라 같은 방식이 반복된다는 점이다.

**옮기는 대신 화살표를 고친다.** 레코드는 삽입 순서로 쌓이고 움직이지 않는다. 순서는 `next_record`가 만든다. 물리 정렬을 포기한 대가로 삽입이 싸진다.

**지우는 대신 표시만 한다.** `DELETE`도 `UPDATE`의 길 B도 전부 비트 하나로 통일된다. 실제 제거는 한 곳으로 몰린다.

**판단을 미루고 한 곳에 몰아준다.** 지금 지워도 되는지를 각자 판단하지 않는다. purge가 나중에 판단한다.

그리고 레코드를 보면서 얻은 한 문장은 이거다.

> 계산할 수 있는 건 저장하지 않는다.

레코드의 끝은 계산되니까 안 적고, 키 순서로 다음이 누구인지는 계산이 안 되니까 2바이트를 내고 적는다. 저장할지 말지의 기준이 일관되어 있다.

처음에 막혔던 자리로 돌아가면, B+트리도 같은 기준으로 읽힌다. 비용은 비교 횟수가 아니라 페이지 접근 횟수이고, 그래서 한 페이지에 최대한 많은 키를 넣는 쪽으로 간 것이다.

다음은 페이지다. 페이지 안에서 레코드를 어떻게 찾는지부터 볼 생각이다. 레코드가 연결 리스트로만 이어져 있으면 페이지 안에서 하나씩 따라가야 하니 느릴 텐데 그렇지 않다고 하니, 그 이유가 제일 궁금하다.
